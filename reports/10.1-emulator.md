# 10.1: Android emulator end-to-end run

Task 10.1 of `mobile-automation-foundation` asks for three things, with no other user on the emulator:

- The Android driver's and the agent's gated suites must pass in full.
- The full harness must run on an emulator started with `-gpu host`, with the control flag on and off.
- Every Android gate must pass. The 50 ms tap-to-frame-change gate is re-measured first, since spike S7 measured 107.0 ms at p50 and 146.5 ms at p95 while the guest rendered in software.

This report records that run on 2026-09-27: the setup, the three suites, the two harness runs, the gates, the baselines and the findings. The runs' reports are committed under `reports/10.1-emulator-grpc/` (controller on) and `reports/10.1-emulator-agent/` (controller off).

## Verdict

Task 10.1 is not complete. One gated device test fails, one Android gate misses, and the controller-off run found a defect of its own.

- **Suites.**
  - `agent-android/test.sh` and the 61 agent host tests pass.
  - The Android driver's suite passes 215 of 216. `the_mirror_serves_compose_big_follows_a_tap_and_reports_a_killed_agent` failed all three times it ran, with `deadline_exceeded`, at 1-minute loads between 2.0 and 14.8.
  - The cause: the agent's Compose poll stalls for about 10 s re-reading a list that a tap has just torn down (finding 1, task 10.9).
- **Gates with the controller on** (`-gpu host -grpc 8554 -grpc-use-token`).
  - Pass: CLI start (11.6 ms at p95), cold attach (894.2 and 1,208.2 ms), and warm snapshot of the 500-cell screens (12.8 and 19.4 ms).
  - Tap-to-frame-change misses its 50 ms at p95 on both fixtures: 52.5 ms on Expo and 55.1 ms on Compose.
  - Host rendering halved the medians against S7's software rendering (45.4 and 31.7 ms, against 86.9 ms for S7's comparable span). It did not bring p95 under the limit.
  - The gate stays as written. [Tap to frame change](#tap-to-frame-change) has the numbers per GPU mode and the analysis.
- **Gates with the controller off** (`-gpu host -ports 5554,5555`).
  - Pass: CLI start (9.1 ms), cold attach (927.6 and 880.1 ms), and warm snapshot (13.2 and 11.3 ms).
  - Tap-to-frame-change has no frame source to measure. The bench counts every attempt as a failure instead of reporting it as not measured (finding 8).
- **Without frames, `open` settles too early** (finding 2). It reports the screen settled while the Expo fixture is still sliding in, and the next click aims at an element's mid-slide position.
  - Run 2's Expo flows: big-screen failed 46 of 50 iterations, list-scroll failed its golden check, and login was flaky in 3.
  - With the controller, the same flows passed every iteration.
  - No physical device has frames, so this matters for task 10.3. It is in neither task 10.9 nor 10.10.
- **Baselines.** They ran with the controller on only. Their flows do not use mobile-agent's controller, so run 1's numbers stand for both runs.
  - On the login and big-screen flows, mobile-agent was 4.3 to 14.5 times faster than Maestro 2.10.0 at p50, and 1.06 to 2.0 times faster than agent-device 0.21.14.
  - Both baselines failed the list-scroll golden check on both fixtures.
- **The bench.** As documented, it could not measure Android.
  - Without a shim, every series on the Big and List screens failed (finding 3).
  - The baselines lost UI automation to the agent (finding 4).
  - Both runs therefore went through `reports/10.1-emulator-grpc/bench-android-cli.rs`, kept as the run's record; task 10.10 has since made the harness measure Android without it.
- **The emulator.** Emulator 37.1.11 serves its controller even when started without `-grpc` (finding 10), so the controller-off run turned the endpoint off with `-ports 5554,5555`.

### GPU mode

The AVD's `config.ini` says `hw.gpu.mode=auto` and `hw.gpu.enabled=no`. S7 saw that resolve to software rendering. `-gpu host` overrides both for the session, in every launch here:

- `hardware-qemu.ini` has `hw.gpu.enabled = true` and `hw.gpu.mode = host`.
- The emulator log reports:
  - `Graphics backend: gfxstream`;
  - `vulkan_mode_selected:host gles_mode_selected:host`;
  - the Vulkan device `Apple M1 Max` through MoltenVK, with Metal external memory;
  - `OpenGL ES 3.0 (4.1 Metal - 90.5)`.
- In the guest, `ro.hardware.egl` is `emulation` and `ro.hardware.vulkan` is `ranchu`. SurfaceFlinger's RenderEngine reports `GLES: Google (Apple), Android Emulator OpenGL ES Translator (Apple M1 Max), OpenGL ES 3.0 (4.1 Metal - 90.5)`.
- For comparison, S7's session had `lavapipe` in `hardware-qemu.ini` and ANGLE on SwiftShader Vulkan in SurfaceFlinger.
- Boots:
  - The first launch refused the quickboot snapshot, which had been saved under the software renderer ("Change of GLES renderer detected"), and cold-booted. `sys.boot_completed` was set 25 s after the launch.
  - Later launches restored the snapshot saved at the previous exit.

### Method

- Each harness run started from the same state:
  - the emulator launched in that run's configuration;
  - the stock keyboard as the default input method;
  - no process of either baseline running on the device;
  - the launcher in front.
- Environment of every run:
  - `MOBILE_AGENT_DRIVERS=android`, so the daemon never listed or touched the host's Simulators.
  - `MOBILE_AGENT_SOCKET_DIR` and `AGENT_DEVICE_STATE_DIR` in private directories under `$TMPDIR`, so neither tool's daemon was shared with another user on the host.
- Load:
  - Every measurement started after a minute in which the 1-minute load average stayed under 10.
  - A logger sampled the load every 20 s throughout.
  - Other work used the host's iOS Simulators and built during the day, and the load reached 60 to 320 while they were busy. A hold between the two runs gave them a build window, and neither run overlapped one.

### Tap to frame change

The gate measures `frameChangeMs` from the click's reply. The span runs from the tap's dispatch to the capture of the first frame whose hash differs from the frame before it, leaving out the status bar. Its end is the frame's capture time, which is its arrival minus the lag the emulator's timestamp shows. It is therefore S7's production span (tap to the frame's timestamp), not S7's tap-to-arrival.

| GPU mode | Source | Screen | Frames | p50 ms | p95 ms | max ms |
|---|---|---|---|---|---|---|
| software (`auto`: lavapipe, ANGLE on SwiftShader) | S7, 40 trials | Settings, "Network & internet" row | RGB888 540x1200 | 86.9 (tap to arrival 107.0) | 130.5 (146.5) | |
| host (gfxstream on Metal) | run 1, 50 clicks | Expo fixture, `row-1` opening its detail | RGB888 540x1200 | 45.4 | 52.5 | 53.4 |
| host (gfxstream on Metal) | run 1, 50 clicks | Compose fixture, `row-1` opening its detail | RGB888 540x1200 | 31.7 | 55.1 | 57.2 |
| host, controller off | run 2 | both | none | not measurable; the bench records every attempt as failed (finding 8) | | |

The two host-rendered samples:

- **Expo**, sorted: 37, 37, 38, 38, 38, 38, 39, 40, 40, 40, 40, 40, 41, 42, 42, 42, 43, 44, 44, 44, 44, 44, 45, 45, 45, 46, 46, 47, 47, 47, 48, 48, 48, 48, 48, 48, 49, 49, 49, 49, 50, 50, 50, 50, 51, 51, 52, 52, 53, 53 ms.
  - The distribution is narrow: 16 ms from minimum to maximum.
  - Nine samples are at or over 50 ms.
- **Compose**, sorted: 23, 24, 24, 25, 25, 26, 26, 26, 27, 27, 28, 28, 28, 29, 29, 29, 29, 29, 29, 29, 30, 31, 31, 32, 32, 32, 32, 33, 33, 34, 34, 34, 35, 35, 35, 35, 36, 36, 36, 37, 38, 38, 39, 39, 42, 44, 49, 55, 56, 57 ms.
  - 47 of 50 samples are under 50 ms.
  - The p95 is the third-largest sample, 55.1 ms: three outliers of 55 to 57 ms set it.

Analysis:

- The span covers the whole guest path:
  - the tap's injection;
  - the app's response: React Native's JavaScript thread for Expo, Compose's recomposition for Compose;
  - drawing and composition at the display's 60 Hz, 16.7 ms a frame;
  - the wait for the emulator to post a frame to the controller's stream.
- On the controller side, S7 measured sendTouch at 0.49 ms (p50), and dispatch here took 2.8 to 3.3 ms at p95. The client is not where the time goes.
- The stream is part of the floor:
  - S7 found it posts frames at up to 45 fps at 540x1200: 44.7 fps under a continuous drag, 21.5 ms between frames at p50 and 32.5 ms at p95.
  - A change composed just after a posted frame waits up to one such interval for the next. A frame drawn just after a vsync waits up to 16.7 ms to be composed.
  - Together those waits reach about 38 ms in the worst alignment and about half that on average. A p95 under 50 ms therefore leaves roughly 12 ms for the input's delivery and the app's own response.
  - The fastest samples, 37.0 ms on Expo and 22.5 ms on Compose, show how much of the span the apps take in the best alignment.
  - S7 measured the stream's rate under software rendering. This run did not measure it again under host rendering.
- Against the limit: p95 is 2.5 ms (Expo) and 5.1 ms (Compose) over 50 ms. It is 7.1 and 23.4 ms above p50.
- As decided for this task, the gate and the spec stay as written, and the miss is recorded here.

## Findings

Tasks 10.9 (the agent) and 10.10 (the bench) on main cover findings 1 and 3 to 9. Finding 2 is new and in neither task; finding 10 concerns the emulator. The evidence is here so that each can be worked from this report.

### 1. A snapshot waits about 10 s behind a Compose re-read of a torn-down list (task 10.9)

- **What fails.** The driver test `the_mirror_serves_compose_big_follows_a_tap_and_reports_a_killed_agent` (`crates/android/tests/agent_session.rs`):
  - It opens the Compose fixture's Big tab.
  - It taps the Login tab through the mirror.
  - It takes a snapshot at line 167, which must list the Login form.
  - That snapshot failed with `deadline_exceeded` after the session's 10 s deadline, three times out of three: at 13:36, 13:39 and 18:27.
- **The agent's log** (`adb logcat -s mobile-agent AccessibilityInteractionClient`, first failure) shows that the stall was the Compose poll's re-read, walking the Big tab's list while the tap replaced it:

  13:36:44.471 16609 16631 D mobile-agent: java.lang.NullPointerException

### 10. Emulator 37.1.11 serves its controller even without `-grpc`

This finding is not part of task 10.10.

- Launched as `emulator -avd pixel_api36 -no-window -no-audio -no-boot-anim -gpu host`, the plan's launch for the controller-off run, the emulator logged:

  ```
  WARNING      | The emulator now requires a signed jwt token for gRPC access! Use the -grpc flag if you really want an open unprotected grpc port
  INFO         | Started GRPC server at 127.0.0.1:8554, security: Local, auth: +token
  ```

- Its discovery file `pid_<pid>.ini` held `grpc.port=8554`, `grpc.token`, `grpc.jwks`, `grpc.jwk_active` and `grpc.allowlist`.
- `emulator -help-all` lists `-grpc-use-jwt  Use a signed JWT token for gRPC authentication. (default, disable with -grpc flag)`.
- mobile-agent's daemon resolved the endpoint from the discovery file and attached through it: `input: emulator controller at http://127.0.0.1:8554 (taps, long presses and swipes)` and `frames: emulator controller, 38 received`.
- Leaving out `-grpc` therefore does not turn the controller off on this emulator, and nothing measured that way would have been the agent path.
- The emulator's help says only `-ports` requires gRPC to be enabled explicitly. Launched with `-ports 5554,5555`:
  - it wrote no discovery file;
  - port 8554 was closed;
  - `adb emu avd grpc` answered `KO: No active gRPC service`;
  - the daemon fell back to the agent: `input: agent (taps, long presses and swipes)`, `frames: none`, and the warning "emulator control endpoint unavailable for emulator-5554 (no discovery file names emulator-5554 in ...)".
- S7's negative path started a fresh AVD with `-port 5556 -no-snapshot` under software rendering and found no endpoint. Which launch condition turns the default endpoint on was not isolated here.
- **Consequences.**
  - A user who starts this emulator without `-grpc` still gets the fast path.
  - The android-driver spec's scenario "Control endpoint disabled" needs `-ports`, not the absence of `-grpc`, to be reproduced on 37.1.11.
  - The daemon has no switch to turn the controller off (`ControllerChoice::Auto` is fixed at `crates/daemon/src/devices/android.rs:202`), so a controller-off measurement depends on how the emulator was launched.
