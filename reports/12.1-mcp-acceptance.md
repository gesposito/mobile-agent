# 12.1: MCP server acceptance

Task 6.2 of `mcp-server` asks for the server driven through the fixtures on this session's own Simulator by a fresh agent session given only the instructions card and the `help` tool: a login, a scroll to a row, a wait for a change and a screenshot, with the turns, tool calls and tokens counted and the outcome recorded; Codex the same, since it is installed; and every gap a model stumbled on recorded as a task before the change is archived.

This report records those runs on the night of 2026-10-19 to 2026-10-20 UTC: the setup, the Claude Code run, the Codex run, the tool calls that failed and what the model did next, the read-only profile check, the findings and a rerun recipe. Times are UTC. The raw transcripts, the stream of every tool call and result in each client's JSON form, are kept privately, as the spike programs are (`docs/spikes/README.md`); every number below comes from them, and the two runs were verified afterwards through the CLI on the same daemon.

## Verdict

Both clients completed the five steps through the server with no failed tool call, and the CLI found the app afterwards as each model's report said: signed in as `agent`, the List tab scrolled to the fifties, the app running with the server's claim released.

- **Claude Code 2.1.304**, in print mode on `claude-fable-5-1`: 21 turns, 19 tool calls on the server and one of its own tool search, 4,649 output tokens with a context that grew from 28,595 to 43,691 tokens, $1.03, 89 s. It read the card: delta snapshots, refs, `get` for a text, `interactive: false` for the whole tree.
- **Codex 0.162.1**, through `codex exec` with the server's `default_tools_approval_mode = "approve"`, the setting that lets `exec` call the acting tools: 1 turn, 16 tool calls, 572 output tokens over 274,954 input of which 248,320 cached, 37 s. It worked by identifiers and text selectors, never a ref, and took every snapshot with `interactive: false`.
- **The read-only profile**: nine tools listed, and the model quoted the card's sentence on the profile from its context.
- **Gaps.** Four things the models worked around, none a failure: a status text is outside the interactive listing and a change wait's delta taken in it (finding 1); `fill` and `scroll --until` answer `✓ Done` alone, so a model takes a snapshot to see what they did (findings 2 and 3, tasks 6.4 and 6.5); a screenshot right after a click shows the transition the tap set off (finding 4). The card now says the first and the last (`crates/mcp/README.md`, The instructions card and `help`).
- **Not a gap of the server's**, recorded all the same: Claude Code's tool search turn, both clients' reading of standard input, the lazy list's hint, and the Simulator's identifier in `open`'s line (findings 5 to 11).

### Method

- **The task**, the same text for both clients: "Use only the mobile-agent MCP server's tools. 1. Open the app dev.mobileagent.fixture.swiftui on the iOS Simulator. 2. On its Login tab sign in with the username agent and the password hunter2, then use the wait tool's change mode to collect what changed and confirm the status text reads Welcome, agent. 3. Go to the List tab, scroll until Row 57 is in view, tap it, confirm Detail 57 is shown, then go back. 4. Take a screenshot and say in one line what it shows. 5. Report each step's outcome in one line each, and which tool calls failed, if any."
- **Claude Code**: `claude -p "<task>" --mcp-config mcp.json --strict-mcp-config --allowedTools "mcp__mobile-agent__*" --max-turns 40 --output-format stream-json --verbose`, run from the socket directory as its working directory, with `mcp.json` holding `{"mcpServers":{"mobile-agent":{"command":"<build>/mobile-agent-mcp","env":{"MOBILE_AGENT_SOCKET_DIR":"<dir>","MOBILE_AGENT_DRIVERS":"simulator"}}}}`. Print mode denies an MCP tool that is not allowed, and the allow rule `mcp__<server>__*` names every tool of one server (Claude Code's permissions reference, Tool name wildcards). The stream carries every tool call and result, each API request's usage, and a last line with `num_turns`, the usage totals, `duration_ms` and `total_cost_usd`.
- **Codex**: `codex exec --skip-git-repo-check --ephemeral --ignore-user-config -s read-only --json -c 'mcp_servers.mobile-agent.command="<build>/mobile-agent-mcp"' -c 'mcp_servers.mobile-agent.env={MOBILE_AGENT_SOCKET_DIR="<dir>",MOBILE_AGENT_DRIVERS="simulator"}' -c 'mcp_servers.mobile-agent.default_tools_approval_mode="approve"' "<task>"`, as S13 ran it, plus the server's approval mode: `codex exec` runs with `approval_policy` `never`, since nobody is there to answer a prompt, and under the default tool approval mode a call to a tool not annotated read-only asks for one; `default_tools_approval_mode = "approve"` on the server skips the approval for its tools (Codex's `codex-rs/core/src/mcp_tool_call.rs`, `requires_mcp_tool_approval_for_mode`; `config/src/mcp_types.rs`), and `"writes"`, the mode the research note recorded, would still prompt for `open`, `fill`, `click` and `scroll`. The `--json` stream carries each MCP tool call with its arguments and result, each turn's usage, and the agent's messages.
- **Between the runs** the fixture app was terminated through `simctl`, so that Codex started as Claude Code had, with the app not running and its state at launch (Signed out on the Login tab); the fixture keeps no state across launches.
- **Verification** after each run, in a CLI session of its own on the same socket directory: `snapshot -i` for the List tab's state as the run left it, then `click '#tab-login'`, `wait --settle` and `get text '#login-status'`, then back to the List tab and `close --keep`, which released the verification session's claim without stopping the app.
- **Standard input.** Both clients read it: `codex exec` with a prompt argument appends a piped standard input to the prompt and waits for its end, so the first Codex attempt waited on the shell's open pipe for 4 min 30 s, started no server and touched nothing, and was stopped; the run below gave it `/dev/null`. `claude -p` waits 3 s for it and goes on with a warning, which the shell's clock includes.
- **Counts.** A turn is what the client reports: Claude Code's `num_turns` of the result line, Codex's `turn.completed` events. Tool calls are the calls the stream shows, counted per tool; Claude Code's own `ToolSearch`, which loads the deferred schemas, is counted apart. Tokens are the clients' usage fields: Claude Code's `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and `output_tokens` summed over the API requests, Codex's per-turn `input_tokens`, `cached_input_tokens` and `output_tokens`. The wall time is the client's own (`duration_ms`) and the shell's, from the command's start to its exit.
- **Load.** Each measured run started once the 1-minute load average had been under 6, polled every 60 s; the Simulator's boot took it to 66 for about three minutes before the first run, the endpoint security software and the Simulator's own daemons busiest, and it was 3.97 when Claude Code started, 1.77 when Codex did and 4.24 at the read-only check. Nothing else of this work ran on the host during the runs; the clients' own processes and the Simulator did.

## Findings

### 1. A status text is outside the interactive listing and a change wait's delta taken in it

`snapshot -i` lists the elements with refs, and a change wait answers with the delta in the options of the session's last snapshot (design D8), so after Claude Code's model took interactive snapshots its `wait {change: true}` answered the listing with the keyboard gone and the tabs back, and nothing of `login-status`. The model said so ("the status text was not in the interactive delta") and read it in one turn with `get {what: "text", selector: "text=Welcome"}` and a full snapshot: two calls more than the task's wording suggests. Codex took every snapshot with `interactive: false`, so its wait's delta carried `- text "Welcome, agent" [id=login-status]`. The card now says that a plain text has no ref and is in neither, and where it is read; the CLI's guide already does (`README.md`, Agent guide, Snapshots).

### 2. `fill` answers `✓ Done` alone

The CLI's human line for `fill` is `✓ Done`, and the reply's `verified`, `method`, `readFrom` and `retried`, what the daemon read back, stay in the JSON the server does not send. Both models took a snapshot after the two fills to see the fields hold the text (Claude Code's interactive, 232 characters; Codex's full, 719). The smallest fix is a `fill` arm in `crates/cli/src/output.rs`, `✓ Done (read back "agent", typed)`, for both surfaces: task 6.4.

### 3. `scroll --until` answers `✓ Done` alone

The same for `scroll`: the reply's `visible`, `strokes` and `element` stay in the JSON. Claude Code's model took a snapshot after the scroll "to confirm its position" before tapping (1,065 characters); Codex tapped `text==Row 57` at once and was right. The smallest fix is a `scroll` arm, `✓ Done (3 strokes; "Row 57" is 100% in view)`: task 6.5.

### 4. A screenshot right after a click shows the transition the tap set off

`click` answers at the tap's first tree delta, 112 to 126 ms after the dispatch on this Simulator, and a push or pop animation runs about 350 ms, so a screenshot called at once is the driver's capture of the animation (Screenshots after a click, probed through the CLI). Codex's first screenshot after Back showed the detail sliding out; it settled and took another. The card now says to settle before a screenshot that follows a click.

### 5. What the clients add

Claude Code loaded the schemas on demand: its tool search, a turn of its own before the first call, chose 12 of the 17 tools and grew the context by 6,692 tokens at the second request, about 560 a tool; it then kept the model's thinking in the context, which the usage counts. The run's 15 requests read 532,711 tokens from the cache, 35,500 a request, at $1.03. Codex ran the 16 calls in one turn of 17 requests, 16,200 input tokens a request, with no reasoning tokens, in 37 s against Claude Code's 89 s. `_meta` `anthropic/alwaysLoad` on the tools would spare the tool search turn at the price of every schema upfront (`docs/research/agent-surfaces.md`), which is a choice for the maintainer rather than a gap.

### 6. The release at exit held under both clients

After each run the daemon's `status` listed the server's session, `mcp-<pid>`, with no target, and the app was running where the model left it: the CLI's verification session claimed the target without `force`, and no `target_claimed` came. Claude Code ends the server by closing its standard input and Codex by ending the process at `exec`'s end; design D9's ways out cover both.

### 7. The lazy list's hint counts the tree

The SwiftUI List holds about 16 rows in its accessibility tree at a time, so the List tab's first listing said `(1 more actionable item below, 1 of them under the footer, scroll down to reveal)` of a list of 200 rows. Neither model was misled: `scroll` with `until` strokes until the element appears, with `amount: 600` (Claude Code) and the default amount (Codex) alike. The hint is the mirror's count of what the tree holds, a matter for the mirror's documentation rather than the server.

### 8. Both clients read standard input

`codex exec` with a prompt argument appends a piped standard input to the prompt and waits for its end: the first attempt printed "Reading additional input from stdin..." and waited 4 min 30 s on the shell's open pipe before it was stopped, having started no server. `claude -p` waits 3 s and goes on with a warning. A script gives each `< /dev/null` (Rerun).

### 9. The host had moved to macOS 27.0.1 and Xcode 27.1

## What was not measured

- **A listing's tokens on either model.** Claude Code's per-request usage mixes a result with the model's text and thinking, and Codex reports a turn's totals; S13's count on the 500-cell listing stands.
- **Claude Desktop and Cursor.** Not run; their configuration is in `README.md`, Agent surfaces.
- **`--structured`, `--call-timeout` and a client's cancellation.** No call waited past the bound and no client cancelled one; the crate's tests cover the mechanisms (`crates/mcp/README.md`, Waits).
- **Codex's model and timing.** The stream names neither the model nor a time per call.
- **Variance.** One run per client, so a second run's turns and tokens may differ; the steps' outcomes were verified, the counts are one sample each.
- **The Android emulator and the iPhone through the server**, and the server's own round trip on a real target: S13 measured it on the fake.

```sh
export DIR=$(mktemp -d /tmp/mcp-acceptance.XXXX)                      # a private socket directory; keep its path short
printf '%s\n' "{\"mcpServers\":{\"mobile-agent\":{\"command\":\"$PWD/target/release/mobile-agent-mcp\",\"env\":{\"MOBILE_AGENT_SOCKET_DIR\":\"$DIR\",\"MOBILE_AGENT_DRIVERS\":\"simulator\"}}}}" > "$DIR/mcp.json"
TASK='Use only the mobile-agent MCP server'"'"'s tools. 1. Open the app ... (the task above, verbatim)'
claude -p "$TASK" --mcp-config "$DIR/mcp.json" --strict-mcp-config --allowedTools "mcp__mobile-agent__*" \
  --max-turns 40 --output-format stream-json --verbose < /dev/null > claude-run.jsonl
xcrun simctl terminate booted dev.mobileagent.fixture.swiftui                 # the app as the first run met it
codex exec --skip-git-repo-check --ephemeral --ignore-user-config -s read-only --json \
  -c "mcp_servers.mobile-agent.command=\"$PWD/target/release/mobile-agent-mcp\"" \
  -c "mcp_servers.mobile-agent.env={MOBILE_AGENT_SOCKET_DIR=\"$DIR\",MOBILE_AGENT_DRIVERS=\"simulator\"}" \

Each run's counts come from its stream: Claude Code's last line (`num_turns`, `usage`, `duration_ms`, `total_cost_usd`) and its `tool_use` and `tool_result` blocks; Codex's `item.completed` events of type `mcp_tool_call` and its `turn.completed` usage.
