# Microbenchmark harnesses and noise control: state of the art

Research note for task 1.1 of `microbenchmarks`. It feeds spike S8 (task 1.2), which chooses the harness library by measuring this host's noise (design D13), and the runner of D15 and D16. Every claim was read from the pinned sources at the end on 2026-10-07, and the versions are the latest on crates.io that day. Library facts come from current documentation: Context7 for criterion, divan, Gungraun and Bencher. Context7 indexes neither tango nor glassbench, CodSpeed's Rust layers or github-action-benchmark, so for those the note reads each repository's README and source at the pinned commit, docs.rs, and CodSpeed's documentation site, and says so in each section. Dependency counts here are direct dependencies read from each manifest; S8 counts the crates each harness adds to a lock file.

Out of scope: profilers (attributing a regression is a profiler's job, design D14), the device benchmarks of `crates/bench` (archived design D10), and the CI change's choice between instruction counts and a dedicated runner, for which this note only records the options.

## Findings in brief

- Four wall-clock harnesses are candidates on stable Rust: criterion, divan, tango and glassbench; S8 checks that each builds and runs here. They differ less in how they time than in what they do with the numbers. Criterion bootstraps confidence intervals and compares a run with a saved baseline. Divan reports fastest, slowest, median and mean, and compares nothing. Tango runs two builds sample by sample in lock-step and reports whether their difference is significant. Glassbench times one loop and stores its mean in SQLite.
- None writes a stable machine-readable file per benchmark by default. Criterion's JSON files are "private implementation details", its stable `raw.csv` needs the `csv_output` feature, which 0.8.2 marks deprecated, and `--output-format bencher` prints one libtest line per benchmark. Tango dumps raw paired samples as CSV with `-d`, glassbench writes an SQLite file, and divan prints only a text table.
- Instruction counting is the standard answer to noisy CI: Gungraun (formerly iai-callgrind) and CodSpeed's simulation instrument count instructions under Valgrind. Valgrind has no arm64 macOS port, so neither runs on this host; they remain the CI change's option for the Linux leg.
- The continuous-benchmarking services (Bencher, CodSpeed, github-action-benchmark) store history and alert past a threshold. Bencher puts shared GitHub runners at over 30% variance between runs and its bare-metal runners at under 2%. This change keeps the history in the repository, as a committed baseline, and measures on this host only.
- agent-browser and agent-device time themselves end to end, not per mechanism, and gate nothing on the numbers. agent-device parked its nightly performance job because iOS medians swung up to +122% from night to night at five samples and nothing compared them. Maestro and Appium have no benchmarks of their own. None of the tools compared has host microbenchmarks.
- Prediction for S8: on a quiet host criterion and divan both pass the 2% gate and tell the 5% variant apart in 10 of 10 runs. Tango tells it apart, with significance, in the fewest seconds, but it compares builds rather than stored numbers, which D16's committed baseline cannot use. Glassbench's single mean, with no outlier handling, is the noisiest under load. The choice then falls to output format and dependency count.

### criterion

**Does.** Each benchmark warms up for 3 s, then takes 100 samples aiming at 5 s of measurement. Sampling is linear (sample *i* runs *i·d* iterations) unless that would take more than twice the target time, in which case every sample runs the same count. The analysis bootstraps 100,000 resamples into 95% confidence intervals for the mean, median, median absolute deviation, standard deviation and slope, and classifies outliers with Tukey's fences. Each run is compared with the previous one, kept under `target/criterion/<id>/base` (or `$CRITERION_HOME`), or with a named `--baseline`, using a t-test at significance 0.05 and a 1% noise threshold. A regression prints "Performance has regressed." and leaves the exit status at 0; the only `process::exit(1)` calls are for bad arguments. Settings can be given per group (`sample_size`, `measurement_time`, `warm_up_time`, `significance_level`, `noise_threshold`, `confidence_level`, `nresamples`, `sampling_mode`) or on the command line (`--save-baseline`, `--baseline`, `--noplot`, `--quick`, `--profile-time`, `--output-format bencher`, a regular-expression filter). `iter` drops the routine's output inside the timed loop; `iter_with_large_drop` moves the drop out.

Each benchmark leaves `new/estimates.json`, `sample.json`, `benchmark.json`, `tukey.json` and `change/estimates.json`, which the book calls private implementation details whose structure may change. The book promises a stable format only for `raw.csv`, and 0.8.2 writes that file only with the `csv_output` feature, which its manifest calls deprecated in favour of cargo-criterion's `--message-format=json`. cargo-criterion's last release is 1.1.0, of 2021-07-28. Since 0.6, `criterion::black_box` is deprecated in favour of `std::hint::black_box`, and 0.8.0 added alloca-based randomisation of the stack layout. `cargo_bench_support`, a default feature, is no longer referenced in the code. The project moved from bheisler/criterion.rs to criterion-rs/criterion.rs; Context7's index still reads the old repository's book, so the facts above were checked against the 0.8.2 tag.

**For this project.** The incumbent, with the richest statistics. A machine-readable result per benchmark comes from an unstable JSON file, a deprecated CSV feature, or the one-line libtest format, which carries no median. With default features off, `rayon` and `plotters` go away, and the bootstrap then runs on one thread.

### divan

**Does.** `#[divan::bench]` registers a function and `divan::main()` runs every registered one. By default each takes 100 samples. The number of iterations per sample is tuned until a sample lasts more than 100 times the timer precision, which divan measures and prints at startup. The timer is the OS clock, or the CPU counter with `--timer tsc`. The text tree reports fastest, slowest, median and mean, with the sample and iteration counts. Outputs that need dropping are dropped after the sample, not inside it. Settings come from attribute options (`sample_count`, `sample_size`, `min_time`, `max_time`, `skip_ext_time`), command-line flags (`--sample-count`, `--sample-size`, `--min-time`, `--max-time`, `--timer`, `--filter`), or `DIVAN_*` environment variables. `AllocProfiler`, installed as the global allocator, adds alloc, dealloc, grow and shrink counts and bytes per iteration to the table.

Divan keeps no baselines, compares nothing, and has no machine-readable output: `--format terse` is accepted only with `--list`, for cargo-nextest, and the source carries `TODO: --format <pretty|terse>`. The last release is 0.1.21, of 2025-04-10.

**For this project.** The lightest of the four, with allocation counting built in, which D14 would otherwise write as a counting allocator. But `micro` would have to parse a text table with units in it, and there has been no release in 18 months.

### tango

Context7 does not index tango; this section reads its README, its source at v0.8.0 and its docs.rs page.

**Does.** Tango benchmarks in pairs. The binary built from the change, the candidate, runs `compare <baseline executable>`. Since 0.8.0 the runner spawns both executables as worker processes (`__worker`). The two run each sample in lock-step, synchronized through a 32-byte shared-memory page, and return their samples over JSON-RPC on stdio, so baseline and candidate see the same host conditions sample by sample. The number of iterations per sample is estimated to fill a 10 ms slice, and without `-t` or `-s` each benchmark samples for 100 ms. The statistic is the per-sample difference, candidate minus baseline: it is significant when its z-score (mean over standard error) reaches 2.6, the 99% level, and the change exceeds the noise threshold. The code sets that threshold at 1%; the README still says 0.5%. `-o` filters outliers by interquartile range.

Each benchmark prints `name [ base mean ... candidate mean ] +x.xx%*`, with an asterisk for significance. `-d <dir>` writes the raw paired samples as CSV (baseline, candidate, iterations, no header). The exit status is 1 on a significant regression, and `--fail-fast` stops at the first. `solo` runs one build alone and prints its mean. A baseline is an executable: `cargo export`, a separate tool, keeps a build of the base commit. The README still shows 0.7's `tango_main!`, which 0.8 marks "Not needed anymore". The README states its design target as "detect a 1% change in performance within just 1 second in at least 9 out of 10 test runs". Optional features: `hw-timer` (rdtscp, x86_64 only), `stack-randomize` (alloca) and `async-tokio`.

**For this project.** Tango answers "is this build slower than that one" better than any of the others, but not "what does this cost" against a number on record. D16's committed baseline would need the base commit rebuilt for every comparison.

### glassbench

Context7 does not index glassbench; this section reads its README and its source at `d3bb2e6`, the untagged commit that published 0.5.0.

**Does.** A `glassbench!` macro names the bench functions, and each defines tasks with `bench.task(name, |task| task.iter(..))`. A task runs two warm-up iterations and five estimating ones, then one timed loop of as many iterations as fill about 2 s, at least 50. It records the total duration and the iteration count, which gives a mean, with no samples, spread or test. Each run is compared with the previous saved one and appended to `glassbench_v1.db`, an SQLite file in the working directory. Its tables are `bench` (time, name, title, tag, commit id) and `task` (iterations, total and mean duration in ns). The other options are `--no-save`, `--tag`, `--history` and `--graph`, which opens an HTML viewer in the browser. The README warns that the measurement "is extremely sensible to the load of your system".

**For this project.** The history lives in a binary database rather than a reviewable file, each run yields one mean, and the bundled SQLite and libgit2 compile C code.

### Instruction counts: Gungraun and CodSpeed

**Gungraun** is iai-callgrind renamed. iai-callgrind's last release is 0.16.1, of 2025-07-30; its repository now redirects to gungraun/gungraun, and Gungraun 0.20.0 came out on 2026-09-26. It runs each benchmark once under Valgrind's Callgrind (or Cachegrind, DHAT, or Linux perf) and reports instructions, cache hits and estimated cycles. It takes `--save-baseline` and `--baseline`; limits such as `--callgrind-limits='ir=5%'` exit with status 3; `--output-format=json` writes one JSON object per benchmark. A `gungraun-runner` binary of the same version must be installed. Its README: "Gungraun cannot be run on Windows or targets that support neither the Valgrind-based tools nor Linux perf", and "If you need wall-clock times, Gungraun cannot help you much". Valgrind 3.27.1 supports Darwin only on x86 and AMD64, up to macOS 10.13 and 11.0, so it cannot run on this arm64 Mac.

**CodSpeed.** Context7 indexes only its pytest plugin; this paragraph reads the codspeed-rust README and codspeed.io's documentation. `codspeed-criterion-compat` and `codspeed-divan-compat` stand in for criterion and divan under their names (`cargo add --dev codspeed-criterion-compat --rename criterion`), and under plain `cargo bench` the suite "will still run it as usual". `cargo codspeed build -m simulation|walltime|memory` and `cargo codspeed run` build and run the benchmarks for CodSpeed's instruments:

- simulation runs each benchmark once on CodSpeed's Valgrind fork, built from source, and estimates cycles from instructions and L1 and last-level cache misses, leaving system calls out;
- walltime measures on CodSpeed's bare-metal macro runners, with 600 free minutes a month on the arm64 Graviton runner, and also runs on macOS;
- memory tracks heap allocations.

Results go to the CodSpeed service, "free and unlimited on public repositories". The criterion layer does not support `iter_custom` or `with_filter`. CodSpeed recommends divan, and against compiler and linker variance, one benchmark per binary.

### Continuous benchmarking: Bencher and github-action-benchmark

**Bencher** (CLI 0.6.13, 2026-09-28). `bencher run --adapter <harness> "<command>"` parses a harness's output and stores the results per project, branch and testbed, on Bencher Cloud or a self-hosted server. Its Rust adapters read libtest bench lines, criterion's printed `time:` line (the typical estimate, slope or mean, not the median), Iai and Gungraun; anything else goes in through its JSON format. There is no adapter for divan or tango. A threshold applies a test over recent history (`static`, `percentage`, `z_score`, `t_test`, `log_normal`, `iqr`, `delta_iqr`), and `--error-on-alert` fails the run. Its documentation: "standard CI runners like GitHub Actions can experience over 30% variance between runs, Bencher's bare metal runners maintain less than 2% variance". It names three mitigations: bare-metal runners, relative continuous benchmarking (base and head measured on the same runner in one job), and harnesses that count instructions.

**github-action-benchmark** (v1.22.2, 2026-09-15). Context7 does not index it; this reads its README and `src/extract.ts`. The action parses a tool's output: `tool: 'cargo'` reads libtest lines, `test <name> ... bench: <n> ns/iter (+/- <m>)`, which criterion prints with `--output-format bencher`, and `customSmallerIsBetter` reads a JSON array of `{name, unit, value}`. It keeps the history on a `gh-pages` branch or in an external JSON file, draws charts, and alerts when a result is worse than the previous one by the `alert-threshold` ratio (default 200%), failing the job with `fail-on-alert`. It computes no statistics beyond that ratio.

## Keeping noise down

- **A quiet host, or no measurement.** No harness checks the host. Criterion's FAQ blames unexplained changes on the environment ("Other processes might be using the CPU or memory. Battery-powered devices often have power-saving modes"), and of cloud CI it says "You probably shouldn't (or, if you do, don't rely on the results)". Glassbench's README asks to "close everything else". This project's practice, S5's `bench.sh` and the 10.x reports, waits for the 1-minute load to fall under a bound and records it; S5 measured anyway after 20 minutes, which D15 ends.
- **Samples, warm-up and duration.** Criterion warms up for 3 s and takes 100 samples over about 5 s. Divan tunes the sample size to 100 times the timer precision and takes 100 samples, with no fixed time. Tango takes 10 ms samples for 100 ms. Glassbench runs 7 untimed iterations, then one 2 s loop. Longer sampling narrows a run's interval but does nothing about drift between runs, and in criterion's FAQ's words, "to increase the sensitivity to small changes, you must also increase the chance of false detections".
- **Keep the work, decide where the drop goes.** Every harness wraps the result in `std::hint::black_box` or its own equivalent (glassbench's `pretend_used`). Criterion's `iter`, tango and glassbench drop each output inside the timed loop; divan drops it after the sample. Harnesses compared on one workload must time the same work, drop included.
- **Pair what is compared.** Tango runs base and candidate in lock-step, sample by sample. Bencher's relative continuous benchmarking measures both commits in one job. Criterion's FAQ procedure runs main and then the branch on the same machine. Pairing cancels drift common to both sides, not the noise within a sample.
- **Count instructions instead of time.** Gungraun and CodSpeed's simulation give counts that do not move with load, but they are not wall time and they need Valgrind, which means Linux.
- **Dedicated hardware.** Bencher's and CodSpeed's bare-metal runners, with Bencher's figures of over 30% variance on shared runners against under 2% on its own.
- **Memory layout.** Criterion 0.8 randomises the stack layout with alloca, tango offers the same as `stack-randomize`, and CodSpeed suggests one benchmark per binary so that unrelated code does not move the measured code.
- **This host.** Apple silicon offers no thread affinity. The OS places threads on performance or efficiency cores from "Information your app provides", "Observation of the app's workload" and "Observation of the system as whole", with QoS classes as the main hint, and `thread_policy_set` with an affinity policy returns `KERN_NOT_SUPPORTED`. A benchmark cannot hold itself on a performance core, so load from other processes can move it. The guard is the only defence; S8's loaded series measures what load does.

## What agent-browser and the baseline tools measure of themselves

- **agent-browser** (0.38.2 at `98e8c79`). `benchmarks/` compares its Node daemon with its Rust daemon inside a Vercel Sandbox microVM. It times per-scenario command latency (navigate, snapshot, screenshot, evaluate, click, fill, an agent loop and a seven-command workflow) over 10 iterations after one warm-up, reported as mean, standard deviation, min, max and p50, plus cold start, binary and distribution size, daemon RSS and CPU time. It runs on demand (`pnpm bench`, `--json` for `results.json`), and the CI workflows (`ci.yml`, `release.yml`) run no benchmark. The Rust CLI has no bench targets. The README notes that "Command latency is dominated by Chrome (CDP round-trips), not the daemon."
- **agent-device** (`e774595`). `pnpm perf` (`scripts/perf/`) times each command through the CLI with `--json` and reports wall min, median, p95 and max (nearest rank) and the daemon's round trip, as JSON and markdown. Its nightly workflow is parked to manual dispatch: "it only writes a report and compares nothing, so it structurally cannot catch a regression, and iOS wall-clock medians swing up to +122% night-to-night at n=5". Its `perf` command profiles the app under test (frames, memory, CPU and traces, through xctrace, simpleperf, Perfetto, hprof and memgraph), not agent-device itself.
- **Maestro** (`60f9ba4`). No benchmark code and no benchmark job; its workflows build, test, run end-to-end tests and publish.
- **Appium** (`e560924`) and its XCUITest driver (`7221d4d`). No benchmarks of themselves. The XCUITest driver's `startPerfRecord` records "the device under test" with xctrace.

This project's device harness (archived design D10) already goes further than any of them, with gates and baselines on device flows. What none of them has is a number for the host-side work, which is the gap this change fills.

## S8 plan

- **Candidates.** criterion 0.8.2 with default features off (no `rayon`, no `plotters`), run with `--noplot`; divan 0.1.21; tango-bench 0.8.0; glassbench 0.5.0; each dropped with its reason if it does not build or run here. Gungraun and CodSpeed's simulation instrument cannot run on this host. CodSpeed's layers time as criterion and divan do outside CodSpeed's environment, so they are not separate candidates.
- **Benchmarks.** Every harness times one function body. `decode` is `protocol::message::Message::decode` of a `Message::Response` carrying a generated 500-node snapshot in S5's shape, with the decoded message dropped inside the timed region and compared with the original outside it. `decode_slow` is the same plus a black-boxed loop over the first N input bytes, with N calibrated on a quiet host to add about 5%. For tango, a baseline build whose `decode` is the plain one is compared with a candidate build whose `decode` is the slow one.
- **Settings.** Each harness's defaults, recorded.
- **Series.** Ten runs per harness on a quiet host (1-minute load under 4, and none of D15's process list over 5% of a core, checked before every run and logged), with the harnesses taking turns run by run. Then ten more per harness under four `yes` processes, which keep four cores busy.
- **Metrics.** Per harness and series: the coefficient of variation of the reported `decode` value across the ten runs; in how many runs `decode_slow` came out slower than `decode`, and by how much; wall time per run; the crates the harness alone adds to the spike's lock file; and whether the output is machine-readable per benchmark without parsing prose.
- **Gate (D13).** Quiet CV at or under 2%, and the 5% variant told apart in at least 9 of 10 runs. Among the harnesses that pass, machine-readable output first, then the fewest dependencies.

## What we take

**D13, the harness.** Choose by measuring this host, not by feature list, with the gate and the order of preference above. Whatever wins, `micro` runs it with explicit sample settings and records them in the baseline's provenance.

**D15, the guard.** Our own quiet-host practice, turned into a refusal: no harness checks the host, and none of the tools surveyed waits for a quiet one. The process list comes from the builders and devices the reports waited for, and the load averages at the start and end go into every report.

**D16, the baseline and the threshold.** A committed baseline file instead of a history service (Bencher, CodSpeed, a `gh-pages` branch): the history is git's, and a regression a change accepts shows in the reviewed diff. The threshold is derived from this host's measured noise, as criterion's noise threshold and tango's are fixed constants. Allocation counts compare exactly, since, like instruction counts, they do not move with load.

**Output.** `micro` writes its own JSON, so that Bencher's JSON adapter or github-action-benchmark's `customSmallerIsBetter` can take it later, and the CI change can add Gungraun or CodSpeed on Linux without touching the suite.

**Where this design differs.** No timing in CI, no service, no history outside the repository, and a refusal, not a warning, on a busy host.

## Risks

- **Criterion's machine-readable output is unstable or deprecated.** The JSON files may change without notice, `raw.csv` sits behind a deprecated feature, and the libtest line carries no median. If criterion wins, `micro` parses `estimates.json` with a recorded sample in its tests, so a format change fails loudly.
- **divan has had no release in 18 months**, and its output is a text table with units.
- **tango 0.8 is new.** Its runner was rewritten on 2026-08-21, and its README still documents 0.7. Its paired model needs the base commit built for every comparison.
- **glassbench measures one mean per run**, with heavy native dependencies.
- **Apple silicon scheduling.** With no affinity, a busy host can move a benchmark to an efficiency core. Only the guard prevents that, and S8's loaded series shows what it costs.
- **Instruction counts are not available here.** The cheapest stable signal in CI needs Linux and Valgrind, so local runs depend on a quiet host and allocation counts.
