# Releasing: state of the art

Research note for task 1.1 of `alpha-release`. It feeds the verdict between cargo-dist and a hand-written workflow and the dry run (design D1), the release workflow and its tag (D2), the alpha's checks (D4), the crates' names, their first publish and trusted publishing (D5, D6), and, in its npm section, written for task 3.4, the packages on npm (D7). Every claim was read from the sources at the end on 2026-11-05, and versions are the latest released that day. Context7 answered for cargo-dist (`/axodotdev/cargo-dist`), GitHub's documentation (`/github/docs`), Cargo (`/rust-lang/cargo`), crates.io (`/rust-lang/crates.io`) and npm (`/websites/npmjs`, `/npm/cli`); each page quoted was then read at its source in the vendor's repository, at the date of its last change given in the sources. Astral's workflows and example rulesets, the actions' READMEs and the runner images' READMEs are read in their repositories. It builds on `docs/research/open-sourcing.md`, whose "What a first release will need" named the mechanisms; what that note found is not repeated, only what a release workflow has to decide.

Out of scope: Homebrew and other package managers (after a second release), Windows, and signing and notarizing the macOS binaries, which needs an Apple Developer ID; the linker signs them ad hoc, which is what an arm64 executable needs to run.

## Findings in brief

- **cargo-dist builds what it knows and owns the workflow it generates.** dist 0.34.0 (2026-11-02) generates a `release.yml` that runs on a pushed tag or, with `dispatch-releases = true`, on a dispatch whose "dry-run" tag builds without publishing; it builds each target in a matrix from `dist plan`, packs archives with SHA-256 checksums and installers, attests them with `actions/attest` when the experimental `github-attestations` is on, and creates the release, and with it the tag, by `gh release create --target <sha>` in its host job. No setting puts that job in an environment of ours, its top-level permissions are `contents: write`, it installs itself by piping its installer script from its release into `sh`, and this workspace's builds need steps it does not know (the Android agent's jar, Xcode 27, libjpeg-turbo, the Simulator reader). Astral's uv and ruff began from its workflow and maintain theirs by hand.
- **No ruleset can let one deployment create a tag.** "Restrict creations: only users with bypass permissions can create branches or tags whose name matches the pattern"; the actors eligible on github.com are roles (admin, maintain, write), teams, GitHub Apps and Dependabot, deploy keys only on GitHub Enterprise Server. A workflow, an environment or a deployment is none of them, and the GitHub Actions app would let every workflow with `contents: write` through. Astral's uv instead adds the rule `required_deployments` to a tag ruleset: a tag can be pushed only on a commit already deployed with success to the `release` environment, with no bypass. Tried in task 2.1: a deployment still in progress does not count, the tag being refused with "Missing successful active release deployment", while a successful one from an earlier job of the same run does.
- **Immutable releases** lock a published release's tag and assets, never let its tag name be reused, and attach a release attestation that `gh release verify` and `gh release verify-asset` check; GitHub recommends creating the release as a draft, attaching every asset and then publishing. The setting has a REST endpoint (`PUT /repos/{owner}/{repo}/immutable-releases`).
- **Artifact attestations**: `actions/attest-build-provenance` v4.2.2 (2026-08-06) is "simply a wrapper on top of `actions/attest`", which "new implementations should use"; `actions/attest` v4.2.2 (2026-08-04) signs SLSA build provenance for any number of files with `id-token: write` and `attestations: write`; `gh attestation verify <file> -R <owner>/<repo>` checks one, and `--signer-workflow`, `--source-digest` and `--deny-self-hosted-runners` narrow who signed it.
- **crates.io trusted publishing** starts after a first publish with a token: a trusted publisher per crate names the repository's owner and name, the workflow's file name and optionally an environment; `rust-lang/crates-io-auth-action` v1.0.6 (2026-10-21) exchanges the job's OIDC token for one that publishes new versions of that crate for 30 minutes and revokes it when the job ends.
- **Cargo publishes a workspace in dependency order.** Multi-package publishing is stable since Cargo 1.90 (2025-09-18), `cargo publish --workspace` or `-p` several times, and is "still non-atomic"; the pinned 1.99.1 has `--workspace`, `--exclude` and `--dry-run`. The order here is protocol, simulator-reader, agent-ios, mirror, android, wire, (bench), cli, simulator, ios, daemon, mcp.
- **Three targets.** aarch64-apple-darwin on GitHub's `xcode-27` image, the only image with Xcode 27, which the Simulator driver needs; no Intel Mac, whose Simulators run x86_64 runtimes the reader is not built for and whose images carry Xcode 26 alone; x86_64 and aarch64 Linux, for hosts that drive Android alone, where the daemon builds today with the Simulator and iPhone drivers as stubs, no feature needed.
- **npm, scoped, esbuild's way, with a first publish by hand.** `mobile-agent` and `mobile-agent-mcp` are other packages on npm, and the scope `@mobileagent` holds nothing. esbuild 0.28.2 ships one package per platform with `os` and `cpu` as optional dependencies of a package whose command is a JavaScript shim, and keeps a `postinstall` that this design drops. npm's trusted publishing (npm 11.5.1 or newer) is configured per package on a package that exists already, so the first version is the maintainer's by hand; a new trusted publisher must publish within 48 hours or it expires (2026-10-02), and its allowed actions default to staged publishing since 2026-09-03. npm 11 refuses a prerelease without a tag, and `npx` cannot pick one of several commands without `--package`.
- **Verdict: a hand-written workflow**, on the three targets, the tag created by the publishing job under Astral's `required_deployments` rule, after a gate job's deployment (task 2.1), with the maintainer's own tag as the fallback; the dry run on 2026-11-05 took 5 min 47 s and produced tarballs of 8.8 MB and 5.2 and 5.0 MB, each verified on its runner and here.

## cargo-dist and a hand-written workflow

From dist's book at v0.34.0 (the configuration reference, "Customizing CI", the workspace guide), its own generated `release.yml` at v0.34.0, its installer template and two open issues, read on GitHub, through Context7 (`/axodotdev/cargo-dist`) for the book.

| Question | cargo-dist 0.34.0 | Hand-written |
|---|---|---|
| Building per target | `build-local-artifacts`, a matrix from `dist plan` over `targets`, runners per target (`github-custom-runners`), `dist build` per leg; `merge-tasks` and `fail-fast` off by default | one job per target in a matrix, the workspace's own build steps |
| Steps a build needs | `github-build-setup` (experimental): a YAML file of steps run before `dist build`; or `local-artifacts-jobs`, reusable workflows | the steps themselves, as CI runs them |
| Artifacts and checksums | archives (`.tar.xz`, `.zip`), `checksum` (SHA-256 by default) per archive and a `sha256.sum`, installers (shell, PowerShell, npm, Homebrew), `dist-manifest.json` | a tarball per target with the binaries, the notices and their `SHA256SUMS` |
| Tag and release | "1 Git Tag = 1 dist Announcement = 1 Github Release"; on a pushed tag, or with `dispatch-releases = true` on a dispatch, "relying on creating a GitHub release implicitly tagging": the host job runs `gh release create <tag> --target <sha> <files>`; `github-release = "announce"` moves it later, "likely to introduce undesirable publishing race conditions" | the publishing job, as the workflow decides |
| Attestations | `github-attestations = true` (since 0.16.0, "experimental"), `actions/attest` in the build legs with `id-token: write` and `attestations: write`; `github-attestations-phase` (0.30.0) moves it to host or announce | `actions/attest` where the files are made |
| Immutable releases | the release is created with its files in one call; with `create-release = false` it uploads into a draft someone else made and "always undrafts" it (issue #2520, open since 2026-09-28) | draft, upload, publish, as GitHub recommends |
| Environment with reviewers | none for the host or announce job; only dist's Azure signing jobs run in a `release` environment; custom publish jobs are reusable workflows with `id-token: write` and `packages: write` by default | the publishing job in `release` |
| Hand edits | `allow-dirty = ["ci"]`, after which dist "will stop trying to update the file and stop checking if it's out of date" | the file is the source |
| Its own supply chain | top-level `permissions: contents: write`; the plan job runs `curl ... cargo-dist-installer.sh \| sh` from its release (the script checks the archive's SHA-256 it embeds; nothing checks the script, though dist's 0.34.0 release is immutable); in containers `curl https://sh.rustup.rs \| sh`; actions pinned to commits, overridable with `github-action-commits` (0.29.0); `cache-builds` off by default | the actions and tools this repository already pins |

Astral's uv and ruff start their `release.yml` with "Originally generated by `cargo-dist`. This workflow is now maintained manually.": `permissions: {}` at the top, a dispatch with a `dry-run` input, a `release-gate` environment that another team member approves, the `release` environment on the jobs that publish to GitHub, PyPI and crates.io, which "a GitHub App with a deployment protection rule webhook" approves only once `release-gate` has succeeded, `actions/attest-build-provenance` before the release is created, and the release created by `gh release create "$TAG" --target "$RELEASE_COMMIT"` with a short-lived token from their own token-exchange service, holding `contents: write` and `workflows: write`. uv still calls `dist` to plan and build; its workflow sets `ACTIONS_CACHE_MODE: none`, "Release actions must not consume shared GitHub Actions caches".

**For this project.** dist would build the three binaries, but every step that makes them this workspace's lives outside it: the jar built once and embedded in each daemon, Xcode 27 checked, libjpeg-turbo installed and checked to be linked statically, the reader checked to be embedded. Its release job cannot sit in our `release` environment without a hand edit, after which dist stops maintaining the file, which is where uv and ruff ended. Its archives, manifest and installers are more than an alpha that a user unpacks needs. A hand-written workflow keeps the hardening this repository has (no write at the top, pinned tools with their SHA-256, no cache) and is about 280 lines.

## Tags under a ruleset

From GitHub's documentation, through Context7 (`/github/docs`) and at its source: "Available rules for rulesets" (2026-11-03), the bypass step (2026-10-05), "About rulesets" (2026-08-11), "Creating rulesets for a repository" (2026-11-04), the REST schema of `required_deployments`, and "Control deployments" (2026-07-16); Astral's example rulesets (gist, 2026-05-22).

- **Restrict creations**: "If selected, only users with bypass permissions can create branches or tags whose name matches the pattern you specify."
- **Who can bypass**: "You can grant certain roles, teams, or apps bypass permissions [...] The following are eligible for bypass access: Repository admins, organization owners, and enterprise owners; The maintain or write role, or custom repository roles based on the write role; Teams, excluding secret teams; [...] GitHub Apps; Dependabot." Deploy keys are listed for GitHub Enterprise Server only, though the REST enum names `DeployKey` beside `Integration`, `OrganizationAdmin`, `RepositoryRole`, `Team` and `User`.
- **No deployment as an actor.** Neither a workflow, an environment nor a deployment is in that list. A job's `GITHUB_TOKEN` pushes as the GitHub Actions app; even where that app can be listed as a GitHub App, the bypass would cover every workflow of the repository given `contents: write`, not the release deployment alone, so it is not what design D2 asks. This was not tried here: the ruleset changes with task 2.1.
- **Astral's rule.** uv's tag ruleset `tag-requires-release` targets every tag with `non_fast_forward` and `required_deployments` for the environment `release`, and no bypass; `tags-are-immutable` (ruff, ty and uv) adds `deletion`, `non_fast_forward` and `update`, no bypass. `required_deployments` is documented for branches, "before a branch can be merged", and in the REST schema as "Choose which environments must be successfully deployed to before refs can be pushed into a ref that matches this rule". uv's jobs that publish to PyPI and crates.io run in `release` before the job that creates the release and its tag, so a successful deployment of the commit exists when the tag is pushed; whether a job's own deployment, still in progress, satisfies the rule is not documented.
- **Environments.** Required reviewers "approve workflow jobs that reference the environment", up to six, one approval enough, with an option to prevent self-review; on GitHub Free, Pro and Team they exist for public repositories only. A job can reference an environment with `deployment: false`, which creates no deployment, while "Required reviewers still apply". Each job that references an environment waits for its own approval; uv's workflow says "GitHub fires approval events on every job that deploys to an environment, so we have a dedicated environment for this purpose instead of using the `release` environment", its `release-gate`.

**For this project.** Task 2.1 adds a tag ruleset for `v*` with `required_deployments: [release]` and `non_fast_forward`, no bypass, beside the existing `tags` ruleset (updates, deletions, force pushes), and orders the workflow so that a job in `release` has finished with success before the job that creates the tag runs: the maintainer approves one job, the gate, and the publishing job either references `release` too (a second approval) or runs after the gate without it. Which of the two holds under the rule, and whether a job's own deployment counts, is for 2.1 to check, through the API where it can read a refusal. **The fallback**, if the rule cannot be met from the workflow: "Restrict creations" on `v*` with the repository admin role as the only bypass; the maintainer creates the annotated tag on the dispatched commit, and the workflow, dispatched on the tag, creates the release for that tag and refuses one that does not point at its commit. **As built** (task 2.1, design D2): the ruleset `releases` on `v*` with `required_deployments: [release]` and no bypass; a publishing job in `release` had its tag refused, its own deployment being in progress, and a gate job in `release` that only ends the commit's deployment, before a publishing job outside the environment, let the tag through, so the maintainer approves one job, the gate.

## Immutable releases

From GitHub's documentation: "Immutable releases" (2026-09-03), "Preventing changes to your releases" (2026-07-20), "Verifying the integrity of a release" (2026-06-05), and the REST reference.

- **What freezes**: "Git tags cannot be moved: Once an immutable release is published, its associated Git tag is locked to a specific commit, cannot be changed, and cannot be deleted while the release exists. If you delete the immutable release, you can delete the tag, but you cannot reuse the same tag name." "Release assets cannot be modified or deleted". The title, the notes and the pre-release and latest marks still change. Each immutable release gets "a release attestation, which is a cryptographically verifiable record of a release containing the release tag, commit SHA, and release assets"; tags of immutable releases cannot be reused even by a repository recreated under the same name.
- **The setting**: Settings, "Releases", **Enable release immutability**, which "will only apply to future releases"; `PUT /repos/{owner}/{repo}/immutable-releases` with the administration write permission does the same.
- **Publishing one**: "Create the release as a draft. Attach all associated assets to the draft release. Publish the draft release." When the tag appears the documentation does not say; task 2.1 saw it appear at the publication, the draft being `untagged-<hash>` until then, so the tag rule above judges the publication.
- **Checking one**: `gh release verify <tag>` checks that the release exists and is immutable; `gh release verify-asset <tag> <file>` that a local file is one of its assets, except the source archives, made on download.

## Artifact attestations

From `actions/attest-build-provenance`'s README at v4.2.2 and `actions/attest`'s at v4.2.2, `gh attestation verify --help` (gh 2.103.3) and GitHub's "Using artifact attestations".

- **The action**: `actions/attest` with no predicate "auto-generates SLSA build provenance"; `subject-path` takes a glob or a list, up to 1,024 subjects in one attestation. It needs `id-token: write`, "to mint the OIDC token necessary to request a Sigstore signing certificate", and `attestations: write`, "to persist the attestation"; `artifact-metadata: write` only for storage records of images pushed to a registry. Attestations are available for public repositories on every current plan.
- **The wrapper**: "As of version 4, `actions/attest-build-provenance` is simply a wrapper on top of `actions/attest`. Existing applications may continue to use the `attest-build-provenance` action, but new implementations should use `actions/attest` instead."
- **Verifying**: `gh attestation verify <file> -R <owner>/<repo>` fetches the attestations for the file's digest from the API and checks the predicate type (`https://slsa.dev/provenance/v1`), the source repository and its owner, and the certificate's identity against the workflow; `--signer-workflow <owner>/<repo>/.github/workflows/<file>` names the workflow, `--source-digest` the commit, `--source-ref` the ref, `--deny-self-hosted-runners` refuses other runners; `--bundle` and `--custom-trusted-root` verify offline. Without a terminal it prints nothing on success; its status says.

## crates.io trusted publishing and the workspace's order

From crates.io's "Trusted Publishing" page (2026-10-02), `rust-lang/crates-io-auth-action`'s README at v1.0.6, RFC 3691, Cargo's changelog (1.90) and `cargo publish --help` and `cargo help publish` on 1.99.1, Cargo's "Specifying dependencies", through Context7 (`/rust-lang/cargo`, `/rust-lang/crates.io`).

1. **The first publish, by hand**: "Your crate must already be published to crates.io (initial publish requires an API token)", and "You must be an owner of the crate".
2. **The trusted publisher**: on crates.io, the crate's Settings, Trusted Publishing, **Add**, GitHub: "Repository owner", "Repository name", "Workflow filename" ("e.g., `release.yml`"), "Environment: Optional environment name if you're using GitHub environments". One per crate.
3. **The job**: `permissions: id-token: write`, `environment: release` "for enhanced security", `rust-lang/crates-io-auth-action` with an `id`, then `cargo publish` with `CARGO_REGISTRY_TOKEN` from its `token` output. The token expires "after 30 minutes", the action's post step revokes it, and its scope is `publish-update` (RFC 3691): new versions of a crate that has the publisher, no new crate, no yank.

**The order.** Cargo 1.90: "Stabilize multi-package publishing. This allows cargo to publish multiple crates in a workspace, even if they have inter-dependencies. For example, `cargo publish --workspace` or `cargo publish -p foo -p bar`. Note that `cargo publish` is still non-atomic at this time. If there is a server side error during the publish, the workspace will be left in a partially published state." Its changelog adds that a whole-workspace publish skips `publish = false` packages, and the members not yet published are resolved from a local overlay while the set is packaged and verified; `cargo help publish` says each upload is polled for until it appears in the index. From the manifests' normal and build dependencies: protocol; simulator-reader; agent-ios; mirror; android; wire; bench, unless it stays unpublished; cli; simulator; ios; daemon; mcp. ios's dev-dependencies on agent-ios, mirror and simulator carry versions, so they are kept in its package and have to exist first, which the order already gives.

**Path and version.** A dependency with both "will use the registry version" once published, and the `version` "is checked against the local copy"; a dev-dependency with a path alone (wire's and simulator's on themselves) is dropped from the package.

**What a package of this workspace leaves behind today**, for task 3.1: `[workspace.package]` still has `publish = false` and no `repository`; the daemon's build script builds the agent from `../../agent-android`, outside its package, so a build from crates.io has no agent source and fails unless `SKIP_AGENT_BUILD=1` or `MOBILE_AGENT_JAR` is set; `crates/simulator/reader` is a package of its own, which cargo leaves out of the simulator's package (`cargo package --list -p simulator` lists no `reader/`), so a build from crates.io embeds no reader and reads trees through the host translator, with a warning; `.cargo/config.toml`'s libjpeg-turbo settings belong to no package. **As built** (task 3.1, design D5): the packages are named `mobile-agent` and `mobile-agent-<name>`, the runner `mobile-agent-ios-runner`, and publish to crates.io alone with the repository's URL, the bench harness never; a build from the packages embeds no agent (the daemon deploys one from `MOBILE_AGENT_JAR`) and no reader (the host translator, or `MOBILE_AGENT_READER`), reads the agent's version through a link the Android driver's package holds as a copy, and finds libjpeg-turbo where `TURBOJPEG_LIB_DIR` and `TURBOJPEG_INCLUDE_DIR` name it; `cargo publish --dry-run --workspace` is green for the eleven, and each crate but protocol and wire waits on its dependencies' publish.

## npm

Written for task 3.4 (design D7) on 2026-11-05. From npm's pages on trusted publishing (last edited 2026-10-06), staged publishing (2026-09-29), [`npm trust`](https://docs.npmjs.com/cli/v12/commands/npm-trust/) (12.2.1, 2026-06-02), `npm publish` (11.21.2, 2026-03-23) and provenance (2026-05-04), the npm CLI's source at v11.20.0, the version Node 26.13.0 bundles (`lib/commands/publish.js`, `lib/utils/oidc.js`, libnpmexec's `get-bin-from-manifest.js`, `npm-exec.md`), GitHub's changelog, `actions/setup-node`'s advanced usage at v7.1.0, the registry's metadata for esbuild 0.28.2 and esbuild's getting-started page, Socket's supply-chain risk page, Node's release index and schedule and the Ubuntu images' READMEs, through Context7 (`/websites/npmjs`, `/npm/cli`) and at each source.

- **The names.** `mobile-agent` (a mobile browser detection helper, first published in 2012 and last changed in 2022) and `mobile-agent-mcp` (another tool's MCP server for Simulators, emulators and devices, first published on 2026-05-30, 1.0.2 of 2026-07-21) answer 200 on the registry; `@mobileagent/cli`, `@mobileagent/cli-darwin-arm64`, `-linux-x64` and `-linux-arm64` answer 404, the registry's search for `scope:mobileagent` finds nothing and `/-/org/mobileagent/package` answers 404. A scope is a user's or an organisation's, so the maintainer creates the organisation `mobileagent` before the first publish.
- **esbuild's pattern**, the prior art: `esbuild` 0.28.2 (published 2026-08-08) lists 26 packages `@esbuild/<platform>-<arch>` as `optionalDependencies` at its own version, each with `os`, `cpu` and `preferUnplugged` (for Yarn's Plug'n'Play, which then keeps the binary on disk) and no `bin`; its `bin/esbuild` is a JavaScript shim, and it keeps a `postinstall`, `node install.js`, that "checks that the esbuild binary is the correct version" and points `node_modules/.bin/esbuild` at the native executable. Its page says what follows without the script: with `--ignore-scripts` "the correct binary is still installed through optional dependencies" and the command stays a shim, at the cost of a Node process per command; with `--no-optional` the script downloads the binary from the registry, which proxies can break; `node_modules` copied to another OS does not work. npm's `package.json` also has `libc` (`glibc`, `musl`), which "only applies if os is linux". This design takes the optional dependencies and the shim and drops the script: no version check at install, no download, no rewrite of the command; Linux's packages name `glibc`, which the binaries need at 2.35 or newer.
- **Socket's view of a package** (its supply-chain risk alerts, page updated 2026-06-05): "Install scripts" is High, "Install scripts are run when the package is installed. The majority of malware in npm is hidden in install scripts."; "Native code" is Medium, "Contains native code (e.g., compiled binaries or shared libraries)"; "Shell access" is Medium. Packages without a script avoid the first; a platform package holds native code by design, and a shim that starts a process is what the third describes, so a scan flags those two and not the install.
- **Trusted publishing**: "Trusted publishing requires npm CLI version 11.5.1 or later and Node version 22.14.0 or higher." It is configured in "Packages → YOUR_PACKAGE → Settings → Trusted publishing", GitHub Actions, with "Organization or user", "Repository", "Workflow filename" ("Enter only the filename, not the full path"), "Environment name (optional)" and "Allowed actions": "`npm stage publish` is always allowed", direct `npm publish` is a choice, configurations created after 2026-09-03 default to staged publishing alone, and npm recommends that for stronger security. "All fields are case-sensitive and must be exact", npm "does not verify your trusted publisher configuration when you save it", and "your package's `repository.url` field in `package.json` must exactly match your GitHub repository"; GitHub-hosted runners only; a package takes up to ten. Under trusted publishing from a public repository, provenance is generated "by default", without `--provenance`. "A newly created trusted publisher configuration must complete its first successful publish within 2 days", or it "expires and can no longer be used or edited" (GitHub's changelog, 2026-10-02, "Unvalidated npm trusted publishing configurations now expire", which also refuses tokens to `issue_comment` events as to `pull_request_target`). `npm trust github <package> --file release.yml --repo <owner>/<repo> --env release --allow-publish` does the same from the command line, with npm 11.15.0 or newer and two-factor authentication on the account.
- **The first publish.** `npm trust`'s page: "The package you're configuring must already exist on the npm registry." So the first version of each package is published by hand, as crates.io's is; the page's path to the form is a package's settings, and the trusted publishing page says nothing of a package that does not exist. Since 2026-10-02 `npm stage publish` can create a package with "a local session or a granular access token, including a stage-only token" (GitHub's changelog), not with trusted publishing; staging a new package publishes a public placeholder, `0.0.0-stage`, and the staged version waits for a maintainer's approval with two-factor authentication (staged publishing, which needs npm 11.15.0). A first publish by hand of the version's packages, with two-factor authentication, is the plainer path, and it carries no provenance.
- **The publish command** (`lib/commands/publish.js` at v11.20.0): without an explicit tag a prerelease is refused, "You must specify a tag using --tag when publishing a prerelease version" (npm/cli#7910, npm 11.0.0), and a tag that is a valid semver range too; a version the registry has is refused; `--access` is "public" for a new package. `npm publish <tarball>` runs no script, scripts running "only for directory type publishes". The OIDC exchange runs before the credentials are checked, in a dry run too: with `id-token: write` it asks GitHub for a token for the audience `npm:registry.npmjs.org` and posts it to `/-/npm/v1/oidc/token/exchange/package/<name>`; any failure is logged and the command goes on ("intended to never throw"), so a dry run without credentials warns "This command requires you to be logged in" and uploads nothing. `package.json`, `README.md` and `LICENSE` are always packed and "Symbolic links are never included". The provenance page asks that `repository` match "(case-sensitive) where you are publishing with provenance from".
- **`npx` and several commands** (libnpmexec's `get-bin-from-manifest.js`): with no `--package`, `npx <package>` runs the one command, or the one named as the package's unscoped name, and otherwise fails with "could not determine executable to run"; `@mobileagent/cli`'s three commands, none named `cli`, therefore need `npx --package=@mobileagent/cli <command>`. "When standard input is not a TTY or a CI environment is detected, `--yes` is assumed", and `-p` is `--package` in `npx` alone. Without `--package`, `npx mobile-agent-mcp` would fetch the unrelated `mobile-agent-mcp`.
- **Node on the runners.** The Ubuntu 22.04 and 24.04 images (20261026) default to Node 22.23.4 with npm 10.9.9, too old for trusted publishing, and cache 22.23.4 and 24.22.1; the Ubuntu 26.04 image (20261101.186.1), which `ubuntu-latest` ran the dry run's jobs on although the images' README still maps the label to 24.04, defaults to 24.22.2 with npm 11.19.1 and caches 22.23.4 and 24.22.2, so `actions/setup-node` downloaded 24.22.1 there from GitHub's `actions/node-versions`. Node 24 (Krypton) is a maintenance LTS since 2026-10-20 until 2028-04-30, 24.22.1 bundling npm 11.19.1; Node 26 (Lithium) became the active LTS on 2026-10-28 with 26.13.0 and npm 11.20.0; Node 22 is maintained until 2027-04-30. `actions/setup-node` v7.1.0 (2026-10-08) asks for npm 11.5.1 or newer and `package-manager-cache: false` in a publishing workflow, and writes an `.npmrc` with a `NODE_AUTH_TOKEN` placeholder only when given `registry-url`, which trusted publishing does not need.

## The binaries' targets

From the runner images' README (2026-11-03) and the `xcode-27`, Ubuntu 22.04 and 24.04 image READMEs, actions/runner-images#14404, `crates/simulator/README.md` (Compatibility), the build scripts and `cargo tree`.

## What we take

- **D1.** A hand-written `release.yml`, for the reasons above; cargo-dist's ideas kept: a dispatch with a dry run, a matrix per target, checksums beside the binaries.
- **D2.** Three targets: aarch64-apple-darwin on `xcode-27` with the image's Xcode 27, x86_64 and aarch64 Linux (gnu) on Ubuntu 22.04. The jar built once and handed to each build; the vendored emulator proto, so that every daemon is built from the same; the version reaching the CLI through `MOBILE_AGENT_RELEASE`. `actions/attest` v4.2.2 on each tarball and its three binaries, so that a user can verify an installed binary as well as the download. No cache in any job, mise's own cache off. The publishing job (2.1) creates the release for `v<version>` on the dispatched commit as a draft, attaches the tarballs, a `SHA256SUMS` of them and the notices, and publishes it; it refuses a version other than the workspace's, which the daemon and the server print. Release immutability is set before the first run that publishes; the tag rule is Astral's `required_deployments`, with the maintainer's tag as the fallback.
- **D4.** `gh release verify v<version>`, `gh release verify-asset` and `gh attestation verify` with `--signer-workflow`, the commands the README's Install gives.
- **D5, D6.** The first publish by hand with `cargo publish --workspace` (or crate by crate in the order above, since it is non-atomic), after `cargo publish --workspace --dry-run`; a trusted publisher per crate naming `release.yml` and `release`; the job with `rust-lang/crates-io-auth-action` v1.0.6. 3.1 answers the jar, the reader and libjpeg-turbo for a build from crates.io.

- **D7.** Four packages under `@mobileagent`: one per target, filled from that target's attested tarball and published only from it, as optional dependencies of `@mobileagent/cli`, whose three commands are a dependency-free CommonJS launcher; no script in any package. The release workflow packs them after the verify jobs and publishes them after the release from the `release` environment, with npm 11.19.1 (Node 24.22.1 through `actions/setup-node`), `--provenance`, the prerelease's first identifier as the tag and no npm token; a dry run publishes with `--dry-run`. The first version by hand; a trusted publisher per package naming `release.yml` and `release`, with `npm publish` allowed, created within 48 hours of the first run that publishes. `npx --package=@mobileagent/cli@<tag> mobile-agent-mcp` in the MCP clients' configurations.

## Where this design differs

- From Astral: one maintainer, so one approval and no second reviewer; no GitHub App and token service, so the publishing job uses its own token with `contents: write`; no installers, PyPI or Docker.
- From cargo-dist: tarballs (`.tar.gz`) without installers or a manifest; the build steps are this workspace's.
- From esbuild: no install script, so no version check or download at install and the commands stay a launcher; three platforms; the platform packages filled from the release's tarballs rather than built for npm.

## Risks

- **`required_deployments` on tags** is documented for branches; task 2.1 saw it refuse a tag on a commit without a successful deployment, the publishing job's own deployment in progress included, and accept one after the gate job's (design D2, As built).
- **Images**: `xcode-27` is a preview image whose label may change when it is generally available; Ubuntu 22.04's image will retire, and the next floor is 24.04's glibc 2.39 or a static musl build.
- **Gatekeeper**: the binaries are signed ad hoc, not notarized. A tarball downloaded through a browser carries the quarantine attribute, which macOS checks before running an unnotarized executable; `curl` and `gh release download` set none. 2.3's clean-account install follows the README and finds out which it needs.
- **A partial publish**: `cargo publish --workspace` stops at a server error with the crates before it published, and a version cannot be deleted, only yanked.
- **npm's first trusted publish** is untried until the run after the first publish by hand: a trusted publisher that does not match the run exactly fails with E404 or ENEEDAUTH, and one not used within 48 hours expires. A version on npm cannot be published again, so a run that stopped between the four packages skips the ones npm holds when it runs again.
