# Wire protocols: state of the art

Research note for task 2.3 of `mobile-automation-foundation`. It feeds spike S5 (wire format, task 2.8) and the protocol crate (group 3), and checks design decisions D1, D4 and D9 against what existing tools do. Every claim was read from the pinned sources at the end on 2026-09-26. Numbers marked *model* are estimates that S5 replaces with measurements.

Out of scope: the ADB transport (S6), emulator token discovery (S7) and Simulator private APIs (`simulator.md`).

## Findings in brief

- agent-browser's CLI-to-daemon protocol is deliberately primitive: one newline-delimited JSON request and one response per Unix-socket connection, with every command serialized behind one mutex. What agents depend on is the command grammar, the ref syntax and the JSON envelope. D9 must mirror those; the device link is free to differ.
- The device protocols that sustain high rates (scrcpy, CDP screencast, the emulator controller) separate lossless control traffic from lossy frames, stamp frames with sequence numbers and pace them with credits or latest-frame-wins. The slow ones (WebDriverAgent, the UiAutomator2 server, Maestro) are request-response only and poll for change.
- The ratio to JSON depends on the schema as much as on the format. At equal schema the *model* puts CBOR at 2.35x smaller than readable-key JSON on a 500-node tree and 2.87x on events (3.54x with positional arrays); without interning class names and resource-id prefixes on either side, the tree ratio falls to 1.68x. D4's "3x better than JSON" gate needs the precise definition given in the S5 plan below.
- Predicted S5 winner: CBOR, with a hand-rolled Kotlin codec on the device and `minicbor` on the host. MessagePack ties on bytes and speed but needs element counts before elements. Protobuf is 8 to 11% smaller in the *model* but is not self-describing, which the device-protocol spec requires. FlatBuffers is larger for small messages and needs `flatc` plus a version-locked runtime.
- Socket Firewall Free wraps npm, yarn, pnpm, pip, uv and cargo, not Maven. Under the "installs through Socket" rule, Kotlin library codecs cannot be fetched for S5 without an explicit exception. That favours hand-rolled codecs regardless of speed.

## Protocol notes

### agent-browser (D1, D9)

**Does.** `connection.rs` resolves a socket directory (`AGENT_BROWSER_SOCKET_DIR`, then `$XDG_RUNTIME_DIR/agent-browser`, then `~/.agent-browser`, then the temp dir, plus an optional namespace subdirectory) and keeps sidecar files per session: `.sock`, `.pid`, `.version`, `.config` (a hash of daemon-affecting options) and `.stream` (the port of the WebSocket stream server). `ensure_daemon` treats "the socket accepts a connection" as liveness. It restarts a daemon whose `.version` differs from the CLI (a graceful internal shutdown action, then kill), spawns the same binary with `AGENT_BROWSER_DAEMON=1` under `setsid`, polls 50 × 100 ms, and reuses a concurrent winner when bind fails with "Address already in use". It rejects socket paths over 103 bytes. `send_command` opens one connection per command, writes one JSON line and reads one line. It makes up to five attempts on transient errors (EAGAIN, EOF, reset) with 200 ms × attempt backoff and respawns the daemon once when the socket is gone.

`native/daemon.rs` runs a tokio `UnixListener`. Each connection loops over lines and runs each command under one `Mutex<DaemonState>`. Replies are `{id, success, data}` or `{id, success: false, error, code?}`. Lines that start with an HTTP verb are rejected, and the daemon exits after `AGENT_BROWSER_IDLE_TIMEOUT_MS` (default 1 h, `0` disables). A 100 ms tick drains CDP events. A **session** is a separate daemon process with its own browser.

`commands.rs` turns argv into `{id, action, …}`; `id` is `r` plus the current microseconds modulo 10^6 and is only echoed back. `batch` is a client-side loop. Commands arrive as quoted argv strings or as a JSON array of argv arrays on stdin, and `--bail` stops at the first failure. `--json` prints an array of `{command, success, result, error, code?, warning?}`; the key is `result`, not `data`. In JSON mode `output.rs` prints the envelope on stdout; otherwise it prints human text, with errors on stderr. Exit status is 1 on failure. `--content-boundaries` wraps page-derived output in markers carrying a CSPRNG nonce, and `--max-output` truncates.

Snapshots render one element per line: `- checkbox "I agree" [checked=false, ref=e2]`. Refs come from a monotonic counter and stay the same while the backing node exists. `parse_ref` accepts `@e2`, `ref=e2` and `e2`. `-i` keeps only ref-bearing nodes: interactive roles (button, textbox, checkbox, switch, tab and others) plus named content roles. JSON data is `{snapshot, origin, refs: {e2: {role, name}}, removedRefs: ["@e5"]}`. With `--delta` it becomes `{kind: full | unchanged | delta, revision, baseRevision, changes: [{op: add | remove | replace, ref, field?, value?, node?}], treeChange: {startLine, deleteCount, lines}}`, falling back to `full` when the delta reaches 70% of the tree's size. Machine-readable codes are snake_case and sparse (`tab_gone`, `webmcp_*`); an unknown ref fails with `Unknown ref: e5` and no code.

`agent-browser mcp [--tools core,network,…]` is a stdio JSON-RPC server. Its profiles (`core` by default with 29 tools, then `network`, `state`, `debug`, `tabs`, `react`, `mobile`, `webmcp`, `all`) decide which tools are listed. Each tool call runs the same binary with `--json`, so the CLI's JSON output is the MCP contract. `agent-browser.schema.json` at the repository root is a draft-07 schema for the config file (51 properties), not for output. Config comes from `--config` or `AGENT_BROWSER_CONFIG` alone, else `~/.agent-browser/config.json` overlaid by `./agent-browser.json`; environment variables override the file and flags override both.

**Reuse.** The grammar, ref syntax, envelope, batch, delta snapshot shape, sidecar and version-restart logic, read-timeout rule and idle exit, listed under D1 and D9 below.

**Differ.** Android permits one UI automation owner per device, so one daemon must own every device and sessions become claims inside it rather than separate processes. Commands for different targets must run concurrently instead of behind one mutex. Every JSON error carries a code, as the agent-cli spec requires, and a stale ref gets its own code with re-snapshot guidance.

### Chrome DevTools Protocol

**Does.** Commands `{id, method, params}` and responses `{id, result}` or `{id, error: {code, message, data?}}` travel as one JSON object per WebSocket message; events are `{method, params}` without `id`. `Target.attachToTarget` with `flatten: true` returns a `sessionId` that later messages carry, and auto-attached targets announce theirs in `Target.attachedToTarget`, so every tab and iframe shares one socket. The older nested `sendMessageToTarget` is deprecated. `waitForDebuggerOnStart` pauses new targets until `Runtime.runIfWaitingForDebugger`. There is no deadline or cancel field. `Page.startScreencast` paces frames with `maxFramesInFlight` (default 3) and `Page.screencastFrameAck`; `sendLastFrame` keeps the newest frame ready for the next ack.

**What agent-browser relies on.** It launches Chrome with `--remote-debugging-port=0`, reads `DevToolsActivePort`, and attaches with `flatten: true`, auto-attach and resume. Ids come from an `AtomicU64`, and pending calls sit in a map of oneshot senders with a drop guard for callers that give up. Each command times out client-side after 30 s, and every pending call fails as soon as the reader exits. Screencast sessions route to a 16-slot queue that drops new frames when full, and a WebSocket ping goes out every 30 s. We copy the envelope semantics, flat addressing, the pending-map discipline and credit pacing.

**Differ.** CDP infers the message kind from which keys are present. WebDriver BiDi's explicit `type: success | error | event` is easier to validate, and our envelope carries an explicit kind the same way. CDP is JSON; our device link is binary.

### scrcpy control protocol

**Does.** The client pushes the server jar and runs it with `app_process`, passing its exact version as the first argument; the server exits on a mismatch, and the protocol is declared internal. By default the client listens on a host port that `adb reverse` exposes on the device as `localabstract:scrcpy_<scid>`, with a 31-bit random `scid` so concurrent instances do not collide; `adb forward` is the fallback. Up to three sockets open in a fixed order. On a forward tunnel the device writes a dummy byte first, because connecting through `adb forward` succeeds even when nothing listens. A control message is one type byte followed by a fixed big-endian layout for that type, with no length prefix. There are 23 client-to-device types and 3 device-to-client types, each message at most 256 KiB. A touch event is 32 bytes including the type byte: action u8, pointer id u64, x and y as i32, the client's view of the screen size as two u16, pressure as u16 fixed point, then action button and buttons as u32. Injected text is a u32 length plus UTF-8 truncated at a character boundary to 300 bytes. Setting the clipboard carries a u64 sequence that the device echoes in `ACK_CLIPBOARD`. The client queue drops droppable messages beyond 60 but never drops UHID create or destroy; the device-side queue holds 16 messages and drops with a warning.

**Reuse.** The random socket suffix, the agent-speaks-first rule, droppable versus non-droppable message classes, and coordinates that carry the sender's screen size so a rotation between send and injection is detectable.

**Differ.** Without a length prefix an unknown type ends the stream; our length-prefixed frames let a receiver skip unknown kinds. scrcpy negotiates by exact version on argv, while D4 negotiates versions and capabilities in-band so a daemon can keep driving an older agent.

### WebDriverAgent, W3C WebDriver and Appium (negative example)

**Does.** W3C WebDriver sends one HTTP request per command and wraps results as `{"value": …}` and errors as `{"value": {error, message, stacktrace, data?}}`; elements are referenced under the key `element-6066-11e4-a52e-4f735466cecf`. WebDriverAgent listens on 8100 with MJPEG on 9100, adds `sessionId`, and names the stack field `traceback`. It serves `/source` as XML by default or as JSON with `format=json`. In the JSON form every node repeats about fifteen keys, stringifies `frame` with `NSStringFromCGRect` next to a `rect` object, and encodes booleans as the strings `"1"` and `"0"`. Its defaults wait up to 10 s for idle and 2 s for animations. The UiAutomator2 server listens on device port 6790 and writes every exposable attribute of every node as an XML attribute string. agent-browser's own iOS path goes through Appium, where a tap is `POST /session/{id}/actions` with a pointer sequence that includes a 100 ms pause.

**Reuse.** Nothing on the wire. The W3C error triple maps onto our error model (code, message, detail), to which we add a retryable flag.

**Differ.** One HTTP exchange per command, a tree re-serialized per request with key names on every node, and fixed idle waits are exactly what D2, D4 and D8 remove. In the *model*, WDA-style JSON for the tree is 8.1x the size of the interned CBOR encoding.

### Maestro and agent-device

**Maestro.** `maestro_android.proto` defines 12 RPCs: `deviceInfo`, `viewHierarchy`, `screenshot`, `tap`, `inputText`, `eraseAllText`, `setLocation`, `isWindowUpdating`, `launchApp`, client-streaming `addMedia`, and two location-mocking calls. `ViewHierarchyResponse` is a single `string` holding an XML dump that the host re-parses with a DOM parser, and `TapRequest` is two `uint32`. Settling polls `isWindowUpdating` with 50 ms sleeps and compares screenshots against a 0.005 threshold. The server runs Netty on port 7001 and permits keepalive pings every 30 s; the client channel runs over a dadb socket with a 2 min keepalive and a 120 s deadline per call. The lesson: gRPC framing did not help, because the payload that matters stayed text and there is no event stream.

**agent-device.** The runner protocol is one HTTP `POST /command`, with `{command, …}` in and `{ok, data?, error?: {code, message}}` out. The daemon stamps a `commandId`, and the runner journals commands and answers `status` so a lost reply can be recovered. Busy states have their own codes, and a table decides whether each error is retried, resent or fatal to the session. The Simulator AX bridge frames requests and responses as a u32 big-endian length plus UTF-8 JSON over AF_UNIX, protocol version 1, frames of at most 16 MiB. It bounds every request: `maxDepth` at most 128, `maxNodes` at most 10,000, `maxDurationMs` at most 120 s, plus `maxResponseBytes`. The host owns identity, deadlines and lifecycle. The runner document notes that an accessibility call cannot be cancelled once issued, so a deadline frees only the caller; reads share one serial queue and are skipped while an abandoned read is still outstanding.

**Reuse.** Explicit per-request bounds with truncation reported in the response, a protocol version in every reply, a command journal for replies lost across a reconnect, a table from error code to retry policy, and a walker that checks its deadline between node reads because one platform call cannot be interrupted.

### Android emulator controller

`emulator_controller.proto` (package `android.emulation.control`, marked experimental) names RPCs by convention: `streamX` for lifetime streams, then `getX`, `setX` and `sendX`. The fast path needs `getScreenshot`, server-streaming `streamScreenshot`, `sendTouch`, `sendKey` and client-streaming `streamInputEvent`, which delivers input in order without a round trip per event. `Image` carries a `seq` that is monotonic but not contiguous, so a client can count dropped frames, plus `timestampUs`. `ImageFormat` offers only PNG, RGBA8888 and RGB888, so JPEG encoding stays on the host (D7), and `ImageTransport.MMAP` can deliver frames through shared memory instead of the socket. The AOSP prebuilts copy has 1,397 lines; the copy shipped with emulator 37.1.11 at `$ANDROID_HOME/emulator/lib/emulator_controller.proto` has 1,865 and only adds RPCs. Generate the tonic client from the installed emulator's copy.

## Multiplexing and flow control

- **Request ids.** CDP, JSON-RPC and gRPC (through HTTP/2 streams) all allow out-of-order responses keyed by id. Copy agent-browser's CDP client: a counter per connection, a pending map, a guard that removes the entry when a caller gives up, and failing every pending call the moment the reader sees EOF. Put an explicit message kind in the envelope, as BiDi does.
- **Sequence numbers.** Two classes of stream. Lossless streams (tree and window changes, lifecycle) carry contiguous per-stream sequences, and a gap triggers a resync, as the device-protocol spec requires. Lossy frame streams carry a monotonic but non-contiguous sequence plus a timestamp, as the emulator's `Image.seq` does, so drops can be counted without ever triggering a resync.
- **Deadlines and cancellation.** gRPC sends a relative `grpc-timeout` (at most 8 digits plus a unit), so clock skew between peers does not matter, and the server's call is cancelled once it passes; there is no deadline by default. CDP has neither, so clients such as agent-browser time out locally after 30 s. For us: a relative `deadlineMs` on each request, checked by the tree walker between node reads. The dispatcher thread sends the deadline error even while the walker is stuck in a Binder call, and answers `busy` while an abandoned walk is still running, which is agent-device's rule.
- **Frame backpressure.** CDP gives the producer credits (`maxFramesInFlight`) that acks replenish. agent-browser's stream server keeps a latest-frame-wins slot (a tokio `watch`), an fps cap and an optional one-in-flight mode with cumulative acks; its CDP router drops new frames when a 16-slot queue is full; tokio's broadcast channel drops the oldest messages for a lagging receiver. For us: frames are latest-wins with a credit window of 1 to 3 and never block. Lossless events pass through a bounded queue whose overflow collapses into one resync marker instead of blocking the accessibility callback thread. Commands and their responses are never dropped, like scrcpy's non-droppable class.
- **Liveness.** agent-browser sends a WebSocket ping every 30 s and sets TCP keepalive (30 s, then 10 s probes). gRPC keepalive leaves client pings off by default, defaults the server to 2 h with a 20 s ack timeout, and enforces a minimum ping interval (default 5 min) with a `too_many_pings` GOAWAY; Maestro uses 2 min and 20 s. All of them exceed the spec's 5 s bound. Over `adb forward` the TCP hop ends at the local adb server, so TCP keepalive proves nothing about the agent, and a connect succeeds even when nothing listens. For us: the agent writes its hello first (scrcpy's dummy byte), EOF means disconnected at once, and an application ping every 1 s while idle declares the agent dead after 3 s of silence.

## S5 benchmark plan

**Datasets**, committed with spike S5's program as logical JSON plus the generator seed, and kept privately with it since the repository was made public (`docs/spikes/README.md`):
- `T500`: one snapshot response holding the 500-node tree. Each node has an id, a class index into a per-snapshot string table, a resource id with its package prefix interned, text, a content description, bounds as four i32, flags as a u32 bitmask, a window id and children. Capture it from the Compose fixture's 500-node screen through S1's agent when that exists; until then, generate it with the model's distributions.
- `E10K`: 10,000 event frames, each a separate frame so per-frame overhead counts: stream, contiguous seq, kind, window id, a path of 2 to 10 u16, a timestamp in µs.
- `R1K`: 1,000 mixed requests (tap, type, snapshot) for the host-to-device direction.

**Candidates**, all on the same logical schema. Rust: `serde_json`; `minicbor` with derive (maps for nodes, arrays for events); `ciborium`; `rmp-serde` with both `to_vec` and `to_vec_named`; `prost` with derive on hand-written structs; `flatbuffers` with `flatc` output. Kotlin on ART: `org.json`; `android.util.JsonWriter`/`JsonReader`; hand-rolled CBOR, MessagePack and protobuf-wire codecs. The library codecs (`msgpack-core`, `protobuf-javalite`, `flatbuffers-java`, `kotlinx-serialization-cbor`) run only if the user approves a fetch path outside Socket Firewall; otherwise the report lists them as not measured and says why.

**Metrics.**
1. Bytes per dataset, including 4-byte frame headers.
2. Rust encode and decode time on the host: warm-up, then at least 100 samples, reporting median and p95. Decode into owned structs, and separately into borrowed ones where the codec supports it.
3. Kotlin encode and decode time on ART through `app_process`, on the API 36 emulator and on one physical device. Report the first call on its own (interpreter and JIT, no AOT profile), then median and p95 over at least 200 iterations after a 2 s warm-up, encoding into a reused buffer where the codec allows.
4. Critical path: Kotlin encode plus Rust decode for `T500` and `E10K`, where Rust decodes the bytes the Kotlin encoder wrote, pulled back with `adb pull`, which also cross-checks the two codecs. Rust encode plus Kotlin decode for `R1K`.
5. Dex delta: the R8 release `classes.dex` of the harness with one codec, minus the same harness using only platform JSON, with `dexdump` method counts. Report the unshrunk d8 size for reference.
6. Environment: host CPU, rustc and kotlinc versions, device model, API level.

**Kotlin build without Gradle.** `KOTLIN_HOME` is the root of the kotlinc distribution; `MIN_API` comes from the android-agent note.

```sh
BT="$ANDROID_HOME/build-tools/36.0.0"; AJAR="$ANDROID_HOME/platforms/android-36/android.jar"
LIBS=$(ls libs/*.jar 2>/dev/null | tr '\n' ' '); LIBCP=$(echo $LIBS | tr ' ' ':')   # library codec jars, if any
mkdir -p build/r8 build/d8
kotlinc src -cp "$AJAR${LIBCP:+:$LIBCP}" -d build/s5-classes.jar
java -cp "$BT/lib/d8.jar" com.android.tools.r8.R8 --release --min-api "$MIN_API" --lib "$AJAR" \
  --pg-conf keep.pro --output build/r8 build/s5-classes.jar "$KOTLIN_HOME/lib/kotlin-stdlib.jar" $LIBS
"$BT/d8" --release --min-api "$MIN_API" --lib "$AJAR" --output build/d8 build/s5-classes.jar $LIBS
(cd build/r8 && jar cf ../s5.jar classes.dex)
adb push build/s5.jar /data/local/tmp/s5.jar && adb push data /data/local/tmp/s5-data
adb shell CLASSPATH=/data/local/tmp/s5.jar app_process / placeholder.s5.Main --dataset T500 --codec cbor
```

The kotlinx candidate also needs `-Xplugin="$KOTLIN_HOME/lib/kotlinx-serialization-compiler-plugin.jar"` on the kotlinc line. The d8 line dexes the harness and library classes without shrinking or the stdlib, as a size reference only. `keep.pro` keeps `placeholder.s5.Main.main` plus each library's own rules, passed explicitly: `-keep class * extends com.google.protobuf.GeneratedMessageLite { *; }` for protobuf lite, and `org.msgpack.core.buffer.MessageBufferU` for msgpack-core. Call the build-tools `d8` and `d8.jar` by path, because a `d8` found on `PATH` may belong to another SDK install. `app_process` accepts a jar that contains `classes.dex`, as scrcpy's server does.

**What "3x better than JSON" means.** For each dataset in {`T500`, `E10K`} and each candidate C, let J be the same logical messages as C (same fields, integer enums, bitmask flags, string table and interned prefixes) encoded as compact JSON with readable keys. J uses `serde_json` on the host and, on the device, whichever of `org.json` and `android.util.JsonWriter`/`JsonReader` is faster. C passes only if all three hold on both datasets:
- bytes(J) / bytes(C) ≥ 3, frame headers included;
- time(J) / time(C) ≥ 3, where time is the warm median Kotlin encode plus the warm median Rust decode (the device-to-host path); `R1K` and cold first calls are reported, not gated;
- the R8 dex delta is under 100 KB.

Appium-style JSON is reported for context and is never the baseline. The *model* predicts that bytes miss 3x on `T500` for every candidate (about 2.4 to 2.6x) and reach it on `E10K` only with positional arrays. If S5 confirms that, D4 records the measured ratios and decides on time, dex delta, evolution and debuggability; it does not weaken the baseline until something passes.

**Prediction.** CBOR wins: `minicbor` on the host (no_std, borrowed decoding, documented index-based evolution rules) and a hand-rolled Kotlin codec of a few hundred lines that adds tens of kilobytes of dex, not hundreds. MessagePack comes within 4% on bytes and should tie on speed, but needs element counts before elements, so a filtered child list must be buffered or back-patched; CBOR streams it as an indefinite-length array. Protobuf is smallest but not self-describing, so choosing it means changing the device-protocol spec. FlatBuffers loses on bytes for small messages and adds `flatc` plus a version-locked runtime. JSON on platform APIs costs no dex but 2.4 to 3.5x the bytes, and on the device `org.json` allocates a map per node.

## What we take

**D1, persistent daemon and thin CLI**
- Socket directory resolution with an environment override, a namespace subdirectory and the 103-byte path check. Sidecar `.pid`, `.version` and a `.config` fingerprint. On a version mismatch, a graceful shutdown request, then kill. A `setsid` spawn with a bounded readiness poll that reuses a concurrent winner.
- CLI↔daemon as newline-delimited JSON over the Unix socket, one request per connection, with agent-browser's field names. It is host-local, debuggable with `socat`, and already carries the JSON the CLI prints; binary encoding is only for the device link.
- Client-side retries of transient errors and a single respawn; a read timeout of max(30 s, op timeout + 10 s) so waits report their own timeout; idle exit with a default and `0` to disable; refusal of HTTP-looking input.
- Differ: one daemon owns every device, sessions are claims inside it, and commands for different targets run concurrently.

**D4, device wire format**
- A u32 big-endian length plus one CBOR item, as in agent-device's bridge and gRPC's 4-byte length, with a negotiated maximum frame size (agent-device caps frames at 16 MiB).
- An envelope with an explicit kind (hello, request, response, error, event, ping), u32 request ids echoed in responses, a relative `deadlineMs`, and errors as `{code, message, retryable}` with snake_case codes.
- The agent speaks first with `hello {versions, capabilities, maxFrame, agentVersion}` on an abstract socket named with a random suffix; the hello doubles as scrcpy's dummy byte.
- Lossless streams with contiguous sequences and resync; frame streams with non-contiguous sequences, timestamps, latest-wins and a credit window; per-request bounds with truncation flags; the protocol version on every response.
- Integer keys, per-snapshot string tables and bitmask flags, since the *model* shows they matter as much as the format.

**D9, CLI grammar and output, mirrored exactly for parity**
- The envelope `{success, data, error}`, plus `code` and `warning` when present, printed on stdout in `--json` mode, with exit status 1 on failure; human errors go to stderr.
- Refs: `@eN` in commands, with `ref=eN` and bare `eN` also accepted; snapshot lines `- role "name" [attrs, ref=eN]`; monotonic numbering and durable refs; JSON `refs` keyed `eN` with `{role, name}`, and `removedRefs` as `@eN`.
- Snapshot flags `-i`, `-c`, `-d`, `-s`, `--delta` and `--full`, and the delta payload shape, which maps directly onto the mirror (D5); `diff snapshot [-b <file>]` against the last snapshot.
- `batch` taking quoted argv strings or a stdin JSON array of argv arrays, `--bail`, and the aggregate array keyed `result`.
- `--session` with the default `default`, an environment variable for each flag, the config precedence, and a published JSON Schema for the config file; `tap <sel>` and `swipe <up|down|left|right> [distance]`.
- A `--json` output stable enough to serve as a future MCP edge's contract, since agent-browser's `mcp` profiles shell out to it. Publish an output schema too, which agent-browser does not.

## Risks

- **The D4 gate conflates schema and format.** At equal schema the *model* puts tree bytes at about 2.4x. Fix the baseline definition above before measuring, and let D4 change if the data says so.
- **Serialization may be noise next to acquisition.** Walking 500 accessibility nodes across Binder likely costs far more than encoding them. Compare S5's times with S1's tree-read latency before optimizing further, and convert byte differences into milliseconds with S6's measured transfer rate.
- **Socket Firewall Free does not cover Maven**, and no covered install path for `flatc` was found. `protoc` has one: prost-build documents building it with `protobuf-src`, which `sfw cargo` can fetch. Kotlin library-codec rows need the user's approval or stay unmeasured.
- **Spec coupling.** The device-protocol spec requires a self-describing payload, which rules out protobuf and FlatBuffers. Picking either means changing the spec, not making an exception.
- **Two hand-written codecs drift.** Mitigate with task 3.5's golden fixtures in both directions, CBOR preferred serialization (RFC 8949 §4.1) so fixtures are byte-stable, a decision on indefinite-length arrays before fixtures are cut, and fuzzing of the Rust decoder.
- **ART is not HotSpot.** Host-JVM timings mislead. Measure on devices and report the cold first call, because an `app_process` agent runs without an AOT profile.
- **Licences and versions.** minicbor is BlueOak-1.0.0 (permissive, but neither MIT nor Apache); `kotlinx-serialization-cbor` is experimental; the emulator proto is experimental and grows between emulator releases.
- **Unknown message kinds.** scrcpy shows the cost of having no length prefix. The decoder must skip unknown kinds and keys, and answer unknown requests with `unknown_method`, marked not retryable.
