# mobile-agent overview

mobile-agent is a Rust daemon with a thin `mobile-agent` CLI that drives Android devices, Android emulators, iOS Simulators and physical iPhones for AI agents. The daemon keeps a replica of every attached screen (its windows, accessibility tree and latest frame), updates it from the platform's change events and frame hashes, and answers snapshots, waits and settle checks from it; on Android a single-dex agent runs as the shell user under `app_process`, on the Simulator the driver works from the host, with only a tree reader spawned into the Simulator, and on a physical iPhone a resident XCTest runner in Rust serves the tree and text while input and frames come from the host (`README.md`). Measured on one host, one iOS 26.5 Simulator and one API 36 emulator, every latency gate passes, with the emulator's tap-to-frame gate restated from 50 to 67 ms (section 3), and mobile-agent ran the three reference flows 6.05 to 8.51 times faster than Maestro 2.10.0 at the median on the Simulator, 4.32 to 14.76 times on the emulator, and 1.06 to 2.89 times faster than agent-device 0.21.14 on the flows agent-device completed there, the login flow measured again after `fill` began reading the field back, and on the emulator once more after its 200 ms hold was kept for typed text alone (`README.md`, Measured). Those comparisons time whole flows around each tool's process: no primitive was compared with another tool's, one physical Android device and one physical iPhone have run, and the MCP server and the CDP-subset endpoint are not built (`README.md`, Status and limitations). On that Android device, a Nexus 5X on Android 8.1, warm snapshot and tap acknowledgement passed their gates, cold attach missed its 1.5 s gate at 2.2 to 3.1 s at the median, and the login flow ran 7.58 to 23.10 times faster than through Maestro (`reports/10.3-physical-android.md`). On the iPhone, an iPhone SE (3rd generation) on iOS 26.6.2, every gate of its class passed, and WebDriverAgent, the device baseline in Maestro's place, was faster on every flow but one: mobile-agent ran login 0.94 and 0.97 times as fast, list-scroll 0.36 and 0.37 times, its every stroke settling and reading where WebDriverAgent flings and checks at the end, and big-screen 0.76 and 1.12 times; it ran login 1.80 and 1.85 times faster than agent-device (`reports/11.1-ios-device.md`).

Paths are relative to the repository root. "Design" is `openspec/changes/archive/2026-10-07-mobile-automation-foundation/design.md`, whose decisions are D1 to D12; S1 to S7 are the spike reports in `docs/spikes/`. The physical iPhone's decisions are D18 to D26 of `openspec/changes/archive/2026-10-14-physical-ios/design.md`, cited as the physical-ios design, and S9 to S11 are its spikes. Percentiles are nearest-rank, as the harness and the spikes compute them; the host microbenchmarks of the `microbenchmarks` change give criterion's median of 100 samples instead (`README.md`, Host costs).

## 1. How is its architecture different from existing tools?

The research notes describe the existing tools as servers that run on the device or in the Simulator and read the screen when asked. Appium's UIAutomator2 server and WebDriverAgent answer W3C WebDriver JSON over HTTP, wait for the screen to go idle and serialize the tree on each request (`docs/research/android-agent.md`, section 3; `docs/research/protocol.md`, WebDriverAgent, W3C WebDriver and Appium); Maestro's Android driver, an instrumentation, answers gRPC, returns the tree as one XML string and polls to settle (`docs/research/protocol.md`, Maestro and agent-device; `reports/10.1-emulator.md`, finding 4). A persistent host daemon is not what sets mobile-agent apart, since agent-browser and agent-device run one too (design D1). What differs is what the daemon holds: a replica of each target, kept current from change events, frame hashes and re-reads, from which it answers snapshots, waits and settle checks instead of reading the device and waiting for idle on every request (design D5 and D8; `crates/mirror/README.md`). One daemon owns every target, and sessions are claims inside it, because Android permits one UI automation owner per device (`crates/daemon/README.md`).

On Android, as the notes read the UIAutomator2 server 10.6.6, Maestro 2.10.0 and agent-device 0.21.15 (section numbers are those of `docs/research/android-agent.md`):

| | mobile-agent | Maestro | agent-device | Appium UIAutomator2 server |
|---|---|---|---|---|
| On the device | one dex of 137,972 bytes, pushed to `/data/local/tmp` and started with `app_process` as the shell user; no APK, no instrumentation (`agent-android/README.md`) | a driver run as an instrumentation on androidx `UiDevice` (`reports/10.1-emulator.md`, finding 4) | a snapshot-helper APK run as an instrumentation, and an input-method APK for text (section 5) | a server APK and a test APK; the server runs inside an instrumentation (section 3) |
| Tree | every interactive window, walked through the agent's own UI automation connection, with the platform's node cache kept between reads (`agent-android/README.md`, Serving the protocol) | one XML string per request, re-parsed on the host (`docs/research/protocol.md`) | every root of `getWindows()`, the cache cleared before each capture | the active window by default, the cache cleared and an idle wait before every read; XML, re-parsed into a DOM for XPath |
| Change | accessibility events naming the changed subtree, with sequence numbers; Compose windows, which send none, re-read after each action and on a 1 s poll; emulator frames hashed (design D5, D7) | polls `isWindowUpdating` with 50 ms sleeps and compares screenshots | waits for 100 ms without events, at most 500 ms, then captures | waits for 500 ms without events, at most 10 s |
| Input | `injectInputEvent` with `WAIT_FOR_RESULT`, 1.9 ms per tap at p50 (S1); on an emulator, the controller's `sendTouch` (design D7) | a `tap` RPC | the hidden three-argument `UiAutomation.injectInputEvent`; text through its input method | UiAutomator2 on `UiAutomation` |

On a physical iPhone, as the research note reads WebDriverAgent 16.14.1 and agent-device 0.21.22 (`docs/research/ios-device.md`, What the existing tools do on a device):

| | mobile-agent | agent-device | Appium (WebDriverAgent) |
|---|---|---|---|
| On the phone | a Rust XCTest bundle in a re-signed copy of Xcode's `XCTRunner.app`, installed by the driver, started through the phone's test manager and kept for the session (physical-ios design D20) | an XCTest runner that `xcodebuild` builds and runs from the host, kept by its daemon | WebDriverAgent, an XCTest runner serving HTTP on port 8100, started by `xcodebuild`, DVT's process control or, below iOS 27, `devicectl` |

| Change | screenshots polled on DVT and CoreDevice from the host, a frame when a pixel below the status bar moves more than two levels, 14 to 19 a second; the tree re-read after input, when frames change and every 10 s while they hold still (physical-ios design D23 and D26) | not described in the research notes | idle waits of up to 10 s and 2 s for animations by default; MJPEG of screenshots at 10 frames a second |
| Input | the disk image's dtuhidd, from the host: a tap acknowledged in about 54 ms, its 50 ms hold included, where the runner's synthesis, the fallback, takes about 290 ms (physical-ios design D22) | the XCTest runner | XCTest's event synthesis, from W3C pointer actions |
| Host link | `idevice` in the daemon's process: the CoreDevice tunnel without root, DVT, the test manager and dtuhidd over it, and CBOR frames to the runner through usbmuxd's `Connect` (physical-ios design D18) | HTTP to its runner over usbmux; `devicectl` for launches and screenshots | W3C WebDriver JSON over HTTP, through a usbmuxd forward or, from iOS 18, a RemoteXPC forwarder whose tunnel needs root |

Maestro 2.11.0 refuses physical iPhones, its device driver unfinished (`docs/research/ios-device.md`, Maestro). The harness started WebDriverAgent its own way, re-signed for the team and started through the test manager by its helper, with Appium attached to it, since `xcodebuild` needs the Mac's DevToolsSecurity on and Appium's own launch a root tunnel (`crates/bench/README.md`, Baselines).

**What is shared with other tools.** The proposal says that a resident shell-user process on Android and fully host-side control of the Simulator "are used by no agent tool today" (`openspec/changes/archive/2026-10-07-mobile-automation-foundation/proposal.md`, Why). The research qualifies both halves. scrcpy, AOSP's `uiautomator` and openatx's `u2.jar` all start with `app_process` as the shell user, and `u2.jar` takes UI automation with the same reflective construction (`docs/research/android-agent.md`, sections 1, 2 and 4), so design D2 puts the novelty in "the resident binary protocol and the event mirror, not the launch path". On the Simulator, idb, iosef, AXe and stim already send input through dtuhidd from the host, and iosef, a Swift CLI with an MCP server, reads trees through the host translator alone (`docs/research/simulator.md`, Prior art and Comparison). mobile-agent is not fully host-side either: S4 found the host translator taking 1.0 to 1.3 s on a 500-cell screen, slower than XCTest, so the tree reader runs in the guest, a Rust port of agent-device's snapshot bridge spawned through CoreSimulator, ready 292 ms after the spawn at p50 against 568 ms through `xcrun simctl spawn` (design D6; S4). On a physical iPhone no tool reads the tree from the host: it lives in the test automation session, which only an XCTest runner holds, so mobile-agent's runner is an XCTest bundle kept alive by a test that never ends, as WebDriverAgent's and agent-device's are (`docs/research/ios-device.md`, Verdict). What differs there is a runner that speaks the device protocol and stays for the session, input sent from the host through the disk image's dtuhidd, as `idevice` and pymobiledevice3 send it and Xcode 27's Device Hub does, and frames polled from the host (physical-ios design D20 to D23).

**What a step costs.** On the Simulator a warm `snapshot -i` of the 500-cell screen took 6.1 ms at p50 through a CLI process, a tap's dispatch 0.07 to 0.12 ms, and `wait --settle` 190 to 436 ms with its quiet window at 200 ms (`reports/10.2-simulator.md`, mobile-agent primitives). `click` replies once the tap's first frame change and tree delta have arrived, or after 200 ms without one, at most 1 s (`README.md`, Agent guide). For the other tools the repository has flow times (section 3), their idle policies above, and design D6's XCTest baseline: 0.66 to 0.71 s for a snapshot of the SwiftUI 500-cell screen, and an idle wait that stalls 1.8 to 2.8 s on the animation tab. On the iPhone a warm `snapshot -i` of the 500-cell screen took 7.3 and 7.0 ms at p50 from the replica (SwiftUI, Expo), where a read of that screen through the runner takes 450 to 650 ms, a tap's dispatch through dtuhidd 53.3 and 53.4 ms with its 50 ms hold, and `wait --settle` 364.7 ms on SwiftUI and 191.9 ms on Expo (`reports/11.1-ios-device.md`, mobile-agent's primitives, the fixed run).

**What it costs the host and the device.** Over ten login flows and a minute idle on each device, with memory as the physical footprint on the host and PSS in the emulator's guest (`reports/10.20-resources.md`), mobile-agent's processes used 0.35 CPU-s per flow on the Simulator, against agent-device's 2.75 and Maestro's 18.82, and on the emulator 0.28 on the host plus 0.05 in the guest, against 0.62 plus 0.22 and 13.45 plus 1.82. Attached and idle, mobile-agent holds 23 MB on the Simulator, its daemon and the reader, and beside the emulator 17.7 MB on the host and a 69 MB agent in the guest; agent-device keeps an XCTest runner warm, 248 MB in six processes, and on Android 87 MB plus an 84 MB helper instrumentation in the guest; Maestro keeps nothing, starting a JVM and reinstalling its driver for every flow, up to 544 MB at once. Idle is where the replica costs: mobile-agent keeps reading, 0.42 CPU-s per minute on the Simulator with 1.01 more in the app it reads, and on the emulator 0.11 on the host and 0.33 in the guest with 0.75 in the app, where agent-device idles at 0.46 and 0.05 and Maestro at nothing. The device works more under the XCTest and instrumentation drivers: beyond its resting rate, a flow cost the Simulator's own processes about 5.7 CPU-s through mobile-agent, 8.6 through agent-device and 17.4 through Maestro, and the emulator's guest 4.5, 6.4 and 14.9. With an iPhone attached and idle, the daemon took 10.4% of a core and usbmuxd 7.6% while the mirror polled the phone every second, and 4.7% and 7.7% with a still screen polled every 10 s, DVT's screenshot failing then; the phone's own share was not measured, since `xctrace` refused to record with the phone attached (`reports/11.1-ios-device.md`, The idle poll). No baseline's cost on the iPhone was measured.

## 2. Why is it faster?

The spikes and the crates' suites measured each mechanism; the harness measured whole flows. No report attributes a flow's difference to individual mechanisms, so the list says what each mechanism saves where it was measured, not its share of a flow. The host microbenchmarks add what a mechanism costs the host without a device, on one host and through a fake target where a mirror or a daemon is needed (`README.md`, Host costs; section 3).

- **Snapshots from the replica.** A warm `snapshot -i` of a 500-cell screen took 6.1 ms (SwiftUI) and 5.9 ms (Expo) at p50 on the Simulator, and 6.1 ms (Expo) on the emulator's agent path, each through a CLI process of its own (`reports/10.2-simulator.md`; `reports/10.11-agent-path/report.md`). Reading those screens from the device costs 126 to 178 ms on the Simulator (S4; `reports/10.2-simulator.md`, Gates), 349 ms cold for the Compose screen on the emulator (S1), and 0.66 to 0.71 s through XCTest (design D6). On the host, the replica's interactive listing of the SwiftUI 500-cell screen takes 327 µs, and of the React Native one, 1,049 nodes as the emulator reads them, 404 µs; a `snapshot -i` of a fake emulator's 500-cell screen through the daemon's socket, the host's whole path less the CLI process, takes 798 µs, against the 6.1 ms through a CLI process and the 126 to 349 ms of a device read. Each read that keeps the replica current costs the host 97 µs the first time on the SwiftUI screen's 510 nodes, every node converted, hashed and given an identity, and 208 µs when the same read comes again and is matched against the replica unchanged; 193 and 413 µs on the React Native screen (`README.md`, Host costs). On a physical iPhone the replica answered a warm snapshot in 7.0 to 7.3 ms at p50, where a read through the runner takes 450 to 650 ms (`reports/11.1-ios-device.md`, Read costs).
- **No idle waits.** A settle ends 200 ms after the last tree or frame change (design D8): 188 to 191 ms at p50 on the emulator's list screens, 190 ms on the Simulator's Expo list and 436 ms on its SwiftUI list, whose transition frames last longer (`reports/10.1-emulator.md`; `reports/10.2-simulator.md`). The UIAutomator2 server waits for 500 ms without events before every read, up to 10 s (`docs/research/android-agent.md`, section 3), `uiautomator dump` for a second, up to 10 s (section 2), and WebDriverAgent up to 10 s for idle and 2 s for animations (`docs/research/protocol.md`). The settle's own work on the host, a change taken in and the quiet window waited out on a fake clock so that no real waiting counts, is 126 ns with frames, and 152 ns without them on the React Native screen, whose windows send change events. Without frames a window that sends none is read again every 200 ms while the settle waits, and that re-read brings the settle on the SwiftUI screen to 210 µs (`README.md`, Host costs).
- **Input acknowledged in milliseconds.** `InputManagerGlobal.injectInputEvent` with `WAIT_FOR_RESULT` acknowledged a tap in 1.9 ms at p50, where the `UiAutomation` overloads that wait for the app took 35 to 45 ms (S1). The emulator controller's `sendTouch` took 0.96 ms per tap, and the same tap through `adb shell input tap` brought its changed frame 55 ms later at p50 (S7). On the Simulator the touch-down reaches XPC 0.03 ms after the request (S3). On a physical iPhone a tap sent from the host through the disk image's dtuhidd was acknowledged in 53.5 ms at p95, its 50 ms hold included, where the runner's XCTest synthesis took 294 ms and `XCUICoordinate`, the public path, 795 ms (S10; physical-ios design D22).
- **A click that returns with its effect.** `click` replies when the first frame change and tree delta have come, or after 200 ms of quiet, at most 1 s, and reports both spans (`crates/cli/README.md`, Timing spans), so the next step needs no fixed sleep. On the Simulator the frame change comes from the daemon's frame thread, which reads the display at most 30 times a second, downscales each frame to 460x1000 in 1.09 ms and hashes it in 0.10 ms to tell whether it changed, and hashes a changed frame below the status bar for the settle in 0.11 ms; it encodes a JPEG, 0.93 ms, only for a screenshot (`crates/daemon/src/devices/simulator.rs`). S2's pipeline encoded every frame, and its whole thread took 20.9% of a core at 60 fps; the steps of it the suite times, with the JPEG, take 2.24 ms a frame now, 13.4% of a core at that rate (S2, Verdict; `README.md`, Host costs). On the emulator the key that tells the controller's 540x1200 frames apart takes 52.7 µs a frame.
- **No helper process per operation.** The daemon persists between commands, so the one process a command starts is the CLI's own, 4.6 ms at p50 (design D1; `reports/10.2-simulator.md`). The daemon's own adb client made a shell round trip in 5.71 ms against 24.27 ms through the `adb` binary, and listed devices in 0.51 ms against 16.73 ms (design D3). The Simulator reader is spawned once per booted Simulator (design D6), and `open` activates the dtuhidd input session while the app launches, so the first click does not wait for it (`crates/daemon/README.md`, The Simulator driver).
- **Scroll strokes that stop.** Each stroke of `scroll --until` comes to rest before the finger lifts, and the screen settled 192 to 302 ms after one, where a flinging 600-point stroke took 1,027 to 1,260 ms to settle on the emulator and 2.8 to 2.9 s on the Simulator (design D8). The SwiftUI list-scroll flow went from 25.3 s to 16.3 s at p50 when it moved to `scroll --until` (`reports/10.2-simulator.md`, list-scroll after `scroll --until`).
- **A binary device link, a small share.** Encoding a 500-node snapshot on the device and decoding it on the host took 104 µs in CBOR against 990 µs in JSON (S5). Beside a cold tree read of hundreds of milliseconds that saving is small, as the protocol note expected (`docs/research/protocol.md`, Risks). The shipped crate decodes a 500-node snapshot of S5's shape in 124 µs on the host and encodes it in 56 µs, and a 1,049-node one in 240 and 110 µs, under the workspace's release profile; built with S5's fat LTO and one codegen unit, its encode drops to 25.4 µs while its decode stays at 119.6 µs, twice S5's 59.1 µs, which leaves the difference to the shipped node decoder (`README.md`, Host costs).

End to end, the reference flows ran 6.05 to 8.51 times faster than through Maestro on the Simulator and 4.32 to 14.76 times on the emulator, and 1.06 to 2.89 times faster than through agent-device where it completed them there (`README.md`, Measured). On the iPhone these mechanisms did not make the flows faster than WebDriverAgent's but on Expo's big-screen: each of mobile-agent's steps waits for the phone's polled screenshots and a read of 450 to 650 ms, and its list-scroll settles and reads after each of 22 to 25 strokes where WebDriverAgent flings nine times (section 3). On the SwiftUI login flow the medians were 4.2 s for mobile-agent, 8.8 s for agent-device and 25.5 s for Maestro once `fill` read the field back, against 3.8, 8.7 and 25.3 s before (`reports/10.26-remeasure.md`; `reports/10.2-simulator.md`, Baselines). On the emulator's Expo login mobile-agent's median was 1.59 s, against 1.97 s while the read-back held every fill 200 ms and 1.58 s before it read fields back (`reports/10.26-remeasure.md`, 10.30 rerun).

## 3. Is it faster on every axis, and were the benchmarks proper?

Not on every axis. The gates cover mobile-agent's own primitives; the comparison with other tools covers three flows.

**How the harness measures.** `crates/bench` drives the release CLI as an agent does, one `--json` process per command, on the reference fixtures of `fixtures/CONTRACT.md`, with 3 warm-up and 50 measured iterations per series, failure and flake rates, a golden end-state check of every flow through every tool before anything is timed, provenance in every report, and gates judged at p95 on mobile-agent alone (`crates/bench/README.md`). The login, list-scroll and 500-node flows also run through Maestro 2.10.0 on Java 21.0.12 and agent-device 0.21.14 on Node 25.8.0, each timed by wall clock around the tool's process; maestro-runner was not installed and was skipped (`reports/10.1-emulator.md` and `reports/10.2-simulator.md`, Setup). On the physical iPhone the baselines are WebDriverAgent 16.14.1, through Appium 3.8.0 and its XCUITest driver 12.16.0 and timed around its requests, and agent-device 0.21.14, both signed for the team; Maestro is skipped, 2.11.0 refusing physical iPhones (`reports/11.1-ios-device.md`, Setup and Baselines).

**What the host microbenchmarks compare.** `just micro` times mobile-agent's own host-side paths, those section 2 attributes savings to, on this one host and without a device: the codec on generated messages, the mirror on its fixture trees through the scripted fake target, on a fake clock and with a copy of the screen where a driver would decode a read, and the daemon through its socket to a fake emulator, so no driver, adb server or CoreSimulator call enters any number (`crates/bench/README.md`, Microbenchmarks). Each path is compared with its own committed baseline, never with another tool's: none of the baseline tools exposes a host-side step to time apart from a whole command, as none exposes the primitives' spans (`crates/bench/README.md`, Baselines). The inputs are reconstructed at the sizes the reports measured rather than captured: the 500-node snapshot generated in S5's shape, the 1,049-node React Native screen rebuilt from S1's per-window counts and the fixture's source, 10,000 events and 1,000 requests in S5's mix, and a synthetic frame of the Expo Big tab, whose JPEG comes to 84,131 bytes against the 82,219 of S2's. They run under the workspace's release profile, which the shipped daemon, CLI and reader are built with, not under S5's fat LTO and single codegen unit, with which the snapshot's encode takes half the time (`README.md`, Host costs). Each number is the median of criterion's 100 samples, from a run the quiet-host guard let start (`reports/micro/README.md`); what the paths cost on another machine, or what the same work costs in another tool, is not measured.

**Where the comparison stops.**

- Only flows are compared. The baselines run flows alone, "since none of them exposes the primitives' spans" (`crates/bench/README.md`, Baselines), so the harness timed no snapshot, tap, screenshot or text entry against another tool's own command. The one side-by-side reading is the React Native smoke test's, a single pass on a host at load 8 to 240, whose times it calls indicative only: on the Expo 500-cell screen mobile-agent's `snapshot -i` took 231 ms and then 70 ms, agent-device's 842 ms (508 ms of it the read), and the XCTest tree 1,226 ms (`reports/10.4-rn-smoke.md`, Simulator: Expo fixture).
- The warm-snapshot gate measures the replica. No device read enters its span, while a fresh read of the SwiftUI screen costs 126 to 178 ms (`reports/10.2-simulator.md`, Gates; S4). On the iPhone too all 200 warm snapshots of the fixed run came from the replica, while the gate's 1 s limit was set from the runner's 450 to 650 ms read; there the gate table shows the reads beside the replica's answers (`reports/11.1-ios-device.md`, Snapshot reads on physical iPhones).
- On the iPhone the flows are not the same work. mobile-agent's settle and verify after every step, as an agent does: a click waits for its first changed screenshot, then for a read, and list-scroll's `scroll --until` makes 22 to 25 resting strokes, each followed by a settle and a read. WebDriverAgent's fire their requests and check at the end, its list-scroll flinging the list nine times and polling for `row-200`, a flow that took mobile-agent 2.77 and 2.73 times WebDriverAgent's time (`reports/11.1-ios-device.md`, Flows and The flows on the fixed run).
- The baselines' times include their start. Each Maestro iteration starts a Java process and Maestro's driver, an instrumentation on Android and an `xcodebuild` XCTest runner on iOS, which end with it (`crates/bench/README.md`, Hand-offs between tools; `reports/10.2-simulator.md`, finding 2); no report separates that start from the flow. agent-device's own durations for the SwiftUI login, 8.39 to 8.73 s, sit close to its 8.67 s wall-clock median (`reports/10.2-simulator.md`, finding 3). mobile-agent pays a process start per command, about 5 ms (`reports/10.1-emulator.md`, finding 9).
- The baselines ran with their defaults, apart from the 90 s timeout the harness writes into Maestro's `scrollUntilVisible` (`crates/bench/README.md`, Baselines). agent-device's `scroll --until` has a fixed 12-pass budget and failed list-scroll on both platforms, and agent-device failed every Expo flow on the Simulator, so it timed 2 of its 6 Simulator flows; when login was measured again, its Expo check passed and it failed 45 of 50 iterations at its first `fill` (`reports/10.26-remeasure.md`, finding 3). On the emulator neither baseline timed list-scroll, Maestro there still running with its default 20 s scroll timeout (`reports/10.1-emulator.md`, Baselines and finding 6; `reports/10.2-simulator.md`, finding 3).
- One host, one runtime, one image. Every run used one Apple M1 Max under macOS 26.6.2, with an endpoint security extension inspecting process starts, one iOS 26.5 Simulator on Xcode 27.0 and one API 36 userdebug emulator image rendering on the host GPU (`reports/10.1-emulator.md` and `reports/10.2-simulator.md`, Setup). One physical device ran, a Nexus 5X on Android 8.1, with 20 iterations after 2 warm-up and only the login flow through the baselines (`reports/10.3-physical-android.md`). The load was recorded rather than controlled: over the Simulator run the 1-minute load had a median of 5.7 and a maximum of 33.1 (`reports/10.2-simulator.md`, Load). The reports do not record the emulator's GPU mode (`crates/bench/README.md`, Reports). One iPhone ran, an iPhone SE (3rd generation) on iOS 26.6.2, twice: on 2026-10-10 and, after the fixes of its findings 1 to 5 and 7, on 2026-10-11, the run the tables give. ## 4. What are the current limitations, and what is left out?

**Not built.** An in-process agent injected into the Simulator, the MCP server, the CDP-subset endpoint, a local decision-model hook and Android video streaming are deferred to follow-up changes (`openspec/changes/archive/2026-10-07-mobile-automation-foundation/proposal.md`, What Changes); physical iPhones, deferred there too, came with the `physical-ios` change, which leaves out iPhones over Wi-Fi, watchOS, tvOS and visionOS, an in-app SDK, more than one iOS version and a phone in CI (`openspec/changes/archive/2026-10-14-physical-ios/proposal.md`, What Changes). Integration as an agent-browser provider is a non-goal of the foundation change and an open question (design, Goals / Non-Goals and Open Questions). tvOS, HarmonyOS, web and desktop are out of scope, as is React Native specific inspection: React Native apps are read through the platform's accessibility layer only (design, Goals / Non-Goals).

**Not run, or not measured.**

- One physical Android device has been measured, a Nexus 5X on Android 8.1, where the agent needed three platform reads gated on their level before it could start (`reports/10.3-physical-android.md`). A device has no frame stream, so `click` reports no `frameChangeMs` there and settle rests on the tree (`README.md`, Status and limitations).
- One physical iPhone has been measured, an iPhone SE (3rd generation) on iOS 26.6.2 under Xcode 27.0 (`reports/11.1-ios-device.md`). iOS 27's path, where dtuhidd takes the host's input only while a display stream runs, the stream that would also give frames, waits for a phone that runs it; AVFoundation's capture of the phone waits on the macOS camera permission; the developer disk image's mount was never exercised, since the image stayed mounted; and no app but the fixtures has run on the phone (physical-ios design, Open Questions, and task 2.5). maestro-runner's device path, which its documentation gives with `--team-id`, is unverified, since it was not installed (`crates/bench/README.md`, Baselines).
- OEM Android builds, and whether Android 17 lets adbd connect to the agent's socket (design D3). The instrumentation fallback for a build that refuses the shell path is a follow-up, not built (design, Risks / Trade-offs).
- Any Xcode but 27.0 and any iOS runtime but 26.5 (design, Spike verdicts). Xcode 26 is in the supported range and CI builds with it, but nothing has run there, and its input would be touch only, through Indigo (`crates/simulator/README.md`, Compatibility).
- Direct USB for adb, deferred (design D3), and web content, since no fixture has a web view (S4, Fidelity).
- XCTest's root without useful children, which agent-device's ADR 0004 reports on Bluesky. Signed in to Bluesky, agent-device's XCTest tree came back `sparse` or timed out on 8 of 52 reads, on the search screen with the keyboard up and a 711-node thread, and mobile-agent's snapshots of those screens were whole and not degraded, so the claim that they stay whole where XCTest's go sparse held; but those failures were the runner's 1 s budget running out, and no read returned such a root (`reports/10.4-rn-smoke.md`, Verdict).
- The fixes for what a smoke test of a production React Native app found on an iOS 26 Simulator on 2026-10-09 were rerun on that app on 2026-10-12 and not accepted (`openspec/changes/rn-app-fixes/tasks.md`, task 2.2); the fixes for what the rerun found are verified on synthetic fixtures of its screens' structure and on the daemon's fake targets, and their own rerun is open (task 3.7). The wait for the keyboard before the first key typed into a field `fill` just focused on iOS answers keys lost while the keyboard slid in, in 3 of 8 runs there; on the SwiftUI fixture fresh-focus fills read back whole with the wait and without it, so the fixture does not show the loss (task 1.4).

**Constraints the design accepts.**

- One UI automation owner per Android device: while the daemon holds a device, Maestro, Appium and `uiautomator dump` cannot run against it, and `--force` takes the role over (`README.md`, Agent guide).
- Private Apple frameworks and hidden Android APIs, confined to `crates/simulator` and `agent-android` (design D12). The driver refuses an Xcode outside 26.0 up to 28 with `unsupported_xcode` (`crates/simulator/README.md`, Compatibility); a hidden Android member the agent cannot find costs its capability rather than the attach (`agent-android/README.md`, Serving the protocol). On the iPhone, private XCTest calls are confined to the runner, `agent-ios`, beside the developer services `crates/ios` reaches through `idevice`; each call site is listed with the iOS and Xcode it was validated on, and a phone outside iOS 17.4 up to 27 is refused with `unsupported_ios` (`crates/ios/README.md`, Compatibility).
- Jetpack Compose sends UI automation no accessibility events, so Compose windows are re-read after each action and on a 1 s poll, and a cold read of a wide list costs about one round trip per child beyond the 49th: 465 round trips and 349 ms for the 500-cell screen (design D5; S1).
- Frames exist on Simulators, on emulators whose controller answers and, as screenshots the driver polls 14 to 19 times a second, on a physical iPhone, which has no frame stream on iOS 26 (physical-ios design D23); elsewhere screenshots are taken on demand (design D7).
- A physical iPhone needs its maintainer: a paid team's signing for the runner, Developer Mode, trust, an unlock, and the passcode for "Enable UI Automation" at a runner's start, which XCTest waits 60 s for before the driver reports `automation_not_enabled`. It has one automation session, so mobile-agent's runner and another tool's take turns, and the daemon registers its driver only when `MOBILE_AGENT_DRIVERS` names `ios`, since the listing checks the signing identity and probes each phone through lockdown, which a phone that does not answer holds for 10 s (`README.md`, Quick start; physical-ios design D20 and D25).
- What the iPhone's tree does not tell: a view an app marks modal, other than an alert, since testmanagerd's reply carries no children count by which a read that pruned it could tell, and a second read would double a 450 to 650 ms read; and a row a floating tab bar covers, which XCTest leaves out, as it did the SE's `row-12` (physical-ios design, Open Questions; `reports/11.1-ios-device.md`, finding 6). An idle iPhone's still screen is read again every 10 s, about 5% of the runner's time, and the first snapshot after a relaunch waits for a read the daemon begins as `open` returns, about 670 ms on SwiftUI and 450 ms on Expo; whether `open` should take that read before it returns is open (physical-ios design, Open Questions).
- The phone's own developer services can fail. On the fixed run's day DVT's screenshot stopped answering and testmanagerd stalled the runner on the 43rd emptying text set of every session, until a reboot, and later DVT refused its process-control channel for about 1 h 30 min. A runner that stops answering is started again once, and a screenshot connection that stops answering is reopened, then left out and named in `status`; but a phone whose DVT refuses that channel cannot be driven, since `open` launches through it, and CoreDevice's app service as the launch's fallback is an open question (`reports/11.1-ios-device.md`, finding 11; physical-ios design D26 and Open Questions).
- On the Simulator, text over 32 characters, or with a character no key types, is pasted, replacing the device's pasteboard, which `fill` reports as `method: direct`, and before the first paste the driver grants every user application on the device the "Paste from Other Apps" setting (`crates/simulator/README.md`, Text). On a Simulator whose first boot did not come from the driver, the first tree reads can fail for several seconds (`README.md`, Status and limitations). S3 once saw a Simulator display stop presenting while input was still accepted, cleared by a reboot (S3, An unexplained freeze).
- A Linux host drives Android only (`README.md`, Supported platforms).
- Degraded reads are reported, not hidden: the host translator, the Simulator's fallback when the reader cannot run, flattens the tree and drops the tab bar's children and React Native text identifiers, and identical siblings are flagged `sibling_collision` (design D6; `crates/mirror/README.md`, Snapshots).
- Neither platform reports what covers a view inside a window, so the mirror infers it. The listing leaves out what a modal covers and what a view drawn over its siblings covers: on Android the agent tells such a view from the order a parent draws its children in, and on iOS the mirror takes XCTest's order for UIKit's drawing order, so a fixed footer, a floating button or a sticky header listed after the content cuts what it spans, a disabled control counting as one that shows, and a bar, or a header pinned across a list's top, cuts what it spans whatever the order. A transparent view drawn over others hides what it spans as if it showed, and a read from the host translator lists what such views cover (`crates/mirror/README.md`, Snapshots; `openspec/changes/rn-app-fixes/design.md`, D31 and D38). A tap goes to the centre of the largest part of an element that no such view covers, at least 8 points on each side, and warns when that part is not most of it (D37); `click` refuses an element with less left with `element_covered`, naming the cover as the listing's line counting the element does, the header or the footer of its list or what a tap at its centre would land on (D57), and makes no stroke: an element nothing of which a tap reaches is in view after the windows are read again fails with `element_offscreen`, and `scroll --until` brings it in (`crates/daemon/README.md`, Tap spans and settle signals). The keyboard covers too, by the bounds its window reports: what lies wholly under it is left out of `snapshot -i` and counted in a line that names it, what lies partly under it says `visible=`, and with it up a scroll strokes inside what shows of the list, or fails `covered_by_keyboard` where less than 120 points show (D38, D41). What a tap reaches is clipped too by what each list around the element shows, and `snapshot -i` leaves out what a tap reaches none of, counted in its list's line, and marks what it reaches part of, whatever covers the rest (D45); `snapshot` marks the same and keeps what a tap reaches none of at `visible=0%`, a view covering it whole or not, and the line names what covers what it counts, as `3 of them behind the header` (D50), a view listed before a list across its top being its header whatever it holds, each listing's lines counting only what it leaves out, so the two agree by construction (D54, D57). A keyboard window that draws no keys, as with a Simulator's hardware keyboard connected, covers nothing and counts as no keyboard, the waits for a keyboard taking the field's focus instead (D52), and once one has been seen the waits end at the focus, a number pad bringing up no window at all (D57); iOS's edit menu, in a window across the screen, covers only the strip it draws on, and `fill` closes the one its lost paste leaves up (D55); and a selector names any element the tree holds, so that an action on a covered one is refused at once as on its ref (D53). React Native's accessibility lists a view that draws something, as a footer's background, as a node holding nothing, what the view lays out beside it, and such a node covers what it lies over of a list listed before it (D48); a stroke that brings an element in aims at a side its list can carry it to, and a scroll that stops names its last stroke (D46). The other tabs of a React Native tab bar, which carry no trait, are told by the selected one's row (D40).
- `fill` verifies only what the tree shows of a field: its value, or for a field without one what lies inside it, as a React Native code field keeps its digits in boxes (`readFrom: descendants`), or else the part of its name the entry changed, separators left out, as such a field spells its digits in its name on iOS (`readFrom: name`, D43); the value of a field that is not a text field counts only when it changed with the entry and is no placeholder, a box's dash or a digit shorter than the entry (D56). A field that shows none of these, as iOS reads a React Native field inside a view marked accessible, cannot be read back: the fill succeeds with `verified: false`, `reason: no_value_to_read` and a warning, and `text_mismatch` is left for a field that shows other text after the text went in again (`crates/daemon/README.md`, Protocol; `openspec/changes/rn-app-fixes/design.md`, D33 and D39). An identifier on a view that takes no text but holds one field fills that field, one on such a view holding no field taps it and enters the text where the keyboard it brings up types (D44), and a field keeps its ref when only its name changes in place (D39).

**Open items and differences.** No task of the foundation change is open: 10.3, the harness on a physical Android device, ran on a Nexus 5X with Android 8.1, and its findings are in `reports/10.3-physical-android.md` (`openspec/changes/archive/2026-10-07-mobile-automation-foundation/tasks.md`). They include a cold attach over its gate on that phone, a `scroll` stroke that starts over the keyboard and types into the focused field, and commands waiting behind reads on Compose's 500-cell screen where Android 8.1's node cache is one for the whole process. ## 5. Does it support native iOS, Android and React Native, and which versions?

**Platforms.** Android devices and emulators, through the resident agent, with the emulator's gRPC controller carrying taps, swipes and frames when it answers (`--emulator-controller off` sends them through the agent, as on a device); iOS Simulators, through the host-side driver; and physical iPhones on USB, through a resident XCTest runner for the tree and text and the disk image's dtuhidd, from the host, for input, signed for a paid team and driven only when `MOBILE_AGENT_DRIVERS` names `ios` (`README.md`, Supported platforms; physical-ios design D20 to D22). The daemon runs on macOS for all three, and on Linux for Android only.

**App technologies.** The tree comes from each platform's accessibility layer, so what is read is what a toolkit exposes there. The record covers:

- Android Views: Settings on the API 36 emulator (`README.md`, Quick start; S1).
- Jetpack Compose: the Compose fixture. Compose sends no accessibility events to UI automation (S1, from Compose UI 1.11.4's bytecode), so the agent marks its windows, dialogs included, by the `androidx.compose.ui.semantics.id` extra data and the mirror re-reads them (design D5).
- React Native on both platforms: the Expo fixture on both, and its Release build on the iPhone SE (`reports/11.1-ios-device.md`); Bluesky 1.133.0's release APK on 4 logged-out and 11 signed-in emulator screens, and its Simulator build on the 9 screens the logged-out app reaches and 13 behind sign-in; Ignite 11.5's demo app on 5 Simulator screens. mobile-agent never reported a sparse tree there, including the screens where agent-device's XCTest tree came back `sparse` or timed out (`reports/10.4-rn-smoke.md`). Two of the mirror's listing rules come from those apps: a field without a label takes its container's, and a labelled leaf container gets a ref (design D5).
- SwiftUI: the SwiftUI fixture, on the Simulator and the iPhone SE. SwiftUI attaches identifiers up to a second after launch on iOS 26.5, so the mirror treats the first tree after a launch as provisional (design D5); on the iPhone a read soon after a launch listed the fixture's rows before its tab bar's identifiers (physical-ios task 9.9).
- UIKit: Settings (`README.md`, Quick start) and Contacts' New Contact sheet in the driver's tests (`crates/simulator/README.md`, Tests).

## 6. Which protocol did we settle on?

Two protocols, one on each side of the daemon.

**The device link is CBOR, protocol version 1** (design D4; `crates/protocol/README.md`). It joins the daemon to the Android agent, to the Simulator's tree reader, which speaks the same protocol over a Unix socket as an agent with the `tree` capability (`crates/simulator/README.md`, Tree), and to the iPhone's runner, reached through usbmuxd's `Connect` to its port on the phone, with the `tree`, `input`, `screenshot` and `text_set` capabilities (`agent-ios/README.md`, How it runs).

- Framing: a 32-bit big-endian payload length, then one CBOR item (RFC 8949) in preferred serialization with definite lengths only. Messages, parameters, results, snapshots and nodes are maps keyed by field index, events are positional arrays, and there are no floats and no tags. The default frame limit is 16 MiB, never below 4 KiB, and an oversized frame is refused naming the limit and the request.
- Handshake: the agent speaks first, with a hello carrying its versions, a capability bitmask, its frame limit, its name and the per-launch token; the host selects the highest common version and the smaller limit and answers with a welcome, or with an error listing both version sets. The capabilities are tree reads, input, screenshots, frames, events, text setting and bounds probes, and a request that needs one the agent did not advertise is refused on both sides.
- Requests carry an id, a method and an optional relative deadline, and may complete in any order. The methods are `snapshot`, `screenshot`, `tap`, `swipe`, `key`, `text_set`, `frames_start`, `frames_stop`, `resync`, `shutdown` and `bounds`. A snapshot request takes `max_depth`, `max_nodes`, `idle_ms` (a bounded wait for the screen to go idle), `evict_event_less` (evict the cache of windows that send no events) and `evict` (windows by id); a snapshot carries a string table for class names and resource-id prefixes, window metadata (`emits_events`, `owner`, `modal`), window flags such as `transformed`, and per-node scroll semantics.
- Events travel on four streams: tree changes, window changes and lifecycle, which are lossless and resynchronized on a sequence gap, and frames, which are lossy. Errors carry a code, a message and a retryable flag. A session pings after a second of silence and closes after three.
- The host decodes with minicbor's derive; the agent's Kotlin codec is written by hand, 1,549 lines with no dependency (design D4), and writes the same bytes: 41 golden samples are checked in both directions by `cargo test -p protocol` and `agent-android/codec-test.sh` (`crates/protocol/README.md`, Golden frames and the Kotlin codec).

**Why CBOR.** Spike S5 encoded the same logical fields as compact JSON with readable keys, CBOR, MessagePack and protobuf, with Kotlin on the API 36 emulator and Rust on the host. JSON was larger than CBOR by 2.49x on a 500-node snapshot, 3.43x on 10,000 events and 2.85x on 1,000 requests (MessagePack 2.53x, 3.49x and 2.88x; protobuf 2.65x, 3.37x and 3.45x). From device to host, CBOR was 9.5 times faster than the faster platform JSON on the snapshot (104 against 990 µs) and 15.9 times on the events (MessagePack 9.0 and 21.7 times, protobuf 7.6 and 13.5). Each codec added 5.2 to 6.3 KB to the shrunk dex, CBOR the least. No format met the stated criterion, three times smaller and faster than JSON on both the snapshot and the events, because none is three times smaller on the snapshot, so CBOR was chosen on time, dex size, evolution and debuggability: it is self-describing, as the device-protocol spec requires and protobuf is not; minicbor derives the integer-keyed layout and decodes 2.2 to 3.2 times faster than ciborium; and frames print in RFC 8949's diagnostic notation (S5, Verdict; design D4). FlatBuffers was not measured, since `flatc` has no install path through Socket Firewall.

**The client link is JSON.** The CLI and the daemon exchange agent-browser's newline-delimited JSON over a Unix socket, one reply per request (`crates/daemon/README.md`, Protocol); the protocol note kept binary encoding for the device link only (`docs/research/protocol.md`, What we take).

**How the host reaches each platform.**

- Android: the daemon's own client for the adb server protocol on port 5037, with no `adb` binary in the hot path. It opens the agent's abstract socket as a device service after `host:transport:<serial>`, so no forward rule or host port exists, and a missing agent fails the open with `closed`; the agent speaks first, checks the per-launch token and refuses a peer whose uid is not 2000. The service stream with its hello took 2.52 ms at p50, and a 64-byte echo 1.5 to 1.7 ms (design D3).
- Android emulator: the emulator's gRPC `EmulatorController`, through a client generated from the proto the installed emulator ships, found through its discovery file and called with its bearer token over two HTTP/2 connections, one for input. It carries taps, swipes and a 540-pixel-wide RGB888 frame stream; keys and text stay with the agent, since the controller drops keys on an AVD without a keyboard (design D7; `crates/android/README.md`, Emulator controller client). Emulator 37.1.11 served the controller even when started without `-grpc`, where S7's fresh AVD started with `-port` served none, and only `-ports` left it off; `--emulator-controller off` exists to take the agent's path on such an emulator (`reports/10.1-emulator.md`, finding 10).
- iOS Simulator: CoreSimulator, SimulatorKit and CoreSimDeviceIO loaded with `dlopen` and driven through objc2, each private call inside an exception guard. Input goes to dtuhidd's XPC service, reached through `-[SimDevice lookup:error:]` and the private `_4sim` libxpc functions, on one connection per target; frames come from the display's IOSurface through its SimScreen callbacks; the tree reader is spawned with `-[SimDevice spawnWithPath:...]` and connects back to the daemon (design D6; `crates/simulator/README.md`).
- Physical iPhone: the `idevice` crate in the daemon's process, with no `devicectl`, helper process or root. It lists the phone through usbmuxd, opens lockdown with the host's pairing record, and opens the CoreDevice tunnel through lockdown's `CoreDeviceProxy` with an in-process TCP stack and no TUN interface, 60 ms at p50 with RSD's handshake; over it go DVT's process control and screenshots, CoreDevice's screen capture, dtuhidd's HID services for input and the test manager's XCTest session that starts the runner. The runner's socket goes through usbmuxd's `Connect` instead of the tunnel, whose TCP stack sends one segment at a time (physical-ios design D18 to D22; `crates/ios/README.md`).

## 7. How easy is it to add agent surfaces such as the CLI or MCP?

**The CLI exists.** `mobile-agent` follows agent-browser's grammar, ref syntax and JSON output where devices have the same concepts (design D9). `snapshot -i` lists actionable elements with `@eN` refs, which stay attached to their element while it is on screen and fail with `stale_ref` once it goes; `--json` prints `{success, data, error}`, with `code` and `warning` when set, and every failure carries a snake_case code; `batch` runs quoted commands, or a JSON array of argv arrays on stdin, with `--bail`; `--session` keeps target claims, refs, diff baselines and default timeouts apart inside one daemon; `snapshot --delta` returns agent-browser's delta object; and `help agent` prints a guide for an agent's prompt (`crates/cli/src/agent-guide.txt`), which the agent-cli spec keeps under 120 lines (`README.md`, Agent guide; `crates/cli/README.md`). Where it departs from agent-browser is listed in `crates/cli/README.md`, Differences from agent-browser.

**The daemon's socket is the integration point.** Another front end does what the CLI does: it connects to `daemon.sock` in the socket directory, writes one JSON object per line (`{"id", "action", "session", ...}`) and reads one reply per request in the same envelope. The 18 actions, from `status` to `shutdown`, with their parameters and reply data, are listed in `crates/daemon/README.md`, Protocol. The CLI links nothing of the daemon: socket discovery, starting the daemon, the version check, retries and the reply wait live in `crates/cli/src/client.rs`, and the mapping from a command to a request in `crates/cli/src/request.rs` (`crates/cli/README.md`, Layout). The daemon runs commands for different targets concurrently (`crates/daemon/README.md`).

**What the design says.** Its goal is to keep every backend swappable behind the protocol "so later changes can add physical iOS, an in-process agent, and CDP or MCP edges without touching the mirror or the CLI" (design, Goals / Non-Goals). The MCP server and the CDP-subset endpoint are non-goals of this change, deferred to follow-ups (`openspec/changes/archive/2026-10-07-mobile-automation-foundation/proposal.md`, What Changes) and not built (`README.md`, Status and limitations). Whether the CLI becomes an agent-browser provider is an open question, with "the daemon API is the integration point either way" (design, Open Questions). The repository describes no shape for either edge beyond that. The protocol note records how agent-browser adds MCP: `agent-browser mcp` is a stdio JSON-RPC server whose tool calls run the same binary with `--json`, so the CLI's JSON output is its MCP contract; the note asked for a `--json` output stable enough to serve that way, and for a published output schema, which agent-browser lacks (`docs/research/protocol.md`, agent-browser and What we take).

**What an MCP server would need**, assessed from the modules above:

- Tools: one per daemon action, its arguments the action's parameters, its result the reply's `data`, and a failure's `code` and message as the error. Refs are valid only for the session whose snapshots listed them, and the daemon already keys claims, refs, diff baselines and timeouts by session name (`crates/daemon/README.md`, Sessions and claims), so an MCP connection can hold one session name and pass it with every request. Reads without side effects, such as `devices`, `status` or `doctor`, could be offered as resources; `snapshot` belongs with the tools, since it issues the refs later calls use and sets the session's diff and delta baselines.
- What helps: one envelope for every action, a code on every failure, and messages that say what to do next (`stale_ref` says to take a new snapshot); delta snapshots, whose `unchanged` and `delta` kinds keep repeated listings short; `click` replies that report the tap's spans and settle replies that name the signal they ended on, so a model learns what happened without another call; sessions and claims, which already separate concurrent clients.
- What gets in the way:
  - No schema to generate tool definitions from. The repository has no JSON Schema for the daemon's requests or replies (its one schema file, `crates/protocol/tests/schema.rs`, tests the CBOR messages), and `data.snapshot` is text or an object depending on `delta`.
  - Nothing is pushed to clients. The socket answers one reply per request (`crates/daemon/README.md`, Protocol), and the sequenced event streams exist only between the device agents and the daemon (`crates/protocol/README.md`, Events and streams). An edge that should tell its client the screen changed has to poll, `snapshot --delta` being the cheap way, or needs a daemon action that waits for a change.
  - `screenshot` writes a JPEG to a path and replies with its metadata (`crates/daemon/README.md`, Protocol), so an edge that returns the image reads the file.
  - Long calls and warnings. Waits run to their timeout, at most 600,000 ms, and the CLI awaits a reply for the command's timeout plus 10 s, at least 30 s (`crates/cli/README.md`, Daemon lifecycle); an edge needs the same rule, and has to pass `warning` on, since it marks a success not to take at face value (`README.md`, Agent guide).
- Effort, in modules:
  - A request-and-reply MCP edge is a new front end beside `crates/cli`, or a subcommand of it: a stdio JSON-RPC loop, a table of the 18 actions with hand-written input schemas, the envelope mapped to results and errors, and one session per connection, reusing `client.rs` and `request.rs`. Nothing in `crates/daemon`, `crates/mirror`, `crates/protocol` or the drivers changes for it. Running `mobile-agent --json` per tool call, as agent-browser does, needs less still, at a process start of about 5 ms per call (`reports/10.1-emulator.md`, finding 9).
  - Change notifications are the larger piece: an action in `crates/daemon/src/handlers` that waits in the target's worker (`crates/daemon/src/worker.rs`) until the replica's revision or its frames change, built on what the mirror exposes (`run_until`, `next_wakeup`, `timestamps()` and the revision; `crates/mirror/README.md`), or a subscription channel on a socket that carries one reply per request (`crates/daemon/src/server.rs`).
  - Returning a screenshot's bytes is a change to the `screenshot` handler (`crates/daemon/src/handlers/view.rs`), and a published schema for requests and replies would serve the CLI, the harness and an MCP edge alike.

**The CDP-subset endpoint.** The repository records its deferral and nothing of its shape.
