# bench

The benchmark harness of design decision D10 and the `benchmark-harness` spec. It measures the spec's primitives through adapters, one per tool, writes a JSON report and a markdown summary from the same data, judges the latency gates, and runs the same flows through Maestro, maestro-runner and agent-device, and on a physical iPhone through WebDriverAgent with Appium's XCUITest driver, for comparison.

The binary is `mobile-agent-bench`; `just bench <arguments>` runs it in release mode. Its `run` measures `mobile-agent` through the CLI adapter on the targets `--target` names, or, with `--fake`, the scripted fake adapter described below, by the full plan of a measured host or the reduced plan of a CI runner (see "The CI plan and the ratios"). Its `micro`, which `just micro <arguments>` runs, times the host-side paths without a device and compares them with a committed baseline, or, with `--ab <ref>`, which `just bench-ab <ref>` runs, with another ref built and run on the same host (see "Microbenchmarks"). Its `trend` sets a report beside the previous scheduled run's in CI (see "Against the previous scheduled run").

```sh
cargo build --release -p cli -p daemon -p bench       # mobile-agent, its daemon and the bench, side by side
target/release/mobile-agent-bench run --target emulator-5554 --out reports/emulator
target/release/mobile-agent-bench run --target <UDID> --cli target/release/mobile-agent --out reports/simulator
target/release/mobile-agent-bench run --target emulator-5554 --flow list-scroll --no-baselines --out reports/list-scroll
target/release/mobile-agent-bench run --target emulator-5554 --primitive text-entry --flow login --out reports/text-entry
MOBILE_AGENT_DRIVERS=ios target/release/mobile-agent-bench run --target <iPhone's UDID> --auto-lock-off \
  --ios-app swiftui=fixtures/swiftui/build/Build/Products/Debug-iphoneos/FixtureSwiftUI.app --out reports/iphone
just bench run --fake run.json --out reports/my-run   # the scripted fake as the tool under test
just bench gates reports/my-run/report.json           # judge an existing report again
just bench gates --gates gates.json reports/my-run/report.json
just bench default-gates > gates.json                 # the spec's defaults, as a gate file
just bench baselines                                  # which baseline tools are on PATH, Appium's WebDriverAgent included
just micro --wait 60                                  # the host microbenchmarks against reports/micro/baseline.json
just bench-ab main --wait 60                          # the same suites of the checkout against main's, both built here
target/release/mobile-agent-bench run --plan ci --gates none --target <UDID> --out target/bench/ci   # a runner's plan, judged by its ratios
just bench trend previous/report.json report.json     # a report beside the previous scheduled run's
```

`run --target <id>` measures `mobile-agent` (`--tool mobile-agent`, the only tool under test there is) on the target `mobile-agent devices` lists with that id, a Simulator's UDID, an adb serial or a physical iPhone's identifier; `--target` repeats for several targets. `--cli <path>` names the `mobile-agent` to drive, by default the one beside `mobile-agent-bench`, where a build of the workspace puts it, else `mobile-agent` on `PATH`; it starts its daemon as usual, with the environment the bench runs in. CLI process start times that executable's process, so `--cli` names `mobile-agent` itself, not a wrapper, whose own start the span would include. Each target runs the fixtures of its platform, SwiftUI and Expo on a Simulator or an iPhone and Expo and Compose on Android, under their bundle identifiers and package names `dev.mobileagent.fixture.swiftui`, `.expo` and `.compose`; `--fixture swiftui|expo|compose`, repeatable, runs the named ones instead. The run's series are `plan::series` for each target and its fixtures, and its flows the fixtures' reference flows: the golden checks run first, then the timed series, each through `mobile-agent` and then, unless `--no-baselines`, the baselines, and between one tool and the next the harness hands the target over (see "Hand-offs between tools"). `--flow login|list-scroll|big-screen`, repeatable, keeps only the named flows' series, so a run measures one flow again on each target's fixtures, after its golden check, without the primitives. `--primitive <id>`, repeatable, with an id of the table below, keeps only the named primitives' series in the same way, beside the flows `--flow` names when both are given (`plan::only`): `--primitive text-entry --flow login` measures text entry and times the login flow on each fixture, the series that fill a field. `run` refuses, with exit status 2 and before anything runs, a target `mobile-agent devices` does not list (naming the ones it lists), a fixture a target's platform lacks and a `--cli` that is not an executable. `--fake <script>` replaces `--target`, `--fixture`, `--flow`, `--primitive` and `--cli`: the script's tool, targets, series and flows make up the run.

`run` also takes `--plan full|ci` (default `full`), `--iterations` (default 50, or 10 with `--plan ci`), `--warmup` (default 3, or 2 with `--plan ci`), `--retries` (default 1), `--gates <file>`, or `--gates none` to judge no gate, and `--no-baselines`, and for a physical iPhone `--ios-app` and `--auto-lock-off` (see "Physical iPhones"); without `--out` it writes to `target/bench/<UTC start time>/`, and the CLI adapter's screenshots go to `cli/` and the baselines' flow files to `flows/` inside it. It prints where the reports went and the gate table, or with `--gates none` the ratio table and the line `No gate judged (--gates none).` Exit status: 0 when every gate passed or none was judged, 1 when any failed, 2 when the harness itself could not run.

## Physical iPhones

A physical iPhone on USB is a target of the `ios-device` class, which `mobile-agent devices` lists once the daemon registers its `ios` driver: the bench passes its environment to every command, so the run needs `MOBILE_AGENT_DRIVERS=ios`, with `MOBILE_AGENT_IOS_TEAM` for the readiness the driver checks. The phone runs the iOS fixtures and the Simulator's series, and the class has gates of its own (see "Gates"). The phone should be as design.md's Delivery process asks for a measured run: plugged in, unlocked, Auto-Lock off and the battery above half, the runner already installed.

- **Fixtures.** The harness installs no fixture on other classes, whose fixtures are installed beforehand. On an iPhone `--ios-app <fixture>=<path>`, repeatable, installs a fixture's device build (`DESTINATION=device fixtures/<fixture>/build.sh` prints its path) on every iPhone of the run before anything runs, through CoreDevice: `xcrun devicectl device install app --device <id> --json-output - <path>`, timed from the process's start to its exit. The app CoreDevice reports installed must be the fixture's (`dev.mobileagent.fixture.swiftui` or `.expo`). A fixture without an iPhone build, a path that is not a directory, a run without an `ios-device` target, a failed install (with CoreDevice's reasons, such as `Failed to install the app on the device.: The device is locked.`) and another app's bundle are refused with exit status 2 before anything is measured. The install goes through CoreDevice rather than through `mobile-agent`'s driver on purpose: the harness stays independent of the tool under test and opens no second tunnel to the phone. On the iPhone SE (3rd generation), CoreDevice installed the SwiftUI fixture's 664 KB build in 1.5 to 2.2 s and the Expo fixture's 28 MB build in 2.1 to 3.4 s. Give the path relative to the checkout: the report records it as given.
- **Provenance.** `devices` gives the model (`iPhone14,6`) and the iOS version. Once the daemon has attached the phone, its `status` gives the runner the driver started (`mobile-agent-ios-runner 0.2.0`), the input path (`dtuhidd`), the frame path (`screenshots`) and the battery: its charge, whether it charges and whether it is on external power, which the driver reads from lockdown's `com.apple.mobile.battery` domain when it attaches, since `devicectl device info details` reports no battery. The report keeps the battery as `status` first gave it in the run. No tool reads Auto-Lock, so `--auto-lock-off` states it for every iPhone of the run, and the report records it as stated, `auto_lock_off: true`, or leaves it out.
- **Tap to frame change** is measured, from the click's `frameChangeMs` on the frames the phone gives, polled screenshots at up to 19 a second, and its gate reports it with no verdict.
- **Baselines.** Maestro is skipped on a run whose targets are all iPhones, with the note `Maestro runs iOS flows on Simulators only; 2.11.0 refuses physical iPhones, its iOS device driver unfinished`, and never runs on an iPhone in a run that has other targets; maestro-runner gets `--team-id` with the team (see "Baselines"); agent-device and WebDriverAgent run there with the team's signing, each releasing its runner app before another tool drives the phone (see "Hand-offs between tools"). Their runners are signed manually with the team's profile under the team's App ID `dev.mobileagent.*`, which registers nothing with the account: `MOBILE_AGENT_IOS_TEAM`, and the identity and profile `MOBILE_AGENT_IOS_IDENTITY` and `MOBILE_AGENT_IOS_PROFILE` name, `Apple Development` and `mobile-agent development` by default, as for `mobile-agent`'s runner and the fixtures.

## The CI plan and the ratios

`run --plan ci` is the reduced plan of a CI runner (design D4 of `ci-benchmarks`): one fixture per target's platform, SwiftUI on a Simulator or an iPhone and Compose on Android, with the series `plan::series` lists for it, CLI process start, every other primitive in its scenario and the three reference flows, at 10 measured iterations after 2 warm-up unless `--iterations` or `--warmup` names others (`plan::Plan`). It refuses `--fixture`, with exit status 2, since the plan picks the fixtures; `--flow` and `--primitive` keep only their series, as in the full plan.

On a shared runner the gates' limits would judge another machine than the maintainer's measured hosts they were set on, so a runner's run takes `--gates none`, which judges no gate: the report's `gates` stays null, the markdown has no gate table, the run prints `No gate judged (--gates none).` and exits 0 unless the harness could not run. `gates <report.json>` can still judge such a report afterwards. What judges it instead are its ratios, which every run with baselines reports (`ratio::of`): per flow, target and fixture, how many times faster the tool under test's p50 was than each baseline's in the same run, the baseline's p50 over the tool's rounded half up to a hundredth, under 1 when the baseline was faster, the factor the top-level README's tables give. A baseline that did not time the flow, because its golden check failed, or that has no samples gets no ratio and a note saying why; the baselines the run skipped are listed with their reasons, WebDriverAgent on a run without a physical iPhone among them. With `--gates none` the run prints the ratio table where it would print the gate table; the markdown has it as `Ratios`, after the comparison table, whether or not gates were judged.

`.github/workflows/benchmarks.yml` runs the plan on a Simulator and on an emulator on a schedule or on demand (top-level `README.md`, How measurements are made).

## What is measured

A run is a list of series. A series is one subject, a primitive or a flow, on one target, in a scenario (a fixture app and one of its screens), and every tool that supports it measures it: first the warm-up iterations, then the measured ones. A failed attempt is retried within its iteration up to `--retries` times.

| Primitive | Spec wording | Scenario (`plan::scenario`) |
|---|---|---|
| `cli-start` | CLI process start | none |
| `cold-attach` | cold attach | a fixture, no screen |
| `first-snapshot` | first snapshot after application launch | a fixture's `big` screen |
| `warm-snapshot` | warm snapshot | a fixture's `big` screen, the spec's reference screen |
| `tap-dispatch` | tap dispatch, the Simulator gate's span | a fixture's `list` screen |
| `tap-to-frame-change` | tap-to-frame-change | a fixture's `list` screen |
| `tap-to-tree-delta` | tap-to-tree-delta | a fixture's `list` screen |
| `text-entry` | text entry of a fixed string | a fixture's `login` screen; the string is `TEXT_ENTRY`, `abcdefghijklmnopqrstuvwxyz0123456789` |
| `screenshot` | screenshot | a fixture's `big` screen |
| `settle` | settle detection | a fixture's `list` screen |

The spec lists nine primitives; `tap-dispatch` is the tenth because the Simulator gate is on dispatch, as spike S3 recommended. The scenario column is the run plan's: `plan::series(target, fixtures)` lists a target's series, CLI process start once, then for each fixture every other primitive in its scenario and the three reference flows, and `plan::fixtures(platform)` the fixtures a platform has. The harness itself takes any scenario a series names, and the default gates look for warm snapshots on the `big` screen. Fixtures and screens are those of `fixtures/CONTRACT.md`: `swiftui` (iOS), `expo` (both platforms) and `compose` (Android); `login`, `list`, `big`, `anim` and `system`.

Statistics follow the spikes: nearest-rank percentiles, so every reported value is a measured sample, over whole microseconds, with warm-up iterations excluded. Each series reports `n`, p50, p95 and max, the node counts the tool returned, a failure rate and a flake rate. An iteration whose first attempt succeeds passes; one that succeeds only on a retry is a flake, and its latency is the successful attempt's; one in which no attempt succeeds is a failure. Rates are percentages of the measured iterations, rounded half up to a tenth. A series whose preparation failed counts every measured iteration as failed. A series the tool cannot measure at all, which its adapter says with `AdapterError::not_measured` while preparing or in any attempt, ends there: it has no samples, no failures and no statistics, and the report lists it as not measured with the reason.

## Reports

`report.json` and `report.md` are rendered from one value, so they cannot disagree: the JSON holds durations as integer microseconds (`_us` keys) and the markdown prints the same values as milliseconds with three decimals, an exact rendering. The JSON also keeps every iteration, warm-up included; the markdown summarizes.

JSON, schema version 1:

| Field | Content |
|---|---|
| `schema_version` | `1` |
| `provenance.started_at`, `finished_at` | RFC 3339 UTC |
| `provenance.host` | `hardware` (CPU and machine model), `cpu_cores`, `memory_bytes`, `os` (`macOS 26.6.2 (25G83)`), `load_average` (1, 5, 15 minutes at the start) |
| `provenance.xcode` | `Xcode 27.0 (27A266a)`, or null |
| `provenance.commit` | `sha` and `dirty` of the checkout the harness ran from, or null |
| `provenance.harness` | `version`, `iterations`, `warmup`, `retries` |
| `provenance.targets[]` | `id` (UDID or adb serial), `class` (`simulator`, `android-emulator`, `android-device`, `ios-device`), `model`, `os`, `api_level`; `controller`, on an Android emulator whether its gRPC controller answered the tool under test (`on`, `off`, else null), and `frame_source`, whether the target gave the tool under test frames (`true`, `false`, else null); on a physical iPhone, when known, `runner` (the runner's hello, such as `mobile-agent-ios-runner 0.2.0`), `input_path` (`dtuhidd` or `runner`), `frame_path` (`screenshots`), `battery` (`level_pct`, `charging`, `external_power`, each null when not read), `auto_lock_off` (`true` when `--auto-lock-off` stated it) and `installs[]` (`fixture`, `bundle` as given, `elapsed_us`), each left out where it does not apply |
| `provenance.tools[]` | `name`, `role` (`under-test` or `baseline`), `status` (`available` or `skipped`), `version`, `note` (why it was skipped) |
| `measurements[]` | one per series and tool, below |
| `handoffs[]` | each hand-off of a target from one tool to the next, in order: `target`, `from` and `to` (the tool about to drive it, null for the release once the run is over), `elapsed_us`, `released` (what the tool's release did, null when it held nothing), `input_method` (on Android, the input method a tool left selected and the one set back, else null), `error` (why the release or the reset failed, a stray the harness ended, or what the tool left running past the wait, else null) |
| `gates` | `passed` and `rows[]` with `gate`, `statistic`, `limit_us` (null for a gate without a limit), `tool`, `target`, `measured_us`, `status` (`pass`, `fail`, `not-measured`, `reported`) and `note` (left out without one); on a run with a physical iPhone whose warm or first snapshots say what they cost the tool under test, `reads[]` with `primitive`, `tool`, `target`, `fixture`, `screen`, `wall` (the series' `stats`) and `reads` (as the measurement's), left out on other runs; null until judged, and in a run with `--gates none` |
| `ratios` | `tool`, the tool under test; `rows[]`, one per flow series of it and baseline that ran the flow on the same target and fixture, with `target`, `target_class`, `fixture`, `flow`, `baseline`, `tool_p50_us` and `baseline_p50_us` (null without samples), `ratio` (the baseline's p50 over the tool's, rounded half up to a hundredth, null without both), `baseline_failure_rate_pct`, `baseline_flake_rate_pct` and `note` (why there is no ratio, else null); `skipped[]`, the baselines the run skipped, with `tool` and `note`; null in a report from before the ratios |

Each measurement:

| Field | Content |
|---|---|
| `tool`, `target`, `target_class`, `fixture`, `screen` | what was measured where; `fixture` and `screen` may be null |
| `primitive` or `flow` | the subject: a primitive id or a flow name |
| `clock` | `wall` (read by the adapter around the tool's process or request) or `tool` (reported by the tool) |
| `iterations`, `warmup` | measured and warm-up iteration counts |
| `stats` | `n`, `p50_us`, `p95_us`, `max_us` over the successful measured iterations, or null |
| `reliability` | `iterations`, `failures`, `flakes`, `failure_rate_pct`, `flake_rate_pct` |
| `nodes` | `min` and `max` node count returned, or null |
| `error` | why the series could not run at all, or null |
| `not_measured` | why the tool could not measure the subject, or null; such a series has no samples |
| `end_state` | for a flow with a golden, the end state the tool's check read (the golden, when the flow was timed), or null |
| `reads` | for a snapshot series whose samples say what they cost the tool, `replica` and `device`: `n`, `p50_us`, `p95_us`, `max_us` of `read_us` over the measured samples served from the replica and over those that read the device, each null when there were none; null for other series |
| `samples[]` | per iteration: `iteration`, `warmup`, `outcome` (`pass`, `flake`, `fail`), `attempts`, `us`, `nodes`, `detail`, `errors`, and for a snapshot whose reply says what it cost the tool, `read_us` (`mobile-agent`'s `readMs`, the daemon's own time to answer, device reads included) and `served_from_replica` (its `servedFromReplica`), each null otherwise |

Provenance covers what the spec asks for: host hardware and OS from `sysctl` and `sw_vers` on macOS (`/proc` and `uname` on Linux), Xcode from `xcodebuild -version`, the commit from `git`, tool versions from each adapter's detection, and each target's model, OS and API level. An adapter may fill the target fields; the harness fills the rest from `adb -s <serial> shell getprop` or `xcrun simctl list devices --json`. Once the run is over, the tool under test fills in what it found out while driving each target (`Adapter::describe`): `mobile-agent` whether an emulator's controller answered and whether the target gave frames, as its daemon's `status` said while it had the target attached, and on a physical iPhone the runner, the input and frame paths and the battery (see "Physical iPhones"). Neither the daemon nor `status` names the emulator's GPU mode, so the report does not record it. `Provenance::environment_differences` lists the fields in which two runs' environments differ, ignoring times, load, a phone's battery and the builds installed before the run, so a run with the emulator's controller on and one with it off differ in `targets[<id>].controller`, and runs with another runner, input path, frame path or stated Auto-Lock on an iPhone in `runner`, `input_path`, `frame_path` or `auto_lock_off`.

The markdown has a provenance table with targets (with their emulator controller and frame source), a table of the run's physical iPhones when it has any (runner, input, frames, battery, Auto-Lock, the builds installed before the run with their times) and tools, a measurements table (tool, target, fixture, screen, subject, clock, n, p50, p95, max, Fail %, Flake %, nodes) followed by the series that could not run and the series not measured, each with its reason, a comparison table with one column per tool that measured something and one row per target, fixture, screen and subject, holding p50 / p95 (`no samples` or `not measured` where there is none), a line naming skipped tools and why, the ratios of the tool under test against each baseline with the baselines skipped (`Ratios`; see "The CI plan and the ratios"), a table of the hand-offs, and the gate table, absent when no gate was judged, followed on a run with a physical iPhone by its snapshot reads: per warm and first snapshot series of the tool under test, the wall p50 / p95 beside the daemon's own time to answer, p50 / p95 with their counts, for the snapshots served from the replica and for those that read the phone (`Snapshot reads on physical iPhones`).

## Gates

Defaults, from the spec as amended:

| Target class | Primitive | Fixture and screen | Limit |
|---|---|---|---|
| simulator | cli-start | | 20 ms |
| simulator | cold-attach | | 2000 ms |
| simulator | warm-snapshot | swiftui, big | 150 ms |
| simulator | warm-snapshot | expo, big | 250 ms |
| simulator | tap-dispatch | | 20 ms |
| android-emulator | cli-start | | 20 ms |
| android-emulator | cold-attach | | 1500 ms |
| android-emulator | warm-snapshot | any fixture, big | 100 ms |
| android-emulator | tap-to-frame-change | | 67 ms |
| android-device | cli-start | | 20 ms |
| android-device | cold-attach | | 1500 ms |
| ios-device | cli-start | | 20 ms |
| ios-device | cold-attach | | 5000 ms, the runner already installed on the phone |
| ios-device | warm-snapshot | any fixture, big | 1000 ms |
| ios-device | tap-dispatch | | 150 ms, through the host's input path, `dtuhidd` |
| ios-device | tap-to-frame-change | | none: reported with no verdict while the phone's frames are polled screenshots |

Every default reads p95. The spec states p95 for the snapshot, dispatch and tap-to-frame gates and no statistic for CLI start and cold attach, so those use p95 too; a gate file can choose `p50`, `p95` or `max` per gate. "Under" is strict: a value equal to its limit fails.

- Gates judge only the tool under test, never a baseline.
- `--gates none` judges no gate, for a shared CI runner, where the limits would judge another machine; the run's ratios against the baselines judge it there (see "The CI plan and the ratios").
- Only gates whose target class has a target in the run are listed.
- A gate with no matching measurement, or whose measurement the tool could not make, is listed as not measured and does not fail the run; a matching series in which no iteration succeeded fails.
- A gate file replaces the defaults: `{"gates": [{"class": "android-emulator", "primitive": "tap-to-frame-change", "limit_ms": 160}]}`, with optional `fixture`, `screen`, `statistic` (default `p95`) and `note`, which the table shows beside the verdict. Limits must be positive. An entry without `limit_ms` is reported: its row shows the measured value, no limit and the result `reported`, and never fails the run, whether or not an iteration succeeded; the summary line counts such rows apart, as in `All 3 gate checks passed. 1 not measured. 1 reported with no verdict.`
- The iPhone's defaults follow the spec delta of `physical-ios`: a 500-cell tree from the runner takes 450 to 550 ms (design D21), a tap through the host's `dtuhidd` is acknowledged in about 54 ms where the runner's synthesis takes about 290 ms (D22), and cold attach counts the runner's session start, not its install, which adds about 1.1 s (D20); tap to frame change comes from screenshots polled at up to 19 a second, its p95 222 to 439 ms in spike S11 (D23), so it is reported, not gated. The input path and the runner the run had are in its provenance. The warm snapshot is answered from the daemon's replica, as on the Simulator, 7.6 ms at p50 on the phone, where its 1 s limit was set from the runner's read; the gate table shows beside the gates what each warm and first snapshot cost the daemon, the reads apart from the replica's answers, so the limit is read against what it measures (design D26). The gates are the spec's, unchanged.
- The emulator's tap-to-frame default, four frames of the AVD's 60 Hz display, holds for a guest rendering on the host GPU (`-gpu host`), whose own frame pipeline takes about three at p95 (`docs/research/emulator-frames.md`). The spec does not gate the span under software rendering; the harness cannot tell the GPU mode, so such a run takes a gate file without that gate.

## Adapter interface

`adapter::Adapter` is what every tool implements, and what the CLI adapter of task 9.4 will implement for `mobile-agent`:

```rust
pub trait Adapter {
    fn name(&self) -> &str;
    fn role(&self) -> Role;                    // UnderTest or Baseline
    fn detect(&mut self) -> Detection;         // Available { version } or Absent { note }
    fn supports(&self, target: &Target, scenario: &Scenario, subject: &Subject) -> bool;
    fn prepare(&mut self, target: &Target, scenario: &Scenario, subject: &Subject)
        -> Result<(), AdapterError> { Ok(()) }
    fn measure(&mut self, target: &Target, scenario: &Scenario, primitive: Primitive)
        -> Result<Sample, AdapterError>;       // default: unsupported
    fn run_flow(&mut self, target: &Target, flow: &Flow)
        -> Result<Sample, AdapterError>;       // default: unsupported
    fn end_state(&mut self, target: &Target, flow: &Flow)
        -> Result<EndState, AdapterError>;     // default: unsupported
    fn check_flow(&mut self, target: &Target, flow: &Flow)
        -> Result<EndState, AdapterError> {    // default: run_flow, then end_state
        self.run_flow(target, flow)?;
        self.end_state(target, flow)
    }
    fn release(&mut self, target: &Target, probe: &dyn Probe)
        -> Result<Option<String>, AdapterError> { Ok(None) }
    fn describe(&self, target: &mut Target) {}
}
```

- The harness never times a call. `measure` returns a `Sample` holding the latency of exactly the primitive's span, the clock it read (`Wall` or `Tool`), the node count for snapshots and an optional detail such as a text entry method. Work outside the span, such as stopping the daemon before a cold attach or relaunching the app before a first snapshot, happens inside the call but outside the span.
- `end_state` reads the screen a flow left through the tool and summarizes it in the terms of the flow's golden; `check_flow` is one untimed run of the flow and that reading, which the harness compares with the golden before it times the flow (see "Golden end states").
- `detect` runs once per run, before any series; an `Absent` tool is skipped with its note. `supports` makes the harness skip combinations a tool cannot measure instead of recording failures. `prepare` runs once per series, before its warm-up; `Scenario` names the fixture and screen.
- An `AdapterError` is a failed attempt; the harness retries it within the iteration. `AdapterError::not_measured(reason)` is no failure: the tool cannot measure the subject at all, and the series is reported as not measured.
- `release` lets go of a target so that another tool can drive it, and says what it did; `describe` fills in the provenance the tool found out about a target (see "Hand-offs between tools" and "Reports").

## The CLI adapter

`cli::CliAdapter` drives `mobile-agent`, the tool under test, as an agent drives it: one process per command in `--json` mode, each reply in agent-browser's envelope (`{success, data, error, code?, warning?}`, `docs/research/protocol.md`), and a reply with `success: false` a failed attempt carrying its code and the first line of its message. Every command names the bench's session and the target, then the command, its flags, `--` and its operands, so an operand that starts with a hyphen stays an operand:

```sh
mobile-agent --json --session mobile-agent-bench --device emulator-5554 click --timeout 10000 -- id=row-1
```

`cli::CliConfig` names the executable (a path, or a name looked up on `PATH`), changes to the environment of every command (the tests point it at a private socket directory with the daemon's fake targets), a working directory, a work directory for screenshots and a deadline per command, 120 s by default. Detection runs `mobile-agent --version`; an executable that is not there is skipped with a note. `CliAdapter::devices` lists the targets `mobile-agent devices` reports, with their class, model and OS, which `run --target` chooses from.

Each primitive, in its `plan::scenario`:

| Primitive | Before the span | Span | Clock | Nodes |
|---|---|---|---|---|
| `cli-start` | | one `mobile-agent --version` process, its output discarded, as hyperfine times a command | wall | |
| `cold-attach` | `shutdown`, repeated until it finds no daemon; the daemon answers once it has let go of its targets, as for a release ("Hand-offs between tools") | `open <app>`, which starts a daemon, attaches the target and brings the app up; the sample notes how long the open's settle took | wall | |
| `first-snapshot` | `open --relaunch --env <big> <app>`, where `<big>` is the Big screen's launch option | `snapshot -i`, repeated until one lists `cell-500`, from the first one's start | wall | refs |
| `warm-snapshot` | once per series: the app relaunched on `big`, `cell-500` visible, a settle, one snapshot | one `snapshot -i`, which must list `cell-500` | wall | refs |
| `tap-dispatch` | once per series: the app relaunched on `list`, `row-1` visible, a settle | a `click` on `row-1`, which opens its detail: the reply's `dispatchMs`; then a `click` on `detail-back` and a settle bring the quiet list back | tool | |
| `tap-to-frame-change` | as for `tap-dispatch` | the same click's `frameChangeMs` | tool | |
| `tap-to-tree-delta` | as for `tap-dispatch` | the same click's `treeDeltaMs` | tool | |
| `text-entry` | once per series: the app relaunched on `login`, a settle | `fill` of `TEXT_ENTRY` into the empty `login-username`, noting how the fill went (below); then a wait until the string shows, a check that the field holds exactly it, the field emptied with an empty `fill`, whose note follows `cleared: `, and a settle | wall | |
| `screenshot` | once per series: the app relaunched on `big` | one `screenshot` into the work directory, noting its size | wall | |
| `settle` | a `click` on `row-1` | `wait --settle`: its reply's `elapsedMs`, noting `endedBy`; then the list brought back | tool | |

A relaunch on a screen passes the launch option the fixtures of the target's platform read (`fixtures/CONTRACT.md`, Launch options, and `fixture::Screen::launch_option`): `--env FIXTURE_INITIAL_TAB=<screen>` on a Simulator, and on Android `--env initial_tab=<screen>`, which the daemon passes as the launch intent's string extra `initial_tab`. After it opens a screen for a series, the adapter reads `status` for what the daemon says about the target: whether it gives frames (`frameSource`) and, on an emulator, whether its controller answered (the driver's `endpoint`).

A fill's note comes from its reply (task 10.23): the method the field's text went in by, `retried` when `fill` entered the text again in one piece, how it read the field back (`read back as text`, or `as length` for a secure field, `in` the reply's `readBackMs`) or `not read back`, and the reply's warning, as in `method direct, retried, read back as text in 301.25 ms, warning: …`. A reply from a `mobile-agent` that does not read fields back gives the method alone.

Spans read from replies are milliseconds to the microsecond, on the daemon's clock (`crates/cli/README.md`, "Timing spans"). A click that watched the tap (its reply has `watchedMs`) without a `frameChangeMs` or `treeDeltaMs` is a failed attempt: the tap changed nothing that way. A span the target cannot produce is not measured, with the reason: tap to frame change on an `android-device` target, which has no frame stream (design D7), and on any target whose `status` says it gives no frames, such as an emulator whose controller did not answer, with the daemon's warning; and both tap spans from a `mobile-agent` whose click does not watch the tap (before task 8.9). A physical iPhone gives frames, polled screenshots, so its click's `frameChangeMs` is measured.

A flow runs its steps as commands, timed by wall clock from the first command's start to the last one's end:

| Step | Commands |
|---|---|
| `launch` | `open --relaunch <app>` |
| `tap` | `click --timeout 10000 <selector>` |
| `fill` | `fill --timeout 10000 <selector> <text>`; the sample notes the fill as `fill <selector>: ` and its note, in the order of the flow's steps beside any scroll-to's |
| `scroll-to` | `scroll --timeout 90000 --until <selector> <direction> 600`, as an agent scrolls to an element: the daemon strokes 600 points at a time, lets the screen settle after each stroke and stops once the element is on screen by its own rule, within the 90 s the Maestro flow's `scrollUntilVisible` has; the sample notes the strokes the reply counts and, from a daemon that reports it, the share of the element in view (`visible`), as in `7 strokes, visible 0.62` |
| `assert-visible` | `wait --timeout 10000 <selector>` |
| `assert-text` | `wait --timeout 10000 --text=<text>`, then `get text id=<id>`, which must be exactly the text |

A selector is `id=<identifier>` or `text=<text>`; the CLI matches a text as part of an element's name or value, so a text selector is exact only while no other element's text contains it. A scroll-to is the one command an agent would run: the flow times the daemon's scroll, which ends where the daemon's rule for an element on screen ends it, with no settle or check of the harness's own. A flow that records its node count takes one `snapshot -i` after its timing and counts the refs.

## Flow description

`flow::Flow` describes a flow once for every tool: a name, a fixture, a list of steps, whether to record the final screen's node count outside its timing, and the golden end state that screen must show:

| Step | JSON | Meaning |
|---|---|---|
| `Launch` | `"launch"` | stop the app if it runs, then launch it; it opens on the Login tab |
| `Tap(selector)` | `{"tap": {"id": "login-submit"}}` | tap the element |
| `Fill { target, text }` | `{"fill": {"target": {"id": "login-username"}, "text": "agent"}}` | type into an empty field |
| `ScrollTo { target, direction }` | `{"scroll-to": {"target": {"id": "row-200"}, "direction": "down"}}` | scroll until the element is visible |
| `AssertVisible(selector)` | `{"assert-visible": {"id": "detail-200"}}` | wait until the element is visible |
| `AssertText { id, text }` | `{"assert-text": {"id": "login-status", "text": "Welcome, agent"}}` | wait until the element shows the text |

A selector is `{"id": …}`, the contract identifier, or `{"text": …}`, the exact visible text. Flows reach screens by tapping their tabs rather than through the fixtures' launch option, because Maestro passes launch arguments to iOS apps as process arguments, not environment variables.

A golden (`end_state::EndState`) states what the final screen shows when the flow did its work, in three kinds of terms: the text an identified element shows (`texts`, `null` for no such element), whether an element has an identifier (`present`), and how many distinct identifiers `<prefix>-<n>` elements have (`counts`). As JSON it sits under the flow's `golden` key; a flow without one leaves the key out.

The spec's three flows, `flow::reference(fixture)` in report order, are the same on every fixture:

| Flow | Steps | Golden |
|---|---|---|
| `login` (`flow::login`) | launch; fill `login-username` with `agent`; fill `login-password` with `hunter2`; tap `login-submit`; wait until `login-status` shows `Welcome, agent` | `{"texts": {"login-status": "Welcome, agent"}}` |
| `list-scroll` (`flow::list_scroll`) | launch; tap `tab-list`; scroll down until `row-200` is visible; tap it; wait until `detail-200` shows `Detail 200` | `{"present": {"detail-200": true}}` |
| `big-screen` (`flow::big_screen`) | launch; tap `tab-big`; wait until `cell-500` is visible; record the node count | `{"counts": {"cell": 500}}` |

A run may hold the same flow for several fixtures. A flow series names the flow and a fixture the run has it for, and no screen; two flows with one name on one fixture are refused before anything runs.

## Golden end states

Timing starts only once the tools agree on what a flow does. Before any series is timed, every flow with a golden runs once, untimed, through each tool that will time it (`Adapter::check_flow`), and the tool reads the screen the flow left (`Adapter::end_state`). The reading is summarized in the golden's terms (`EndState::observe`): the text of the first element with each named identifier (value before name or label, as each tool reports it; the empty text when it shows none; null when no element has the identifier), whether an element has each identifier the golden requires, and how many distinct identifiers `<prefix>-<n>` the screen has. A tool whose summary differs from the golden, after `--retries` further tries, does not time the flow: its series has the error `the end state differs from the golden:` followed by each difference (such as `login-status shows "Invalid credentials", not "Welcome, agent"`), counts every measured iteration as failed, and is listed among the series that could not run. The summary read is kept as the measurement's `end_state`. A flow without a golden is timed unchecked.

Each tool reads its screen its own way:

| Tool | Reading | Identifier | Text |
|---|---|---|---|
| the fake | its flow series' scripted `end_state`, else the flow's golden; a check uses none of the scripted attempts | | |
| `mobile-agent` | a full `snapshot`, its listing parsed line by line (`cli::listing`) | `id=` | the value after `: `, else the name, as `get text` reads it |
| Maestro | `maestro --device <id> hierarchy`: a tree of nodes with `attributes` and `children` | `resource-id`, without the `<package>:id/` prefix of native Android views | `text`, else `accessibilityText`, where Maestro puts an iOS label |
| maestro-runner | `maestro-runner --platform <ios\|android> --device <id> hierarchy`: its tree normalized across drivers, nodes with `id`, `text` and `children` | `id` | `text` |
| agent-device | `agent-device snapshot --json --platform <p> --udid\|--serial <id> --session mobile-agent-bench`: `data.nodes`, a flat list linked by `parentIndex` | `identifier` | `value`, else `label`; a node marked `inheritsLabel` or `inheritsIdentifier`, whose value agent-device left out as equal to its nearest ancestor's, takes the ancestor's |
| WebDriverAgent | Appium's `mobile: source` with `format: json`: WebDriverAgent's tree of nodes with `children` | `rawIdentifier` | `value`, else `label` |

A baseline's check is one run of the flow's file or batch and one read of the screen. The shapes come from the tools' sources: Maestro's `PrintHierarchyCommand`, `TreeNode` and its drivers' attribute mapping (github.com/mobile-dev-inc/maestro), maestro-runner's `hierarchy` command (`pkg/cli/hierarchy.go` in github.com/devicelab-dev/maestro-runner), and the installed agent-device 0.21.14's `CaptureSnapshotResult` type, its JSON printer and its snapshot serialization. agent-device prints its JSON pretty-printed, so replies are read as the first JSON object that starts a line, with any progress lines before it and anything after it ignored; the batch reply is read the same way.

## Baselines

Each baseline adapter finds its executable on `PATH`, following symbolic links, and reads its version from `--version`; a tool that is not found is skipped with the note `<tool> not found on PATH`, and the tools that ran are still measured and compared. A tool that runs on none of the run's targets is skipped with its reason before it is looked for: Maestro on a run of physical iPhones only, WebDriverAgent on a run without one (`run` gives the adapters its targets' classes; `baselines` lists every tool as found). Baselines run flows only, timed by wall clock around the tool's process, or for WebDriverAgent around its requests, since none of them exposes the primitives' spans; the flow file is written to `<out>/flows/` and rewritten before every run.

| Tool | Flow as | Command |
|---|---|---|
| Maestro | a Maestro flow file: `appId`, then `launchApp`, `tapOn`, `inputText` (after a `tapOn` of its field), `scrollUntilVisible` (with a 90 s `timeout`), `assertVisible` | `maestro --device <id> test <file>`; never on a physical iPhone |
| maestro-runner | the same file, which it runs unchanged | `maestro-runner --platform <ios\|android> --device <id> test <file>`, with `--team-id <team>` after the platform on a physical iPhone |
| agent-device | one batch of `open` (with `relaunch`), `press`, `fill`, `scroll` (with `until`), `wait` and `is` steps with their structured inputs | `agent-device batch --steps-file <file> --on-error stop --json --platform <p> --udid <udid>` or `--serial <serial>` `--session mobile-agent-bench`; on a physical iPhone with the team's signing in its environment |
| WebDriverAgent | WebDriver requests to Appium, one session attached to WebDriverAgent on the phone: `mobile: terminateApp` and `mobile: launchApp`, an element found by accessibility identifier then `click`, `click` then `value` for a fill, `mobile: swipe` until the element is found and displayed for a scroll-to (90 s), and assertions polled for 10 s | Appium's HTTP API on `127.0.0.1:4723`; physical iPhones only |

Maestro matches `id` and `text` as regular expressions, so selector values are escaped. Its `scrollUntilVisible` gives up after 20 s by default; on the Android emulator Maestro 2.10.0 swipes about 9 rows of a fixture's list every 2.2 to 2.5 s, so the default reaches row 97 of 200, and the flow's scroll has 90 s (`maestro::SCROLL_TIMEOUT_MS`), about 52 s of which reach row 200, within the flow's 120 s deadline. Assertions wait, as Maestro's do: agent-device checks a visible element with `wait` on its selector, and a text with `wait` for the text followed by `is text` on the element. A Maestro or maestro-runner flow fails on a non-zero exit, reported with the last lines the tool printed; an agent-device flow fails on `success: false` in its JSON reply, reported with the failing step and error, and its `totalDurationMs` is kept as the sample's detail.

A flow that records its node count, the 500-node flow, reads the screen once more after each timed run, outside the timing, with the same command as the golden check ("Golden end states"), and records how many nodes the tool's output held: every node of Maestro's and maestro-runner's trees, every entry of agent-device's `nodes`. A read that fails fails the iteration. `mobile-agent` records the refs of a `snapshot -i` in the same place, so the report shows the node count each tool actually returned.

## Hand-offs between tools

An Android device has one UI automation owner at a time, and tools keep the role between their commands: `mobile-agent`'s daemon keeps its agent until the daemon exits (`close` only ends the session's claim), and agent-device keeps a snapshot helper, an instrumentation, until its session is closed. A tool that finds the role held fails, as Maestro's driver did on the emulator with `UiAutomationService ... already registered!`. Tools also leave device state behind: agent-device selects its test input method for text entry, and Maestro carries one of its own. So the harness hands a target from one tool to the next (`handoff`):

- It notes which tool drives each target. Before another tool drives it, and once every series has run, the tool that drove it last lets go of it (`Adapter::release`). A tool whose golden check of a flow failed does not time the flow, so it does not drive the target for it and is not handed it. Hand-offs happen between series, never inside one, so no measured iteration includes one; the first iteration after a hand-off pays the next tool's own start, such as `mobile-agent`'s daemon and agent, which warm-up iterations absorb.
- `mobile-agent` reads `status`, then stops its daemon with `shutdown` until none answers. The daemon answers `shutdown` only once it has detached its targets, stopping their agents, and removed its socket (task 8.16), so the next tool never meets its agent, nor does the `open` of a cold attach, which follows the same `shutdown`.
- agent-device closes its session: `agent-device close --json --platform <p> --udid|--serial <id> --session mobile-agent-bench`, which stops the snapshot helper and selects the input method it found again (never `close --shutdown`, which would shut the target down). A session that is not there held nothing. It then stops its daemon with `agent-device daemon stop --clean --json`, which would otherwise idle for 5 minutes into the next tool's series, on a Simulator with the XCTest runner and the snapshot bridge it keeps after `close` (see below); `--clean` ends a runner the daemon leaves for its successor, and there is none on Android. The release stops the daemon even when the close failed, since the daemon ends its sessions as it stops, and reads `stopped` from the reply. That daemon serves every session of its state directory, so a run should give agent-device a state directory of its own (`AGENT_DEVICE_STATE_DIR`), as the rerun recipe of `reports/10.2-simulator.md` does. On Android it then lists the device's processes, `adb -s <serial> shell ps -A -o PID,NAME`, and force-stops those of agent-device's helper apps, `adb -s <serial> shell am force-stop <package>`: the input-method helper `com.callstack.agentdevice.imehelper`, which neither `close` nor `daemon stop` ends, and the snapshot helper `com.callstack.agentdevice.snapshothelper`, whose instrumentation a daemon killed with its session open leaves running (see below).
- Maestro and maestro-runner hold nothing: Maestro's driver instrumentation ends with the `maestro test` process that started it.
- A physical iPhone has one automation session, which the XCTest runner app of the tool driving it holds, and a runner that starts while another holds it waits rather than fails. Each tool's release ends its own: `mobile-agent`'s daemon ends its runner as it shuts down (`crates/ios/README.md`, Runner session); agent-device's, after its `daemon stop --clean` killed the runner's `xcodebuild`, ends the runner app should it outlive it, through CoreDevice (`xcrun devicectl device process terminate --device <udid> --pid <pid> --json-output -`), and waits up to 5 s for it to leave the phone's process list; WebDriverAgent's deletes Appium's session, stops Appium with SIGTERM and the helper by closing its standard input, which ends WebDriverAgent's test manager session, and ends the runner app the same way, since on iOS 26.6.2 it outlived that session (still running 10 s after the helper exited; the termination returned in 0.26 s and the runner was gone at the next listing). After the release the hand-off lists the phone's processes too (`xcrun devicectl device info processes --device <udid> --json-output -`, about 0.3 s a call) and treats the runner app of the tool that let go, `MobileAgentRunner-Runner`, `AgentDeviceRunnerUITests-Runner` or `WebDriverAgentRunner-Runner` by the tool's name (`baseline::iphone::RUNNERS`), as a stray: it ends it through CoreDevice, SIGTERM and then `--kill`, never with the host's `kill`, and names it in the hand-off's error, as in `agent-device left runner app on the iPhone (pid 812) running after its release; the hand-off sent it SIGTERM, and it exited`. A baseline about to start on an iPhone lists the phone's processes first and fails at once when another tool's runner holds the session, naming it: `agent-device did not start: the iPhone's automation session is held by webdriveragent's runner WebDriverAgentRunner-Runner (pid 7920); one tool drives a phone at a time`. On an iPhone agent-device leaves its daemon and its runner's `xcodebuild` on the host, whose destination names the phone (`-destination platform=iOS,id=<udid>`), and starts no bridge; WebDriverAgent leaves its helper (`mobile-agent-bench wda-session --udid <udid>`) and Appium (`… appium … --port 4723`), both strays once its release has run, since it stops them itself.
- After the release the harness waits until the tool has nothing left running for the target (`Adapter::left_running`), asking every 100 ms for at most 30 s. For agent-device that is its daemon of the state directory `agent-device session state-dir --json` prints, and on a Simulator also its runner's `xcodebuild` and app, and its bridge's `simctl spawn` and process in the Simulator (`agent_device::left_running`). The harness lists the host's programs with `ps -A -o pid=,comm=`, then reads `ps -E -ww -o pid=,command= -p <pids>` for those named `node`, and on a Simulator `xcodebuild`, `simctl` or `snapshot-bridge`. It keeps a daemon whose environment sets `AGENT_DEVICE_STATE_DIR` to that directory, the runner and the bridge whose arguments name the Simulator's UDID, the bridge whose environment sets `SIMULATOR_UDID` to it, and the runner app under the Simulator's directory. A daemon still running once the release's `daemon stop` has returned is one the stop did not reach, as a daemon whose `daemon.json` a timed-out request deleted (see below), and `left_running` marks it a stray. The harness sends a stray SIGTERM, `kill -TERM <pid>`, as soon as it lists it, and SIGKILL if it is still running 10 s later, as `daemon stop` does with the daemon its `daemon.json` names, and waits for it as for the rest. Since the release left it behind, a stray is an error naming it and what was sent, however it ended, such as `agent-device left daemon (pid 4711) running after its release; the hand-off sent it SIGTERM, and it exited`. Any other process still running after 30 s is an error naming it and its pid, such as `agent-device left bridge (pid 4712) running 30 s after its release`. The 30 s bound comes from the exit times measured below.
- On an Android target the harness then selects the input method the run found again, read at the start with `adb -s <serial> shell settings get secure default_input_method`, when a tool left another selected (`adb -s <serial> shell ime set <it>`).

Each hand-off is recorded in `handoffs` with its duration (the release, the wait and the input method's reset), what the release did, the input method set back and any failure, such as a stray the harness ended or a process still running past the wait; a failed release does not stop the run, and the next tool meets the target as it was left. Before a run, the target should be as a run leaves it: the stock input method, no automation running, the launcher in front.

On the Simulator, agent-device keeps three things running outside its session: a daemon per state directory, an XCTest runner (`xcodebuild test-without-building … -only-testing AgentDeviceRunnerUITests/RunnerTests/testCommand … -destination platform=iOS Simulator,id=<udid>`, and the runner app it starts in the Simulator) and a snapshot bridge (`xcrun simctl spawn <udid> …/snapshot-bridge serve <socket> --idle-timeout 60 --exit-on-disconnect false`, and its process in the Simulator). `close` keeps the runner warm for the next session: the runner stops after 5 idle minutes and the daemon exits after 5 minutes without a session or a request, which is how they overlapped `mobile-agent`'s series in `reports/10.2-simulator.md` (finding 2). `AGENT_DEVICE_IOS_RUNNER_IDLE_STOP_MS` and `AGENT_DEVICE_DAEMON_IDLE_TIMEOUT_MS`, read from the daemon's environment, change the two windows, and no flag of `close` ends them sooner; `--shutdown` would also shut the Simulator down. `daemon stop [--state-dir <dir>] [--clean]` sends SIGTERM to the daemon the state directory's `daemon.json` names, waits up to 10 s for it to exit, then sends SIGKILL. On SIGTERM the daemon stops the bridge and its runners, except a ready runner with no command in flight, which it detaches and leaves running for the next daemon to adopt; `--clean` then kills that runner and its `xcodebuild`. Every command, `daemon stop` included, uses the directory `--state-dir` names, else `AGENT_DEVICE_STATE_DIR`, else `$HOME/.agent-device`. The bench passes no `--state-dir`, and `agent-device session state-dir --json` prints the directory without starting a daemon. On an iOS 26.5 Simulator, after two login batches and a snapshot, `close` took 120 to 466 ms over three runs and `daemon stop --clean` 463 and 472 ms. The daemon, `xcodebuild`, the runner app and both bridge processes were gone at the first 0.5 s sample after the stop. After a bare `daemon stop`, `xcodebuild` and the runner app were still running when watching ended 40 s later. A daemon can also slip past `daemon stop`. When a first batch timed out after 90 s while the runner built, the client removed the daemon's `daemon.json` without killing it, the next command started a second daemon for the same directory, and `daemon stop` stopped only that one. The first idled with its session open for 7 minutes, until a SIGTERM ended it in 0.08 s. Sources: agent-device 0.21.14's `help daemon`, `help close` and the "Runner and daemon lifecycle" part of `help physical-device`; in its package, `dist/src/daemon.js` (`daemon stop`), `dist/src/internal/daemon.js` (the daemon's shutdown and idle exit), `dist/src/runner-client.js` and `dist/src/runner-disposal.js` (the runner's idle stop, its detach and `--clean`), `dist/src/daemon-client-lifecycle.js` (a timed-out request), `dist/src/native-build-cache.js` and `dist/src/adapter.js` (the bridge's start and stop) and `apple/snapshot-bridge/SnapshotBridge.m`. Maestro keeps nothing of the kind: its `xcodebuild` and XCTest runner end with each `maestro test` (the same finding).

On an Android emulator, agent-device's session holds the snapshot helper, `adb -s <serial> shell am instrument -w … com.callstack.agentdevice.snapshothelper/.SnapshotInstrumentation` run by the daemon, and the input-method helper `com.callstack.agentdevice.imehelper`, which it selects as the keyboard for text entry. `close` ends the instrumentation and its `adb` on the host and selects the input method it found again, deleting its record of it; agent-device's input method stays enabled. The daemon keeps running on the host, holding nothing on the device, until its 5 idle minutes are over, which is how it overlapped `mobile-agent`'s series in `reports/10.26-remeasure.md` (finding 5). The input-method helper stays in the guest as a cached process, which Android had frozen 90 s after the close and keeps until it needs the memory; neither `close` nor `daemon stop` ends it. On the API 36 emulator, after a login batch, `close` took 516 ms and `daemon stop --clean` 406 ms, the daemon gone by the time it returned. The helper then held 9.5 MB PSS and had used 40 ms of CPU, and `am force-stop` ended it in 34 ms at the median, 254 ms at a load of 20, without its coming back. A daemon slips past `daemon stop` here too. A `close` or `batch` that times out, after 90 s, resets the daemon: the client deletes `daemon.json` and the daemon's lock in any case, and kills the daemon only once `ps` has confirmed its start time and command, each within 1 s. Where it killed it, the daemon's `adb … am instrument -w` was left reparented to `launchd`, with `AGENT_DEVICE_STATE_DIR` in its environment, the instrumentation running in the guest and agent-device's input method still selected. Ending that `adb` left the instrumentation running, and `mobile-agent` still attached beside it. ## Microbenchmarks

`micro` runs the host microbenchmarks of `protocol`, `mirror`, `daemon`, `simulator` and `android` (designs D13 to D16 of the `microbenchmarks` change) on a quiet host, compares them with the committed baseline, `reports/micro/baseline.json`, and writes `report.json` and `report.md`. `just micro <arguments>` runs it in release mode; it works from any directory of the checkout, whose root it finds with `git rev-parse --show-toplevel`.

```sh
just micro                                    # every suite, compared with reports/micro/baseline.json
just micro --wait 60                          # wait up to an hour for a quiet host first
just micro --filter protocol/decode           # only the ids the filter matches
just micro --threshold 10 --out target/micro  # a looser threshold, the reports in target/micro
just micro --wait 60 --save-baseline          # refresh the baseline from a quiet run of every suite
just bench-ab main --wait 60                  # the checkout against main, both built and run here
just bench-ab v0.1.0 --rounds 5 --filter mirror/  # five rounds each, the mirror's benchmarks only
cargo bench -p mirror -- --noplot pump        # one suite on its own, with criterion's output only
```

| Flag | Default | Meaning |
|---|---|---|
| `--wait <minutes>` | none: a busy host is refused at once | check the host every 30 s, for up to this long, until it is quiet |
| `--max-load <n>` | 4, or the host's core count with `--ab` | the 1-minute load average must be under this |
| `--threshold <percent>` | 5, or 10 with `--ab` | a median slower than the baseline's by more than this and above the baseline's interval is a regression, one faster by more and below it an improvement; with `--ab`, a head median slower or faster than base's by more than this |
| `--filter <name>` | every benchmark | criterion's filter: a regular expression matched against the ids |
| `--save-baseline` | off | rewrite `reports/micro/baseline.json` with this run's values and provenance, after comparing; refused with `--ab` |
| `--ab <ref>` | none: compare with the committed baseline | compare the checkout with this ref, both built and run on this host (see "Two refs on one host") |
| `--rounds <n>` | 3, with `--ab` only | how many times each side runs the suites |
| `--out <dir>` | `target/bench/micro/<UTC start time>/` in the repository root | where `report.json`, `report.md` and criterion's files go |

**The guard.** Before anything is built or measured, `micro` checks that the host is quiet, as the spikes and the device reports did by hand: the 1-minute load average, from `sysctl -n vm.loadavg` on macOS and `/proc/loadavg` elsewhere, under `--max-load`, and no process of the builders and devices the reports waited for above 5% of a core in `ps -A -o pid=,ppid=,pcpu=,comm=`: `cargo`, `rustc`, `xcodebuild`, `java` and `Simulator` by name, the `gradle`, `kotlinc`, `qemu-system`, `emulator` and `com.apple.CoreSimulator` families by prefix, leaving out the runner and the processes it started. A load or a process list that cannot be read is not quiet. A busy host is refused with exit status 2, naming the load and each busy process with its pid and share of a core, such as `the 1-minute load average is 6.50, not under 4; busy: qemu-system-aarch64-headless (pid 4242, 17.2% of a core); nothing was measured`. With `--wait` the runner prints why and checks again every 30 s: the first quiet check starts the run, and a host still busy once the wait is over is refused. The report records the load averages at the check that passed and once the suites have run, the bound, and how long the run waited. A raised `--max-load` is for smoke runs on a busy host, and their reports carry the bound they ran under.

**The run.** `micro` runs `cargo bench --workspace --bench codec --bench mirror --bench daemon --bench frames -- --noplot [filter]` in the repository root, with the cargo `$CARGO` names, which `cargo run` sets, else `cargo`: the bench profile, and criterion's default sample settings of design D13, 3 s of warm-up, 100 samples over about 5 s and 100,000 bootstrap resamples for 95% intervals. `CRITERION_HOME` is `criterion/` in the output directory, which must not exist yet, so every file criterion leaves there is this run's. Cargo's progress and criterion's go through on stderr; stdout, criterion's results and the lines of the counting allocator in the codec, mirror and daemon benches, `allocations <id> <allocations> <bytes>` before each benchmark, is echoed as it comes and kept. Cargo builds the suites after the guard; built beforehand, with the same command and `--no-run` in place of `-- --noplot`, they start measuring at once. A cargo that fails, a suite that panics and a filter that matches nothing are runs that could not complete, with exit status 2.

The `[lib]` and `[[bin]]` sections of the five crates, `cli`, the Simulator's reader and this crate set `bench = false`: cargo hands the arguments after `--` to every bench target it runs, and a library's or a binary's libtest harness refuses criterion's `--noplot`. So one suite also runs on its own, `cargo bench -p <crate> -- --noplot [filter]`, with criterion's text output and files under `target/criterion/`, compared with that crate's previous run there rather than with the baseline.

**What is read.** Every directory `<id>/new/` under `CRITERION_HOME` that holds an `estimates.json` is one benchmark, whose id is its path, `<crate>/<function>/<input>` as the benches name them, such as `protocol/decode/snapshot-500`. The median's point estimate and its 95% interval come from `estimates.json`, rounded to whole nanoseconds, and the sample count from `sample.json`; the `base/` copies criterion keeps beside `new/` do not count. The allocations and bytes are those of the allocation line with the same id. The suites print a line before each benchmark even when the filter skips it, and under `--list`, so the lines of benchmarks that wrote no estimates are dropped. criterion calls these files private, so its version stays pinned in `Cargo.lock` and the reader is tested on files spike S8 recorded, under `tests/fixtures/micro/`.

**The comparison.** A benchmark's difference is its median against the baseline's, in percent of the baseline's, rounded to a tenth. Its time verdict has two conditions, each judged on values both reports show, the rounded difference and the medians and interval in whole nanoseconds: a median more than `--threshold` slower than the baseline's and above the high end of the 95% interval the baseline recorded around its own median is a regression, one more than `--threshold` faster and below the interval's low end an improvement, and anything else the same. A median inside the baseline's interval, its ends included, is therefore the same whatever its difference, which is still shown. The interval is there for benchmarks whose median moves by more than the threshold from one run to the next, as their own interval shows. In the first baseline those were `protocol/decode/requests-1k` and `protocol/decode/events-10k`, which decode 1,000 and 10,000 small messages and drop them: their samples fell in two modes 5 to 15% apart, about half in each, so their median landed in either mode from run to run, and `requests-1k`'s interval reached 7.5% above its median and `events-10k`'s 5.0% below, where every other benchmark's stayed within 0.5% of its median. The first run against that baseline measured `requests-1k` at 141.370 µs, 5.9% slower than the baseline's 133.498 µs and inside its interval of 132.178 to 143.493 µs: a regression by the threshold alone, the same by both conditions (design D16). The two modes came from criterion's per-sample shift of the stack, to which those two loops are sensitive; they have since run on a stack pinned to a page (design D16), their intervals in the committed baseline are as narrow as the others', and the threshold is the condition that binds for every benchmark in it. A baseline entry without an interval, its `spread_ns` null or absent, is judged on the threshold alone. Allocations and bytes per iteration are deterministic and compare exactly: a regression when either rose, an improvement when one fell and neither rose, whatever the time; a benchmark counted on one side only is compared on its time. A benchmark regressed when its time or its allocations regressed, else improved when either improved, else is the same. One the baseline lacks is new and one the run lacks missing, and neither changes the exit status; without a baseline file every benchmark is new. A baseline measured elsewhere is compared all the same, and the report names the environment fields in which its provenance differs: `host.hardware`, `host.cpu_cores`, `host.memory_bytes`, `host.os`, `toolchain` or `harness`.

**The baseline.** `reports/micro/baseline.json` holds `schema_version` (1), the `provenance` of the run that wrote it, as in the report, and `benchmarks[]` in id order, each with `id`, `median_ns`, `spread_ns` (`low` and `high`, the median's 95% interval), `samples`, `allocations` and `bytes_allocated` (null where the bench counts none). To refresh it, run `just micro --wait 60 --save-baseline` on a quiet host: the run compares against the baseline it finds, as any run does, then writes its own values and provenance. Commit the file with the change that moved the numbers and review its diff, where a regression the change accepts shows beside the provenance it was measured with. `--save-baseline` is refused with exit status 2 together with a `--max-load` above 4, so a baseline never comes from a host the default guard would refuse, and with `--filter`, since a baseline holds every suite. A toolchain bump re-baselines the same way, and the provenance names the compiler.

**Reports.** `report.json` and `report.md` are rendered from one value: the JSON holds times as whole nanoseconds (`_ns` keys) and differences in tenths of a percent, and the markdown prints the times as microseconds with three decimals, an exact rendering, and the differences with their sign, so the two agree on every number. JSON, schema version 1:

| Field | Content |
|---|---|
| `schema_version` | `1` |
| `provenance.started_at`, `finished_at` | RFC 3339 UTC: when the guard found the host quiet, and when the suites had run |
| `provenance.host` | `hardware`, `cpu_cores`, `memory_bytes`, `os`, and `load_average`, the 1, 5 and 15 minute load averages at the check that passed |
| `provenance.load_average_end` | the load averages once the suites had run |
| `provenance.commit` | `sha` and `dirty` of the checkout, or null |
| `provenance.toolchain` | `rustc -V` in the checkout |
| `provenance.harness` | `library` (`criterion`), `version` (from `Cargo.lock`), `warm_up_s`, `measurement_s`, `sample_size`, `resamples`, `confidence_pct` |
| `provenance.guard` | `max_load`, the bound the run passed, and `waited_s` |
| `threshold_pct` | the run's threshold |
| `baseline` | `path`, `reports/micro/baseline.json`; `provenance`, that of the run that saved it, or null without a baseline; `environment_differences`; `saved`, whether this run wrote it |
| `benchmarks[]` | in id order: `id`, `median_ns`, `spread_ns` (`low`, `high`), `samples`, `allocations`, `bytes_allocated`; `baseline`, the baseline's entry for it (its `spread_ns` null when the baseline file holds no interval), or null when new; `difference_pct`; `time_verdict` and `allocations_verdict` (`regression`, `improvement`, `same`, or null when not compared); `verdict` (`regression`, `improvement`, `same`, `new`) |
| `missing[]` | the baseline's entries this run did not measure |
| `summary` | `benchmarks`, `regressions`, `improvements`, `same`, `new`, `missing`, `exit_status` and `reason` |

The markdown opens with the summary line, `Exit status <n>: <reason>.` and the counts, then has the provenance table, the baseline compared against with the fields its environment differs in, a table of benchmarks per crate (median, interval, samples, allocations, bytes, the baseline's median, the difference and the verdict, which names the measures that moved, or reads `same (median inside the baseline's interval)` for a median past the threshold that the interval kept the same), a table of the regressions and one of the improvements, each measure that moved with the baseline's value, the baseline's interval for a median, the measured value, the difference and the threshold (`exact` for allocations and bytes, which have no interval), and the missing benchmarks. Once the run is over it prints where the reports went, the regressions and improvements tables and the summary line, as `run` prints its gate table.

Exit status: 0 without a regression, new and missing benchmarks included; 1 on any regression; 2 when the host was busy, `--save-baseline` was refused, the baseline file does not read or the run could not complete.

**Two refs on one host.** `micro --ab <ref>` (design D2 of `ci-benchmarks`, `micro::ab`) compares the checkout, head, with another ref of the repository, base, both built and run on this host, instead of with the committed baseline, which it neither reads nor writes: `--save-baseline` is refused with it, and `--rounds` without it, with exit status 2. It resolves the ref with `git rev-parse --verify <ref>^{commit}` and refuses one the checkout has no commit for before anything else. The guard checks the host as above, keeping its busy-process check, with the load bound at the host's core count unless `--max-load` gives one (`sysctl -n hw.ncpu` on macOS and `nproc` elsewhere, else the parallelism the OS grants the process, 4 when none reads): on a CI runner of 2 to 4 cores the job's own setup weighs on the load average, which the quiet host's 4 would not allow for. Then the base is checked out with `git worktree add --force --detach` into `mobile-agent-bench-ab-<pid>` in the system's temporary directory, not under the checkout, since cargo reads the `.cargo/config.toml` of every directory above the one it runs in; `--force` takes over a registration of that path a killed run left, and no other worktree of the repository is touched. Both trees' suites are built, `cargo bench --workspace --bench codec --bench mirror --bench daemon --bench frames --no-run`, the head's in its own target directory and the base's in `target/bench/micro-ab/target/` of the checkout, both with the toolchain `RUSTUP_TOOLCHAIN` names, else the one `rustup show active-toolchain` resolves in the checkout, so a base that pins another toolchain builds with the head's. The guard checks the host again once both are built, waiting as long again, so the rounds start on a quiet host whatever ran during the builds. Each of `--rounds` rounds runs both sides' suites, the side that goes first alternating, base then head, head then base, base then head, so a drift through the run weighs on both sides alike; each run writes criterion's files into a fresh `criterion/round-<n>-<side>/` of the output directory, `target/bench/micro-ab/<UTC start time>/` without `--out`, read as above. The worktree is removed with `git worktree remove --force` once the rounds are over, whether or not they completed; a removal that fails is said on stderr after the reports.

A side's value for a benchmark is the median of its rounds' medians, the nearest rank and so one of them, with the samples and allocations of that round. Head's median is judged against base's on the threshold alone, `--threshold`, 10% by default with `--ab` until spike S12 measures the runners' noise (design D3): slower by more is a regression, faster by more an improvement, anything else the same, with neither side's interval as a condition, since both sides were measured in the same run. Allocations and bytes compare exactly, as against the baseline: a regression when either rose, an improvement when one fell and neither rose. A benchmark only head measured is new, one only base measured missing; neither changes the exit status. Exit status: 0 without a regression, 1 on any, 2 when the ref is unknown, the host busy, a build or a run fails, or an option is refused.

Its `report.json`, schema version 1:

| Field | Content |
|---|---|
| `schema_version` | `1` |
| `provenance` | as above; `commit` is head's, `started_at` and `host.load_average` are those of the check once both trees were built, and `guard.waited_s` adds up both waits |
| `base` | `ref`, as given, and `sha`, the commit it named |
| `rounds`, `order` | the rounds, and the sides in the order they ran, round by round, such as `[["base", "head"], ["head", "base"], ["base", "head"]]` |
| `rustup_toolchain` | the toolchain both sides were built and run with, or null when rustup named none |
| `threshold_pct` | the run's threshold |
| `benchmarks[]` | head's benchmarks in id order: `id`, `base` and `head`, each with `median_ns`, `rounds_ns` (each round's median, in round order), `samples`, `allocations` and `bytes_allocated`, `base` null when new; `difference_pct`; `time_verdict`, `allocations_verdict` and `verdict` (`regression`, `improvement`, `same`, `new`) |
| `missing[]` | base's benchmarks head did not measure: `id` and `base` |
| `summary` | as above, its `reason` naming the base, such as `no regression against main` |

`report.md` opens with the summary line, then the provenance with the base, the rounds and their order and the toolchain, a table per crate of each benchmark's base and head medians, the difference, each side's rounds, allocations and bytes, and the verdict, which reads `regressed (median)`, `regressed (allocations)`, `faster`, `fewer allocations`, `same` or `new`, then the regressions and the improvements, each measure that moved with base's and head's value, the difference and the threshold, and base's benchmarks head did not measure. The run prints the regressions, the improvements and the summary line, as `micro` does.

**Against the previous scheduled run.** `mobile-agent-bench trend <previous report.json> <report.json>` prints, as markdown, a report beside an earlier one of the same kind, which `.github/workflows/benchmarks.yml` downloads from the previous scheduled run's artifact (design D5 of `ci-benchmarks`). For two A/B reports it lists each benchmark's head median in both, the change between them, and each run's difference against its base; for two `run` reports, each flow's ratio against each baseline in both, with the tool under test's p50, the ratios recomputed from the measurements so that a report from before them compares too, and the rows matched by target class, fixture, flow and baseline, since the targets' ids differ from run to run. Two runs on shared runners had different machines, so the changes are shown and never judged: the exit status is 0, or 2 when a report does not read or the two are of different kinds.
