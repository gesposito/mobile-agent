# Design

## Context

`docs/research/open-sourcing.md`'s "What a first release will need" names the four mechanisms: trusted publishing to crates.io (a first manual publish, then a trusted publisher per crate and a job with `id-token: write`), artifact attestations (`actions/attest-build-provenance`, `gh attestation verify`), immutable releases (a repository setting), and a release environment with tag rules. `docs/maintaining.md` holds them unticked under "At the first release". The crates carry `license`, `repository`, `readme` and `description` (open-sourcing task 4.1) and versioned path dependencies, and `publish` is on; their package names are the short ones (`daemon`, `mirror`, `protocol`, `wire`, `ios`, `android`, `simulator`, `mcp`, `cli`, `bench`, `agent-ios`), which crates.io has taken or would let anyone take, while `mobile-agent`, `mobile-agent-daemon` and `mobile-agent-mcp` are free (checked 2026-11-05). The binaries run on the host that drives the devices: a Mac with Xcode for the Simulator and the iPhone, any host with the Android SDK for the emulator and devices; the Simulator reader is built into the daemon at build time for the host's Xcode, and the Android agent is a jar the daemon carries.

## Goals / Non-Goals

Goals: a reproducible, attested, immutable pre-release that a Mac user installs without building; the crates publishable and published; nothing that weakens the hardening (no long-lived tokens, no cache in the publishing job, no tag anyone can push). Non-Goals: Homebrew or other package managers (after a second release); Intel Macs (the Xcode the drivers need runs on Apple silicon; stated in the README); Windows; a stable interface promise (the alpha's words say what may change).

## Decisions

### D1. Research first, then a dry run
A prior-art note, `docs/research/alpha-release.md`: cargo-dist (axodotdev's `dist`) against a hand-written workflow, judged on attestations, immutable releases, the environment gate and how each creates the tag; the tag ruleset's bypass for a workflow (what GitHub's rulesets let bypass: a deployment, an app, a role) and how Astral does it; crates.io trusted publishing's exact steps and the order a workspace publishes in (`cargo publish` of a workspace in the current Cargo, or crate by crate); the binaries' targets (aarch64-apple-darwin for the host with Xcode; x86_64 and aarch64 Linux for Android-only hosts) and what each needs at build time (the Simulator reader's cross build, libjpeg-turbo static, the Android agent jar). Then a spike: the workflow in dry-run mode on the real runners, its artifacts downloaded and verified with `gh attestation verify`, before any tag exists. The verdict decides cargo-dist or hand-written; the measurement is the workflow's minutes and the artifacts' sizes. As built (tasks 1.1 and 1.2, 2026-11-05): `docs/research/alpha-release.md`, read from dist 0.34.0's book and generated workflow, Astral's uv and ruff release workflows and example rulesets, GitHub's documentation on rulesets, environments, immutable releases and attestations, crates.io's trusted publishing page and Cargo 1.99.1, through Context7 and at each source with its date. The verdict is a hand-written workflow: dist's build steps cannot carry the jar, Xcode 27, libjpeg-turbo and the reader without its experimental setup hooks, its release job cannot sit in our environment without a hand edit after which it stops maintaining the file (where uv and ruff ended), its workflow writes at the top level and pipes its installer into `sh`, and its archives and installers are more than the alpha needs. The targets are aarch64-apple-darwin on the `xcode-27` image and x86_64 and aarch64 Linux (gnu) on Ubuntu 22.04, glibc 2.35 or newer; no Intel Mac, whose Simulators run x86_64 runtimes the reader is not built for and whose GitHub images carry Xcode 26 alone. The dry run, run 42011151745 on main `d6af6b7` with `version=0.0.0-dryrun`, was green in 5 min 47 s of wall time and 13 billed minutes once each job is rounded up: the jar 0.6 min; the builds 4.5 min on macOS (its `cargo build` 3 min 46 s) and 1.4 min on each Linux (1 min 00 s and 1 min 03 s); the verify jobs 0.5 min each. The tarballs are 8,770,454 bytes for aarch64-apple-darwin, 5,161,918 for x86_64 Linux and 5,002,102 for aarch64 Linux, the Mac's daemon 16,019,376 bytes with the reader, the jar and libjpeg-turbo inside it, the jar 72,530; the artifacts are kept to 2027-02-03. Downloaded here, `gh attestation verify` on the Mac's tarball printed "✓ Verification succeeded!" with the build and signer workflow `.github/workflows/release.yml@refs/heads/main`, and the Linux tarballs and the extracted daemon verified too; the binary printed `mobile-agent 0.0.0-dryrun (d6af6b741d1b)`. The Simulator reader was built by Xcode 27.1 (27A9275), the image's default, against the iOS Simulator SDK 27.1 for iOS 14.0 and later; the image runs the iOS 27.0 Simulator runtime.

### D2. The release workflow
`release.yml` on `workflow_dispatch` with `version` (semver, `0.1.0-alpha.1` first) and `dry_run` (default true), `permissions: {}`, every action pinned, no cache in any job that publishes. Jobs: `build` per target (macOS: the three binaries with the reader built in, through the Xcode the runner image carries, named with the target; Linux: the CLI, the daemon and the server without the Simulator driver), each uploading its artifacts and attesting them (`id-token: write`, `attestations: write` on the build job alone); `verify` downloading every artifact and checking the attestations and that `--version` prints the version and the commit; `publish`, in the `release` environment with the maintainer as required reviewer, only when `dry_run` is false: creates the annotated tag `v<version>` on the dispatched commit, the pre-release with the binaries, their checksums and `THIRD-PARTY-NOTICES.md`, and the notes from the changelog's section. The tag ruleset gains "restrict creations" with the workflow's deployment as the sole bypass, the way D1's research says GitHub allows; release immutability is turned on before the first run that publishes. As built (task 1.2, 2026-11-05), the build and verify jobs, the publishing job left to task 2.1: `release.yml` has `version` and `dry_run` (default true; false is refused, since nothing publishes yet), `permissions: {}`, one run at a time never cancelled, and the version reaching the shell through the environment alone. A `jar` job builds the Android agent once (JDK 21 and Kotlin 2.4.20 through mise with its cache off, android-36 and build-tools 37.0.0), so every daemon embeds the same jar through `MOBILE_AGENT_JAR`. `build` runs per target on `xcode-27`, `ubuntu-22.04` and `ubuntu-22.04-arm`: it checks that the image's default Xcode is 27, installs the toolchain from `rust-toolchain.toml` (the iOS targets with it) and libjpeg-turbo on macOS, builds `cargo build --release --locked --target <target> -p cli -p daemon -p mcp` with `MOBILE_AGENT_RELEASE` set to the version and the vendored emulator controller proto, so that every target's daemon is built from the same, checks the reader is embedded and that the daemon links nothing from Homebrew, packs `mobile-agent-<version>-<target>.tar.gz` with `THIRD-PARTY-NOTICES.md` and a `SHA256SUMS` of the four files, attests the tarball and its three binaries in one attestation with `actions/attest` v4.2.2 (`actions/attest-build-provenance` v4 is a wrapper of it whose README sends new workflows to it), with `id-token: write` and `attestations: write` on this job alone, and keeps the tarball 90 days. `verify` runs per target on the same runners with `attestations: read`: it downloads every tarball, verifies each and its own binaries with `--signer-workflow`, `--source-digest` set to the dispatched commit and `--deny-self-hosted-runners`, checks the sums, and checks that `mobile-agent --version` prints `mobile-agent <version> (<12 digits of the commit>)`. No job uses a cache. `crates/cli/build.rs` reads `MOBILE_AGENT_RELEASE` (else `local`) and the commit from git, and the benchmark harness records for mobile-agent what `--version` prints after its name. The daemon's and the server's `--version` print the workspace's version, so 2.1's publishing job refuses a version other than the workspace's. As built (task 2.1, 2026-11-05), the publishing path: a dispatch with `dry_run` false runs two jobs after the verify jobs. `gate`, in the `release` environment, whose required reviewer is the maintainer and which `main` alone may deploy from, does nothing but end the commit's deployment to `release` with success; `publish`, after it and in no environment, is the one job of the workflow with `contents: write`, with no cache. `scripts/release-notes.sh` refuses there a version other than `[workspace.package].version` and a changelog whose section for the version is missing, undated (its heading `## <version> — <YYYY-MM-DD>`) or empty, and prints the section as the notes; the job checks the three tarballs against their sums, refuses a version whose tag or release exists already, creates the draft pre-release `v<version>` on the dispatched commit (`gh release create --draft --prerelease --target`) with the three tarballs, a `.sha256` sum per tarball, which the build job writes beside it and the verify jobs check, and `THIRD-PARTY-NOTICES.md`, publishes it, which creates the tag, a lightweight one, and reads back the tag's commit, the pre-release mark and the seven assets. The first job runs the same check when a run publishes, so that a refused version builds nothing. The tag rule is a second tag ruleset, `releases`, on `refs/tags/v*` with `required_deployments: [release]` and no bypass, beside `tags` and its update, deletion and force-push rules, in place of a restricted creation with the deployment as its bypass, which no ruleset can express (D1's note). It was tested on a throwaway version, `0.0.0-dryrun2`, from a branch allowed to deploy to `release` for the test alone and before the reviewer was set: a tag pushed on a commit without a deployment was refused with "Missing successful active release deployment"; run 42019676267, whose publish job was itself in the environment, created the draft, and the draft's publication, which is when the tag is created, was refused with the same message, a deployment in progress not being a successful one; run 42020858421, with the gate before the publish job, published the pre-release and its tag on the dispatched commit, and its downloaded tarball verified with `gh attestation verify` and its `.sha256`, its three binaries printing `0.0.0-dryrun2`. The throwaway's release, tag, branch, branch policy and two deployments were deleted afterwards, and the exclusion of `refs/tags/v0.0.0-*` that the `tags` ruleset had during the test, so that the tag could be deleted, removed, so that nothing of it remains. The maintainer approves one job per release, the gate; a second job in the environment would ask for a second approval. Release immutability was turned on through `PUT /repos/{owner}/{repo}/immutable-releases` after the test; the environment's "Allow administrators to bypass configured protection rules" has no field in the REST API and stays on, the maintainer's to untick in the web form (`docs/maintaining.md`, At the first release).

### D3. The version and the words
`0.1.0-alpha.1` in the workspace's `[workspace.package]`; the changelog's unreleased section becomes `0.1.0-alpha.1 — 2026-11-..` with the changes since the first commit summarized by change, as the file's style already does per change; the README gains Install (download, verify the attestation, put the binaries on the path, the Xcode and Android prerequisites, "experimental, pre-release: the drivers use private Apple Simulator frameworks, Apple's developer services on an iPhone and hidden Android APIs; the interface may change between alphas"); `mobile-agent --version` prints the version and the commit it was built from (the workflow passes it; a local build prints `local` and the commit from git when there is one). SECURITY.md's supported-versions table lists the alpha.

### D4. The alpha, published and checked
The maintainer approves the `release` deployment in the web form; the workflow publishes; `gh release verify` and `gh attestation verify` on each binary from a download; an install on a clean user account of a Mac with Xcode, following the README's Install alone, driving the SwiftUI fixture's login flow once; the record in the task with the run, the release URL and the install's lines. A problem found by the install is fixed in a second alpha, not by editing the release.

### D5. The crates' names
Every workspace package is renamed `mobile-agent-<name>` (`mobile-agent-daemon`, `mobile-agent-mirror`, `mobile-agent-protocol`, `mobile-agent-wire`, `mobile-agent-ios`, `mobile-agent-android`, `mobile-agent-simulator`, `mobile-agent-mcp`, `mobile-agent-bench`, `mobile-agent-agent-ios` or a better name for the iPhone runner; the CLI's package is `mobile-agent` so that `cargo install mobile-agent` gives the command), with `[lib] name` kept as today so that every `use daemon::...` stays and the bin names stay; dependencies declared by the new package names; `cargo publish --dry-run` per crate in dependency order green; `publish = false` on crates that should not ship (the bench harness, the iPhone runner if its build needs the signing team: say which and why). The notices and the README's crate list follow.

### D6. The first publish and trusted publishing
The first publish is the maintainer's by hand, crate by crate in dependency order with the exact commands listed in the task, since publishing claims the names for good; then a trusted publisher per crate on crates.io (the repository, the workflow file, the environment), and `release.yml` gains a `publish-crates` job in the `release` environment with `id-token: write`, running `cargo publish` in order with the token exchanged through `rust-lang/crates-io-auth-action`, after the binaries' job; `cargo install mobile-agent --version 0.1.0-alpha.1` verified on a clean account; later alphas publish both from one dispatch.

## Risks / Trade-offs

- A name once published cannot be reused and a version cannot be deleted, only yanked: the dry runs and the maintainer's own hand on the first publish.
- The tag ruleset's bypass must be exactly the workflow's deployment; if GitHub's rulesets cannot express it, the fallback is the maintainer creating the tag by hand in the web form and the workflow running on the tag (the research says which).
- The macOS runner's Xcode decides the Simulator reader the alpha carries; the README says which Xcode and iOS runtimes the alpha was built and run with.
- Renaming packages touches every manifest and the lockfile; the lib names kept hold the source still.
