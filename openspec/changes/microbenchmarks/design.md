# Design

## Context

The archived change `mobile-automation-foundation` (`openspec/changes/archive/2026-10-07-mobile-automation-foundation/design.md`, design D1 to D12) measured the model end to end: spikes S1 to S7 timed the platform mechanisms, and the harness of `crates/bench` (D10) timed primitives and flows through devices against Maestro and agent-device. What it never measured apart is the host-side work between a device's bytes and an agent's reply: minicbor's decode of a snapshot (S5 timed it once, 59.1 µs for a generated 500-node tree, on a spike's own model types, not the shipped `protocol` crate), the replica's matching of a read against the previous one, the listing with its names, roles, hidden nodes and refs, visibility and the bars, delta snapshots, the daemon's JSON wire, and the frame pipeline's downscale, hash and encode (S2 timed the encoders, before the shipped pipeline existed). Those paths are what `docs/overview.md` section 2 attributes the savings to, and what the earlier ranking's item 3 asks numbers for.

Constraints that shape the approach:

- The host is a shared Apple M1 Max (8 performance and 2 efficiency cores, 64 GiB, macOS 26.6.2) on which other sessions build, boot Simulators and run emulators. Every measured run so far waited for a 1-minute load under a bound (S5's `bench.sh` under 6, the 10.x reports under 4) and recorded it. Microbenchmarks are more sensitive to that noise than flow timings, since they measure microseconds, and the same rule binds them: measure only on a quiet host, record the load.
- CI is not a measuring environment: GitHub's hosted runners are shared virtual machines, and the account's Actions are blocked by its spending limit at the time of writing. The suite compiles there and runs here.
- The repository's existing bench inputs are reusable: the mirror's fixtures (`crates/mirror/fixtures/`, the 500-cell `grid`, the 200-row `list`, Bluesky's screens) with their loader in `crates/mirror/tests/support/mod.rs`, its scripted `FakeTarget` on a fake clock (`crates/mirror/src/testing.rs`), the protocol's 41 golden samples (`crates/protocol/tests/common/samples.rs`), the daemon's fake targets (`MOBILE_AGENT_FAKE_TARGETS`, `crates/daemon/src/fake/`), and the Simulator pipeline's pure functions (`crates/simulator/src/pipeline.rs`: `fit_within`, `scale_bgra`, `thumbnail_hash`, `content_hash`).
- The sizes to measure at are the ones the reports used: the 500-cell fixture screens (546 nodes as XCTest returns the SwiftUI one, 573 as the agent reads the Compose one), the 1,049-node React Native screen on the emulator, S5's 10,000 events and 1,000 requests, and frames of the iPhone 17 Simulator (1206x2622 pixels) downscaled to the 1000-pixel long edge, 460x1000 as S2 measured.

Research note: `docs/research/microbenchmarks.md` (task 1.1). Spike report: `docs/spikes/s8-bench-harness.md` (task 1.2).

## Goals / Non-Goals

**Goals:**
- Numbers for what each host-side mechanism costs, on the same host and at the same sizes as the device reports, so that `docs/overview.md` can say what a mechanism costs beside what it saves.
- A regression check that runs in minutes without a device, before a device run and before a change is accepted: a quiet run compared against a committed baseline, with a threshold set from measured noise rather than guessed, and allocation counts compared exactly.
- Keep the core lean: no benchmark-only feature flags or hooks in the crates. Benches use the public API of each crate and the test support that exists; where a hot path has no public entry point, the benchmark goes through the public call that contains it, and attribution within is a profiler's job when a regression shows.
- Decide the harness library by measurement, as D3, D4, D6 and D7 were decided.

**Non-Goals:**
- Running the suite in CI, on hosted or self-hosted runners, or publishing a history service. The CI change decides between instruction counts on Linux and a dedicated runner; this design keeps the suite's output machine-readable so either can consume it.
- Optimizing anything the numbers point at. Findings are recorded as follow-ups.
- Benchmarking the Android agent's Kotlin codec on a device (S5 and task 10.3 did), the adb client (S6 did) or the Simulator's private calls (S3 and S4 did).
- A general-purpose benchmarking service in `crates/bench`: `micro` runs `cargo bench`, parses one harness's output and compares; nothing more.

## Decisions

### D13. Harness library, chosen by spike S8 on this host's noise
Candidates, from the research note: criterion (the incumbent: statistics with confidence intervals, `--save-baseline` and `--baseline`, `raw.csv` as its stable machine-readable output, `significance_level` and `sample_size` per group, `--noplot` to skip the HTML reports and their dependencies), divan (one attribute per benchmark, `--sample-count` and `--sample-size` on the command line or `DIVAN_*` in the environment, `AllocProfiler` for allocations per iteration, text output only, no baselines of its own), tango (paired runs of two builds interleaved in one process, which cancels noise the other two cannot; Context7 does not index it, so the note reads its repository), glassbench (criterion's model with an SQLite history), and iai-callgrind with CodSpeed's compatibility layers, which count instructions under valgrind and run on Linux only, kept for the CI change. The spike builds the same two benchmarks under each candidate that builds here: `protocol`'s decode of a generated 500-node snapshot, and a variant of it made about 5% slower by a calibrated amount of extra work in the timed region. It runs each ten times on a quiet host (1-minute load under 4, nothing of the guard's process list using CPU) and ten times under a synthetic load of four busy cores, and records per harness the coefficient of variation of the reported median across runs, how many of the ten paired runs told the 5% variant apart in the right direction, the wall time per run, the dependency count and whether the output is machine-readable per benchmark without parsing prose. Gate: on the quiet host, median CV at or under 2% and the variant told apart in at least 9 of 10 runs; among the harnesses that pass, the one with machine-readable output and the fewest dependencies. The result replaces this paragraph's candidates with the choice and its numbers; the threshold of D16 and the guard's bound of D15 follow from the same measurements. If no harness passes on the quiet host, the suite still ships, with the sample settings raised until one passes, and the report says so.

### D14. What is benchmarked, at which sizes, with what inputs
One `benches/` directory per crate, each benchmark file one `[[bench]]` with `harness = false`, verifying its result outside the timed region as S5's harness did, with the inputs built once before timing:

- `protocol`: `Message::encode`, `Message::decode` and `Message::to_vec` of the `response_snapshot` golden sample (small), of a generated snapshot of 500 nodes in S5's shape (depth 7, a 16-entry string table, resource ids on 55% of nodes, text on 50%, descriptions on 12%, a scroll node per list, seeded so the bytes are stable) and of one of 1,049 nodes in the React Native shape (each cell a view holding a text); `encode` and `decode` of 10,000 tree events and of 1,000 requests in S5's mix; `write_frame` of each, and `FrameDecoder::push` and `next_frame` over the event stream fed in 64 KiB pieces. The generator lives in `benches/support/`, with a test in the crate's tests asserting the node counts and the encoded byte lengths, so the inputs cannot drift silently.
- `mirror`: on the `grid` fixture (510 nodes), the `list` fixture, `bluesky-typeahead-android` and a new `grid-rn` fixture of 1,049 nodes in the React Native shape, through `Mirror` on a `FakeTarget`: `pump` for the first read (convert, hash, allocate identities), `pump` after a `Show` of the same screen (match with no changes), after one row's text changed, after a system window added and removed, and after a `Reconnected` item (start over); `snapshot` interactive and full right after a read (view, hints, listing, refs, verdict) and again unchanged (every ref a table hit); `visibility` of a row inside the list, `scroll_viewport` of a point in it and `uncovered` of the screen under a keyboard window; `delta_snapshot` after one row changed and `diff` against the unchanged baseline; `wait` for text that is already on screen (one evaluation) and over the `events-typing` timeline (one evaluation per item); `settle` of a quiet screen with frames and without, on the fake clock, which costs no real time. The fixture loader is included from `tests/support/mod.rs` by path, as the tests include it.
- `daemon`: `wire::Request::parse` of a snapshot request line, `wire::reply_line` of a success carrying the `grid` listing as the CLI prints it, and a `snapshot` with `interactive` set through the daemon's socket to a fake target showing its 500-cell screen, one request per iteration against a daemon started once with the test support's `Builder`, which is the host's whole path less the CLI process.
- `simulator`: `scale_bgra` of a 1206x2622 BGRA frame to the size `fit_within` gives for 1000, `thumbnail_hash` and `content_hash` of the frame, the JPEG encode of the scaled output at quality 80 through the shipped encoder, and the four in sequence as the frame thread runs them; the encoder's benchmark is macOS only, behind `cfg(target_os = "macos")`, the pure functions everywhere the crate builds. The crate keeps `pipeline` and `macos::encode` private today; the benches reach them through public re-exports of the pure functions, `FrameView` and `Encoder` from the crate root, the smallest change, and no benchmark-only module or feature.
- `android`: the emulator `FrameHasher::key` of a 540x1200 RGB888 frame, which `android::emulator` already exports.

Allocations per iteration come from a counting global allocator in the bench binaries of `protocol`, `mirror` and `daemon` (divan's `AllocProfiler` when divan is chosen, else thirty lines over `System` in `benches/support/`), reported beside the time; they are deterministic, so the comparison flags any change (D16).

### D15. The runner: `mobile-agent-bench micro`
A subcommand of the harness binary, not a shell script, so its guard, parser and comparison have tests. `micro [--wait <minutes>] [--max-load <n>] [--threshold <percent>] [--filter <name>] [--save-baseline] [--out <dir>]`:

1. The guard reads the 1-minute load average (`sysctl vm.loadavg` on macOS, `/proc/loadavg` on Linux) and lists processes using more than 5% of a core whose names match the builders and devices the reports waited for (`cargo`, `rustc`, `gradle`, `xcodebuild`, `kotlinc`, `java`, `qemu-system`, `emulator`, `Simulator`, `com.apple.CoreSimulator`), excluding its own process tree. Quiet means load under `--max-load` (default 4, the reports' bound; D13 may lower it) and no such process. Otherwise it exits 2 naming what it found, or with `--wait` checks again every 30 s until the limit, then exits 2. S5's `bench.sh` measured anyway after 20 minutes; `micro` never does, which is the rule for every measured run.
2. It runs `cargo bench --workspace --benches` in the release profile with the harness's flags for the sample settings of D13 and its machine-readable output, `--filter` passed through, and reads the output into one value: per benchmark its id (`crate/bench/name`), median, spread (the harness's interval or the sample percentiles), sample count and allocations.
3. It compares that value against `reports/micro/baseline.json` (D16) and renders `report.json` and `report.md` from it, as `run` renders its reports from one value, into `--out` or `target/bench/micro/<UTC start time>/`; `--save-baseline` also writes the baseline file.
4. Exit status: 0, 1 on any regression, 2 when the host was busy or the run could not complete.

`just micro` runs it (`cargo run -p bench --release -- micro "$@"`).

### D16. The baseline, the threshold and what counts as a regression
`reports/micro/baseline.json` is committed: `schema_version`, `provenance` (as the device reports: hardware, cores, memory, OS, commit and dirty flag, the Rust toolchain, the harness library and version, the sample settings, the load averages at start and end, the UTC time) and `benchmarks[]` with `id`, `median_ns`, `spread_ns` (low and high), `samples` and, where measured, `allocations` and `bytes_allocated` per iteration. A time regresses when the measured median exceeds the baseline's by more than the threshold, whose default is twice the quiet-host median CV the spike measured for the chosen harness, with a floor of 5%, recorded here by task 1.2; improvements past the same threshold are reported too, so a baseline that was measured on a busier host than this run shows as such. Allocations compare exactly. New and missing benchmarks are listed, not failed. The baseline is refreshed only by a run that passed the guard, through `--save-baseline`, and its diff is reviewed with the change that made it: a regression a change accepts is visible in that diff, with the provenance that says what it was measured on. A toolchain bump re-baselines in the same way; the provenance records the compiler, so a change in the numbers without a change in the code has its cause on record.

### D17. Where the numbers go
`README.md`'s Measured section gains a table of host costs from the baseline (a 500-node snapshot decoded, a read of the 500-cell screen taken in, its interactive listing, a frame downscaled, hashed and encoded, a snapshot through the daemon's socket), and `docs/overview.md` section 2 states each mechanism's host cost beside what it saves on a device, with section 3's "what was not compared" updated. `crates/bench/README.md` documents `micro`; each crate's README lists `benches/` in its layout; `reports/micro/README.md` says how to refresh the baseline and read a report. `docs/overview.md` section 7's note on numbers for an MCP surface stays as is.

## Delivery process

The rules of the archived design's Delivery process bind this change unchanged: research first, spikes before construction, measured decisions, tests first with red-then-green evidence, atomic commits in `type(scope): summary` form with no attribution trailers, validation and fix after every task (`cargo build --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --check`, `cargo test --workspace`, `openspec validate`, a diff review against the spec), installs through Socket Firewall (`sfw cargo add`), the pinned toolchain, and a recap before each dispatch. Two rules are specific here:

- **Quiet host.** Every number that goes into a report, the baseline or a design paragraph comes from a run that passed the guard of D15 (the spike applies the same check by hand before `micro` exists), with the load averages recorded beside it. A number measured on a busy host is not recorded.
- **Disjoint files.** Task 2.1 adds the dev-dependency to every crate in one commit so that `Cargo.lock` changes once; the suite tasks 2.2 to 2.5 then touch only their own crate, and 3.1 only `crates/bench`, so they can run as separate implementers in separate worktrees, each with its own `target/`.

## Risks / Trade-offs

- [The host's noise defeats a 5% threshold even when quiet] → the spike measures it before the threshold is set; if the quiet CV is above 2.5%, the threshold rises with it and the report says so, and allocation counts, which do not vary, carry the fine-grained check.
- [Benches add build time to `just lint` and CI] → `cargo clippy --all-targets` already compiles the tests; the benches add one binary per crate with one dependency, measured by the spike's dependency count. The harness library is a dev-dependency only.
- [A fake-clock `settle` or `wait` blocks on real time somewhere] → the mirror's tests run them in milliseconds on the fake clock; the benchmark asserts the iteration's elapsed real time stays under a bound, and if it does not, the benchmark measures the evaluation alone and the design records it.
- [The daemon's socket benchmark starts a process and measures a round trip, so its number includes the kernel's socket cost] → that is the point of it: the host's whole path less the CLI process, to set beside the harness's `warm-snapshot` through a CLI process.
- [The turbojpeg static link makes the simulator bench macOS-only] → the pure pipeline functions bench everywhere; the encoder's benchmark is gated on macOS, as its code is.
- [The baseline drifts with the toolchain or the machine] → provenance carries both; a baseline from another machine is reported as such in the comparison header, and the comparison still runs.
- [Microbenchmarks reward the wrong thing] → the suite measures the paths the reports attribute savings to, at the sizes they measured; it adds no path for its own sake, and a benchmark of a path no report cites is not added.

## Migration Plan

Nothing deployed changes. New `benches/` directories, a new subcommand, a new committed baseline and reports directory. Rolling back is removing them.
