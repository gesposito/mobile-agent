# Design

## Context

The archived change `mobile-automation-foundation` (`openspec/changes/archive/2026-10-07-mobile-automation-foundation/design.md`, design D1 to D12) measured the model end to end: spikes S1 to S7 timed the platform mechanisms, and the harness of `crates/bench` (D10) timed primitives and flows through devices against Maestro and agent-device. What it never measured apart is the host-side work between a device's bytes and an agent's reply: minicbor's decode of a snapshot (S5 timed it once, 59.1 µs for a generated 500-node tree, on a spike's own model types, not the shipped `protocol` crate), the replica's matching of a read against the previous one, the listing with its names, roles, hidden nodes and refs, visibility and the bars, delta snapshots, the daemon's JSON wire, and the frame pipeline's downscale, hash and encode (S2 timed the encoders, before the shipped pipeline existed). Those paths are what `docs/overview.md` section 2 attributes the savings to, and what the earlier ranking's item 3 asks numbers for.

Constraints that shape the approach:

- The host is a shared Apple M1 Max (8 performance and 2 efficiency cores, 64 GiB, macOS 26.6.2) on which other sessions build, boot Simulators and run emulators. Every measured run so far waited for a 1-minute load under a bound (S5's `bench.sh` under 6, the 10.x reports under 4) and recorded it. Microbenchmarks are more sensitive to that noise than flow timings, since they measure microseconds, and the same rule binds them: measure only on a quiet host, record the load.
- CI is not a measuring environment: GitHub's hosted runners are shared virtual machines, and the account's Actions are blocked by its spending limit at the time of writing. The suite compiles there and runs here.
- The repository's existing bench inputs are reusable: the mirror's fixtures (`crates/mirror/fixtures/`, the 500-cell `grid`, the 200-row `list`, Bluesky's screens) with their loader in `crates/mirror/tests/support/mod.rs`, its scripted `FakeTarget` on a fake clock (`crates/mirror/src/testing.rs`), the protocol's 41 golden samples (`crates/protocol/tests/common/samples.rs`), the daemon's fake targets (`MOBILE_AGENT_FAKE_TARGETS`, `crates/daemon/src/fake/`), and the Simulator pipeline's pure functions (`crates/simulator/src/pipeline.rs`: `fit_within`, `scale_bgra`, `thumbnail_hash`, `content_hash`).
- The sizes to measure at are the ones the reports used: the 500-cell fixture screens (546 nodes as XCTest returns the SwiftUI one, 573 as the agent reads the Compose one), the 1,049-node React Native screen on the emulator, S5's 10,000 events and 1,000 requests, and frames of the iPhone 17 Simulator (1206x2622 pixels) downscaled to the 1000-pixel long edge, 460x1000 as S2 measured.

Research note: `docs/research/microbenchmarks.md` (task 1.1). Spike report: `docs/spikes/s8-bench-harness.md` (task 1.2).

## Goals / Non-Goals

**Goals:**
- Numbers for what each host-side mechanism costs, on the same host and at the same sizes as the device reports, so that `docs/overview.md` can say what a mechanism costs beside what it saves.
- A regression check that runs in minutes without a device, before a device run and before a change is accepted: a quiet run compared against a committed baseline, with a threshold set from measured noise rather than guessed, and allocation counts compared exactly.
- Keep the core lean: no benchmark-only feature flags or hooks in the crates. Benches use the public API of each crate and the test support that exists; where a hot path has no public entry point, the benchmark goes through the public call that contains it, and attribution within is a profiler's job when a regression shows.
- Decide the harness library by measurement, as D3, D4, D6 and D7 were decided.

**Non-Goals:**
- Running the suite in CI, on hosted or self-hosted runners, or publishing a history service. The CI change decides between instruction counts on Linux and a dedicated runner; this design keeps the suite's output machine-readable so either can consume it.
- Optimizing anything the numbers point at. Findings are recorded as follow-ups.
- Benchmarking the Android agent's Kotlin codec on a device (S5 and task 10.3 did), the adb client (S6 did) or the Simulator's private calls (S3 and S4 did).
- A general-purpose benchmarking service in `crates/bench`: `micro` runs `cargo bench`, parses one harness's output and compares; nothing more.

## Decisions

### D13. Harness library, chosen by spike S8 on this host's noise
criterion 0.8.2 with its default features off (no `rayon`, no `plotters`), a dev-dependency of each crate with benches, run with `--noplot` and its default sample settings: 3 s of warm-up, then 100 linear samples aiming at 5 s of measurement, and 100,000 bootstrap resamples for a 95% interval, about 10 s per benchmark. `micro` reads each benchmark's median point estimate and interval from `$CRITERION_HOME/<id>/new/estimates.json` and its sample count from `sample.json`. Criterion's book calls those files private and free to change, and the stable `raw.csv` needs the `csv_output` feature, which 0.8.2 deprecates. The version therefore stays pinned in `Cargo.lock`, and the parser is tested on files S8 recorded. Criterion counts no allocations; D14's counting allocator does. Shorter sample settings would need S8's measurement repeated at them before the threshold of D16 could rely on them.

Spike S8 (`docs/spikes/s8-bench-harness.md`) timed two bodies under criterion, divan 0.1.21, tango-bench 0.8.0 and glassbench 0.5.0, each with its default settings. The first is the shipped crate's `Message::decode` of a generated 500-node snapshot response in S5's shape: 21,410 bytes, about 125 µs, with the decoded message dropped inside the timed region. The second is a variant made 5.06% slower by black-boxed extra work. Each harness ran ten times on a quiet host, every run starting at a 1-minute load between 2.89 and 3.95, and ten times under four busy cores, at loads up to 7.99.

On the quiet host, the coefficient of variation of the reported `decode` value across the ten runs was 1.15% for criterion, 1.37% for divan, 1.73% for tango and 2.16% for glassbench. The variant came out slower in 10, 10, 10 and 9 of the ten runs; criterion's 95% intervals of the two medians were apart in all ten, and tango marked all ten significant. Glassbench fails the gate on its CV. Of the three that pass, only criterion writes a machine-readable result per benchmark: divan prints a text table, and tango dumps raw samples but states its means and verdict in text and its exit status. Criterion is chosen, although it adds 48 crates to a lock file, 23 of them new to this workspace's, against divan's 17 and tango's 80, and takes 19.6 s per run of two benchmarks against 0.1 and 0.2 s.

Under four busy cores criterion held best: CV 0.34%, and the variant told apart in 10 of 10 runs with its intervals apart. Tango fell to 8 of 10 (CV 7.38%), from a preempted worker's samples within its 100 ms default. Divan's difference within a run ranged from +0.3% to +8.6%.

Alternatives:

- divan: passes and is the lightest, with allocation counting built in, but its output is a text table and its last release is of 2025-04;
- tango: passes, with the tightest paired difference on a quiet host, but it compares builds rather than a committed baseline and fails under load with its defaults;
- glassbench: fails, with one mean per run, no outlier handling, and 184 crates including C builds;
- Gungraun (formerly iai-callgrind) and CodSpeed's instruction counts: Valgrind has no arm64 macOS port, so neither runs here; both are left to the CI change.

### D14. What is benchmarked, at which sizes, with what inputs
One `benches/` directory per crate, each benchmark file one `[[bench]]` with `harness = false`, verifying its result outside the timed region as S5's harness did, with the inputs built once before timing:

- `protocol`: `Message::encode`, `Message::decode` and `Message::to_vec` of the `response_snapshot` golden sample (small), of a generated snapshot of 500 nodes in S5's shape (depth 7, a 16-entry string table, resource ids on 55% of nodes, text on 50%, descriptions on 12%, a scroll node per list, seeded so the bytes are stable) and of one of 1,049 nodes in the React Native shape (each cell a view holding a text); `encode` and `decode` of 10,000 tree events and of 1,000 requests in S5's mix; `write_frame` of each, and `FrameDecoder::push` and `next_frame` over the event stream fed in 64 KiB pieces. The generator lives in `benches/support/`, with a test in the crate's tests asserting the node counts, the encoded byte lengths and a digest of each dataset, so the inputs cannot drift silently. The 1,049-node snapshot is a reconstruction from S1's per-window counts and the fixture's source, not a capture, and carries no scroll semantics, since the grid fits its scroll view.
- `mirror`: on the `grid` fixture (510 nodes), the `list` fixture, `bluesky-typeahead-android` and a new `grid-rn` fixture of 1,049 nodes in the React Native shape, through `Mirror` on a `FakeTarget`: `pump` for the first read (convert, hash, allocate identities), `pump` after a `Show` of the same screen (match with no changes), after one row's text changed, after a system window added and removed, and after a `Reconnected` item (start over); `snapshot` interactive and full right after a read (view, hints, listing, refs, verdict) and again unchanged (every ref a table hit); `visibility` of a row inside the list, `scroll_viewport` of a point in it and `uncovered` of the screen under a keyboard window; `delta_snapshot` after one row changed and `diff` against the unchanged baseline; `wait` for text that is already on screen (one evaluation) and over the `events-typing` timeline (one evaluation per item); `settle` of a quiet screen with frames and without, on the fake clock, which costs no real time. The fixture loader is included from `tests/support/mod.rs` by path, as the tests include it.
- `daemon`: `wire::Request::parse` of the line the CLI sends for `snapshot -i`, `wire::reply_line` of the daemon's own reply to it for the fake fixture's 500-cell Big tab (505 elements with the tab bar, a 45 KB line, its `readMs` fixed so the bytes allocated do not vary with the digits), and that `snapshot` through the daemon's socket to the fake target, one request per iteration against a daemon started once with the test support's `Builder`, which is the host's whole path less the CLI process; the daemon is stopped before the wire benchmarks run, so its process stays out of them.
- `simulator`: `scale_bgra` of a 1206x2622 BGRA frame to the size `fit_within` gives for 1000, `pixels_hash`, `thumbnail_hash` and `content_hash` of the 460x1000 output, which is what the frame thread hashes (`pixels_hash` decides delivery, `content_hash` leaves the status bar out), the JPEG encode of the output at quality 80 through the shipped encoder, and the steps in the order the frame thread runs them; the frame is a synthetic Expo Big tab, the screen S2 encoded, so the encode time stands beside S2's; the encoder's benchmark is macOS only, behind `cfg(target_os = "macos")`, the pure functions everywhere the crate builds. The crate keeps `pipeline` and `macos::encode` private today; the benches reach them through public re-exports of the pure functions, `FrameView` and `Encoder` from the crate root, the smallest change, and no benchmark-only module or feature.
- `android`: the emulator `FrameHasher::key` of a 540x1200 RGB888 frame, which `android::emulator` already exports.

Allocations per iteration come from a counting global allocator in the bench binaries of `protocol`, `mirror` and `daemon` (divan's `AllocProfiler` when divan is chosen, else thirty lines over `System` in `benches/support/`), reported beside the time; they are deterministic, so the comparison flags any change (D16).

### D15. The runner: `mobile-agent-bench micro`
A subcommand of the harness binary, not a shell script, so its guard, parser and comparison have tests. `micro [--wait <minutes>] [--max-load <n>] [--threshold <percent>] [--filter <name>] [--save-baseline] [--out <dir>]`:

1. The guard reads the 1-minute load average (`sysctl vm.loadavg` on macOS, `/proc/loadavg` on Linux) and lists processes using more than 5% of a core whose names match the builders and devices the reports waited for (`cargo`, `rustc`, `gradle`, `xcodebuild`, `kotlinc`, `java`, `qemu-system`, `emulator`, `Simulator`, `com.apple.CoreSimulator`), excluding its own process tree. Quiet means load under `--max-load` and no such process. The default bound is 4, the reports' bound, which spike S8 kept. Its quiet series ran at 1-minute loads of 2.89 to 3.95 with criterion's CV at 1.15%. Four busy cores, at loads up to 7.99, moved criterion's median by 4.4%, most of D16's threshold. Otherwise it exits 2 naming what it found, or with `--wait` checks again every 30 s until the limit, then exits 2. S5's `bench.sh` measured anyway after 20 minutes; `micro` never does, which is the rule for every measured run.
2. It runs `cargo bench --workspace --bench codec --bench mirror --bench daemon --bench frames` in the release profile, naming the bench targets, with the harness's flags for the sample settings of D13 and its machine-readable output, `--filter` passed through. Cargo hands the arguments after `--` to every bench target, the libraries' and binaries' libtest harness included, which rejects `--noplot` (task 2.4 found `cargo bench -p daemon -- --noplot` refused that way), so the crates' `[lib]` and `[[bin]]` sections also set `bench = false`, criterion's documented fix, and a developer's `cargo bench -p mirror -- pump` works as well. It reads the output into one value: per benchmark its id (`crate/bench/name`), median, spread (the harness's interval or the sample percentiles), sample count and allocations.
3. It compares that value against `reports/micro/baseline.json` (D16) and renders `report.json` and `report.md` from it, as `run` renders its reports from one value, into `--out` or `target/bench/micro/<UTC start time>/`; `--save-baseline` also writes the baseline file.
4. Exit status: 0, 1 on any regression, 2 when the host was busy or the run could not complete.

`just micro` runs it (`cargo run -p bench --release -- micro "$@"`).

### D16. The baseline, the threshold and what counts as a regression
`reports/micro/baseline.json` is committed: `schema_version`, `provenance` (as the device reports: hardware, cores, memory, OS, commit and dirty flag, the Rust toolchain, the harness library and version, the sample settings, the load averages at start and end, the UTC time) and `benchmarks[]` with `id`, `median_ns`, `spread_ns` (low and high), `samples` and, where measured, `allocations` and `bytes_allocated` per iteration. A time regresses when the measured median exceeds the baseline's by more than the threshold. Its default is 5%: twice the chosen harness's quiet-host CV, with a floor of 5%, where spike S8 measured criterion's CV at 1.15%, and twice that, 2.3%, falls under the floor. Improvements past the same threshold are reported too, so a baseline that was measured on a busier host than this run shows as such. A time regression or improvement also needs the measured median outside the 95% interval the baseline recorded around its own median (task 3.3): the first run against the baseline (task 3.2) found 67 of 68 benchmarks within 0.2% at the median of their absolute differences, and one, `protocol/decode/requests-1k`, 5.9% slower by median alone, 141.4 against 133.5 µs, although inside the baseline's interval of 132.2 to 143.5 µs. Its samples, like `protocol/decode/events-10k`'s, fell in two modes 5 to 15% apart, about half in each, so the median landed in either mode from run to run while the interval said so; every other benchmark's interval is within 1% of its median. Task 3.4 found the cause: criterion runs sample i under `alloca::with_alloca(i % page_size)`, a stack lowered by about i bytes in 16-byte steps on arm64, so samples fall in blocks of 16 that share one stack offset, and these two decode loops run 35 to 56% slower at one or two of the eight offsets, which ones depending on where the process's stack starts in its page, set by the environment's size, so that the slow share, and with it the median, followed the layout rather than the code; dropping the decoded messages outside the timed region changed nothing. The two benchmarks therefore run on a stack pinned to a page boundary, one alignment timed, the same on every run, in exchange for criterion's deliberate variation, which every other benchmark keeps: in three runs after it, requests-1k's samples stayed within +2% block to block and events-10k's within +5%. The three snapshot decodes show the same sensitivity, one block of eight 106 to 127% slower in some layouts, which leaves their medians where they are while one block of eight is slow; it is recorded as a follow-up on the decoder, whose inner loop runs at one alignment in the daemon too. Allocations compare exactly. New and missing benchmarks are listed, not failed. The baseline is refreshed only by a run that passed the guard, through `--save-baseline`, and its diff is reviewed with the change that made it: a regression a change accepts is visible in that diff, with the provenance that says what it was measured on. A toolchain bump re-baselines in the same way; the provenance records the compiler, so a change in the numbers without a change in the code has its cause on record.

### D17. Where the numbers go
`README.md`'s Measured section gains a table of host costs from the baseline (a 500-node snapshot decoded, a read of the 500-cell screen taken in, its interactive listing, a frame downscaled, hashed and encoded, a snapshot through the daemon's socket), and `docs/overview.md` section 2 states each mechanism's host cost beside what it saves on a device, with section 3's "what was not compared" updated. `crates/bench/README.md` documents `micro`; each crate's README lists `benches/` in its layout; `reports/micro/README.md` says how to refresh the baseline and read a report. `docs/overview.md` section 7's note on numbers for an MCP surface stays as is.

## Delivery process

The rules of the archived design's Delivery process bind this change unchanged: research first, spikes before construction, measured decisions, tests first with red-then-green evidence, atomic commits in `type(scope): summary` form with no attribution trailers, validation and fix after every task (`cargo build --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo fmt --check`, `cargo test --workspace`, `openspec validate`, a diff review against the spec), installs through Socket Firewall (`sfw cargo add`), the pinned toolchain, and a recap before each dispatch. Two rules are specific here:

- **Quiet host.** Every number that goes into a report, the baseline or a design paragraph comes from a run that passed the guard of D15 (the spike applies the same check by hand before `micro` exists), with the load averages recorded beside it. A number measured on a busy host is not recorded.
- **Disjoint files.** Task 2.1 adds the dev-dependency to every crate in one commit so that `Cargo.lock` changes once; the suite tasks 2.2 to 2.5 then touch only their own crate, and 3.1 only `crates/bench`, so they can run as separate implementers in separate worktrees, each with its own `target/`.

## Risks / Trade-offs

- [The host's noise defeats a 5% threshold even when quiet] → the spike measures it before the threshold is set; if the quiet CV is above 2.5%, the threshold rises with it and the report says so, and allocation counts, which do not vary, carry the fine-grained check.
- [Benches add build time to `just lint` and CI] → `cargo clippy --all-targets` already compiles the tests; the benches add one binary per crate with one dependency, measured by the spike's dependency count. The harness library is a dev-dependency only.
- [A fake-clock `settle` or `wait` blocks on real time somewhere] → the mirror's tests run them in milliseconds on the fake clock; the benchmark asserts the iteration's elapsed real time stays under a bound, and if it does not, the benchmark measures the evaluation alone and the design records it.
- [The daemon's socket benchmark starts a process and measures a round trip, so its number includes the kernel's socket cost] → that is the point of it: the host's whole path less the CLI process, to set beside the harness's `warm-snapshot` through a CLI process.
- [The turbojpeg static link makes the simulator bench macOS-only] → the pure pipeline functions bench everywhere; the encoder's benchmark is gated on macOS, as its code is.
- [The baseline drifts with the toolchain or the machine] → provenance carries both; a baseline from another machine is reported as such in the comparison header, and the comparison still runs.
- [Microbenchmarks reward the wrong thing] → the suite measures the paths the reports attribute savings to, at the sizes they measured; it adds no path for its own sake, and a benchmark of a path no report cites is not added.

## Migration Plan

Nothing deployed changes. New `benches/` directories, a new subcommand, a new committed baseline and reports directory. Rolling back is removing them.

## Open Questions

- CI: instruction counts under valgrind on the Linux leg (iai-callgrind or CodSpeed's criterion and divan layers, free for public repositories) against timings on a dedicated Mac runner; decided by the CI change once the account's Actions run again. The suite's machine-readable output and the baseline's schema are kept so that either can consume them.
- Whether the daemon's socket benchmark should also drive `click` and `wait --settle` on the fake target, which the fake's realtime module can play; added if the first numbers show the snapshot path is not where the host's time goes.

Follow-ups the numbers point at, recorded as candidates for later changes, as the Non-Goals have it; this change implements none of them:

- The release profile: built with S5's fat LTO and one codegen unit, the 500-node snapshot's `encode` took 25.4 µs, against 54.4 µs under the workspace's release profile in the first baseline, taken the same day, its `write_frame` and `to_vec` fell likewise to 25.6 and 27.4 µs, and its `decode` stayed at 119.6 against 123.8 µs (task 3.2). The daemon, the CLI and the Simulator reader are built with the default release profile; the two settings would halve their encodes, against longer builds here and in CI.
- The node decoder: under S5's profile it takes twice S5's derived decoder, 119.6 against 59.1 µs for the 500-node snapshot. The candidates are the heap stack of open nodes it keeps for the 256-level limit (`MAX_NODE_DEPTH` in `crates/protocol/src/snapshot.rs`) and how it preallocates arrays. Decoding is also sensitive to alignment (D16): under criterion's per-sample stack shift, one of the eight 16-byte offsets ran the three snapshot decodes 106 to 127% slower in some layouts, and the decodes of 1,000 requests and 10,000 events 35 to 56% slower at one or two offsets until those two were pinned to a page; the daemon's decode runs at whichever offset its thread's stack gives it.
- The replica's matching: a read matched unchanged costs about 2.1 times a cold acquisition, 208.3 against 97.4 µs on `grid`'s 510 nodes and 412.8 against 192.6 µs on `grid-rn`'s 1,049 (`mirror/pump/unchanged-*` against `mirror/pump/first-read-*`), with 3,114 against 2,092 and 7,334 against 4,180 allocations, so matching a screen that did not change costs more than building the replica from it.
- `removed_refs` in `Mirror::snapshot` (`crates/mirror/src/mirror.rs`): the refs the previous listing had and the new one lacks are found with a linear `contains` over the new listing's refs for each previous one, quadratic in the listing's length, so an unchanged interactive listing taken again costs more than the first, though it allocates less: 338.1 against 327.3 µs and 7,632 against 8,155 allocations for `grid`'s 505 refs, 419.7 against 404.4 µs for `grid-rn`'s.
- `wire::reply_line` (`crates/daemon/src/wire.rs`): writing the daemon's 45 KB reply to `snapshot -i` on the fake 500-cell Big tab takes 98.4 µs, 21 allocations and 295,346 bytes, since it serializes the data into a string of its own, copies it into the line and doubles the line's capacity at the end (task 2.4).
- The daemon's other `eprintln!` sites (task 2.6): those of `crates/daemon/src/server.rs` run on the main thread, where a failed write exits 101 without the clean-up, and the Android worker's two sites would end that worker. Only a daemon whose stderr pipe lost its reader, or a full disk, reaches them; the CLI's daemons log to a file.
- `Message::to_vec` against `encode`: over 10,000 events `to_vec` takes 1,442.9 µs and 30,040 allocations, `encode` into a reused buffer 716.6 µs and none. The sessions write each message with `write_frame` into an outbox that `poll_transmit` hands over with `std::mem::take` (`crates/protocol/src/session/`), which leaves an empty buffer behind, so a message written after a hand-over grows a new buffer as `to_vec` does; which of the two costs a session pays per message, with how many messages a hand-over carries, is to be measured.
- `just micro`'s builds and its guard: the recipe builds the runner (`cargo run -p bench --release`) before the guard and the suites after it. A cold run's build of the runner raises the 1-minute load that the guard then waits out, 90 s for the first baseline (task 3.2), and the suites' build ends right before the first measurement. Building both ahead of the run would spare the wait, and checking the host again once the suites are built would cover their build. The daemon's bench also starts its daemon under `--list`, which adds a few seconds to every filtered run (task 3.1).
