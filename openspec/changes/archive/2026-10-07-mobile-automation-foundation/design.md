# Design

## Context

See proposal.md for motivation. The constraints that shape the approach come from the platform investigation that preceded this change, kept privately:

- Neither OS exposes a CDP-like protocol. Android's only privileged UI primitive is the UI automation connection normally used by instrumentation; a shell-user process started with `app_process` may own it, because the connection records whoever connects as its owner and the Shell package holds the accessibility, event-injection and frame-buffer permissions. Only one such owner exists per device.
- On the iOS Simulator every primitive is reachable from the host process: CoreSimulator for lifecycle, SimulatorKit's input services for HID, the runtime's private accessibility client for trees, and the display surface for frames. These are private frameworks whose shapes changed in iOS 26 and Xcode 27, so transports must be negotiated at runtime.
- On a physical iPhone the only supported route is an XCTest bundle. That is a separate change.
- Emulators expose a gRPC controller for input and frame streaming when started with the control flag.
- agent-browser's daemon is pure Rust, speaks CDP directly, and its command grammar is what agents already know. The exact envelope, ref syntax, snapshot line format, delta snapshots and batch semantics to mirror are catalogued in the protocol research note.

Research notes (task group 2): `docs/research/protocol.md`, `docs/research/simulator.md`, `docs/research/android-agent.md`. Spike reports: `docs/spikes/s1-android-ownership.md`, `docs/spikes/s2-simulator-frames.md`, `docs/spikes/s3-simulator-hid.md`, `docs/spikes/s4-simulator-ax.md`, `docs/spikes/s5-wire-format.md`, `docs/spikes/s6-adb-transport.md`, `docs/spikes/s7-emulator-grpc.md`.

## Goals / Non-Goals

**Goals:**
- Prove the live-mirror model end to end on Android and Simulator with numbers, not claims.
- Keep every host-side component in Rust and keep the only non-Rust component, the Android agent, as small as a single dex.
- Make each backend swappable behind the protocol so later changes can add physical iOS, an in-process agent, and CDP or MCP edges without touching the mirror or the CLI.
- Partition work so independent agents can implement crates in parallel with disjoint files.
- Keep the core lean: a safeguard one platform, toolkit, version or entry method needs is gated on that case and costs the others nothing, even at the price of a separate path (task 10.30 keeps `fill`'s read-back hold after typed keys alone, where an app's re-sets can interleave with the entry, since the 200 ms it cost every fill took the emulator's text entry from 24 ms to 224 ms in task 10.26).

**Non-Goals:**
- Physical iOS devices, tvOS, HarmonyOS, web, desktop.
- Video encoding on Android beyond what the emulator controller streams.
- MCP server, CDP-subset endpoint, decision-model hooks, agent-browser provider integration.
- React Native specific inspection. React Native apps are exercised only as fixtures through the accessibility layer.

## Decisions

### D1. Persistent host daemon with a thin CLI
A daemon holds device connections, replicas and sessions; the CLI is a client over a Unix socket that auto-starts the daemon. Alternative: one-shot CLI that connects per command. Rejected because attach and replica warm-up dominate latency and the whole point is amortizing them; agent-browser and agent-device both converged on the same shape. `shutdown` answers only once the daemon has stopped its targets, which it waits up to 5 s for, and removed its socket and sidecar files, so a client that starts another daemon right after never meets the old one's Android agent still holding UI automation (task 8.16): on a fake target the daemon's reply takes 4.8 ms at the median of 20 runs (2.8 ms with no target attached), where a reply sent before the stop took 0.08 ms but left the socket in place until 7.7 ms, and on an emulator the `mobile-agent shutdown` command takes 35 ms with the Android agent's stop, where it took 7.8 ms with the reply sent first.

### D2. Android agent as a single-dex Kotlin program started with `app_process`
The agent is compiled with `kotlinc` against the platform jar and dexed with `d8`, pushed to `/data/local/tmp`, and started through `adb shell` with `app_process` as the shell user, the way scrcpy's server starts. It obtains the UI automation connection through reflection on the hidden constructor and connects with the accessibility service client, then uses the tree, event listener, input injection and screenshot APIs. Alternatives: an instrumentation APK started with `am instrument` (rejected: install step, signing, test-only package handling on some OEMs, still one owner); an accessibility service app (rejected: user toggle, no screenshots without consent, real-time gesture playback); the existing UIAutomator2 server (rejected: HTTP and JSON per node, its own idle waits). Fallback to an instrumentation APK is deferred to a later change if an OEM build refuses the shell path. openatx's current client already runs a jar through `app_process` with the same reflective construction, so the novelty here is the resident binary protocol and the event mirror, not the launch path. Input acknowledgements use `InputManagerGlobal.injectInputEvent(event, INJECT_INPUT_EVENT_MODE_WAIT_FOR_RESULT)`, whose return value is the accepted flag the spec asks for; S1 measured a tap (DOWN and UP) at 1.9 ms p50 and 3.1 ms p95 on the API 36 emulator. Neither `UiAutomation` overload qualifies: with `sync = true` both call `syncInputTransactions` around the tap and wait for the app to finish each event (public: 45.2 ms p50, 65 of 200 taps over 50 ms; hidden three-argument: 35.3 ms p50, 39 of 200 over), and with `sync = false` the injection is ASYNC and always reports success. The agent sets `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` after connecting and waits for an active window before its first snapshot, because the window list stays empty or partial for up to 55 ms. A refused attach raises `IllegalStateException` ending in `already registered!`, whose binder proxy is the holder's and names no process, so the conflict report names the likely holder from `ps`, where `app_process` holders appear under their `setArgV0` names. Screenshots use only the public `UiAutomation.takeScreenshot()`, because the hidden screenshot plumbing changed in Android 16, 16 QPR2 and 17. The Kotlin standard library alone dexes to 2.28 MB, so the shipped agent is shrunk with R8 (task 4.10).

### D3. ADB through the local server protocol, spoken by the driver's own client; no `adb` binary in the hot path
The driver speaks the adb server protocol on port 5037 with a small client in `crates/android`. It opens one server connection per request and uses:

- `host:devices-l`, parsed so that every state is kept, including unauthorized, offline and `no permissions`;
- `shell,v2,raw:` for the exit status and separate stderr;
- sync `SEND` in 64 KiB chunks, each header written with its data;
- `host-serial:<serial>:forward` and `reverse:forward`, reading through the second status so device-side failures surface.

The driver reaches the agent by opening `localabstract:<name>` as a device service after `host:transport:<serial>`. No forward rule or host port exists to leak or to reinstall after a transport reconnect, and a missing agent fails the open with `closed` instead of yielding an empty connection. Spike S6 (`docs/spikes/s6-adb-transport.md`) measured these p50 and p95 times on the API 36 emulator, own client against the `adb` binary:

- device listing: 0.51 and 0.79 ms, against 16.73 and 18.68 ms;
- `echo ok` shell round trip: 5.71 and 9.16 ms, against 24.27 and 34.43 ms;
- push of the 663 KB agent jar: 9.88 and 12.66 ms, against 31.80 and 37.11 ms;
- 10 MiB push: 35.1 and 68.4 ms (285 MiB/s at p50), against 62.6 and 75.7 ms;
- service stream plus hello: 2.52 and 3.06 ms;
- forward setup plus first connect: 3.08 and 3.58 ms, against 22.30 and 24.88 ms;
- reverse setup, connect-out and first echo: 5.73 and 6.45 ms, against 23.85 and 26.52 ms.

However the connection was made, an echo round trip took 1.5 to 1.7 ms at 64 B and 2.6 to 3.5 ms at 64 KiB at p50.

Alternatives:

- the `adb` binary (rejected: a process per operation, 16 to 22 ms more at p50 with maxima near 100 ms);
- the adb_client crate (rejected: its `ADBServer` runs `adb start-server` before every connection, its `reverse` reports success when adbd refuses, its `devices_long` fails the whole listing on one `no permissions` target, and it brings 84 crates, including rustls and RSA, for paths the driver does not use);
- the mozdevice crate (rejected: `Device::new` runs `setenforce permissive` on rooted and userdebug targets, `devices` drops every target not in the `device` state, the typed forward and reverse API is TCP-only, and shell v1 loses the exit status);
- direct USB via the ADB device protocol (not measured, since no device was attached; deferred because it conflicts with a running adb server over USB claims; kept as an option for hosts without an adb server).

On API 36 with SELinux enforcing, adbd connects to an abstract socket owned by the shell-user agent, both through `adb forward` and as a service stream, and logs no denial. `adb reverse` with the agent dialing out also works and remains the fallback for a build that refuses the forward direction; Android 17 and OEM builds are unverified. The fallback is constrained. When a device-side connection arrives for a reverse destination the server has already dropped, the adb server aborts (`LOG(FATAL)` in `handle_packet`), which S6 triggered once by closing the agent's connection just before removing its rule, so that the agent's redial raced the removal. The agent therefore dials only when asked, and rules are removed only after its connections are closed. The agent listens on an abstract Unix socket named with a per-launch id and speaks first. The handshake carries a per-launch token: the agent closes a connection whose first frame from the host is not that token, and refuses a peer whose `SO_PEERCRED` uid is not 2000, the uid adbd runs as; spike S1 measured a 3 ms token handshake and a 1.5 ms echo on the service-stream, forward and reverse paths alike. It never opens a TCP port, unlike openatx's server on 0.0.0.0:9008.

Spike report: `docs/spikes/s6-adb-transport.md`.

### D4. Wire format: CBOR, measured by spike S5
Frames are a 32-bit big-endian payload length followed by one CBOR item (RFC 8949) in preferred serialization with definite lengths. Requests, responses, snapshots and tree nodes are maps keyed by small integers, the field index, so absent optional fields cost nothing and receivers skip keys they do not know; events are positional arrays, because at thousands of frames the keys are the overhead. Message kinds: request with id, method and params; response with id and either result or error; event with stream, sequence and payload. Snapshots carry a per-snapshot string table for class names and resource-id prefixes; enums are integers and node flags a bitmask. The host uses minicbor with derive (no_std, borrowed strings, index-based evolution rules) and preallocates arrays from their length; the Kotlin agent hand-rolls the encoder and decoder for the fixed message set with no dependency; the shipped codec (group 3) is 1,549 lines with strict checks and adds 53,932 bytes to the unshrunk dex, which task 4.10's R8 pass reduces. Version and capability negotiation are the first exchange on every connection.

Spike S5 (`docs/spikes/s5-wire-format.md`) measured CBOR, MessagePack and protobuf against compact JSON with readable keys on the same logical fields: a 500-node snapshot, 10,000 event frames and 1,000 requests, with Kotlin on an API 36 emulator and Rust on the host. JSON is larger than CBOR by 2.49x on the snapshot, 3.43x on events and 2.85x on requests (MessagePack 2.53x, 3.49x and 2.88x; protobuf 2.65x, 3.37x and 3.45x). On the device-to-host path, Kotlin encode plus Rust decode, CBOR is 9.5x faster than the faster platform JSON on the snapshot and 15.9x on events (MessagePack 9.0x and 21.7x, protobuf 7.6x and 13.5x). Each codec adds 5.2 to 6.3 KB to the R8 dex. No candidate meets the pass criterion (at least three times smaller and faster than JSON on both the snapshot and the events, under 100 KB of dex), only because no format is 3x smaller on the snapshot: the string table, interned prefixes and integer enums already shrink its JSON, and strings are 37% of its CBOR. The criterion stays as stated, and CBOR is chosen on time, dex, evolution and debuggability. It is within 6% of the smallest candidate on the snapshot and 2% on events (protobuf is 17% smaller on requests), and adds the least dex; it is self-describing, as the device-protocol spec requires and protobuf is not; minicbor derives the integer-keyed layout that serde formats need hand-written impls for, and decodes 2.2 to 3.2x faster than ciborium; frames print in RFC 8949 diagnostic notation; and indefinite-length arrays remain available for lists of unknown length. Alternatives: MessagePack (as small, and 20% faster at encoding events on ART, but no integer-keyed derive in rmp-serde, no standard text form, and counts before elements); protobuf (not self-describing, zero values of non-optional fields dropped, a sizes-first pass on the device; its hand-rolled wire codec adds only 5.4 KB, so the dex is no longer the objection); FlatBuffers (not measured, since `flatc` has no install path through Socket Firewall); JSON over HTTP (per-node cost and no event channel). The Kotlin library codecs and a physical device were not measured; the former need Maven, which Socket Firewall does not wrap, and task 10.3 repeats the Kotlin timings on a device.

Spike report: `docs/spikes/s5-wire-format.md`.

### D5. Mirror update strategy
Android, View-based windows (Views and React Native): the agent forwards content-changed and window-changed events with the source node path; the mirror marks that subtree dirty and refreshes it with descendant prefetch, and performs a full walk only on window state changes or a sequence gap. Simulator: display surface callbacks are the change signal; the tree is re-read after frames change and once more when they stop, bounded by a minimum interval. Text that goes in in one piece is the exception: after text pasted on a Simulator or set directly on Android into a field of a window that sends no change events, that window is re-read as soon as a frame changes after its last read began, or on a target without frames as soon as that read ends, until a read shows the field's text changed, the next input, or a poll interval after the text (task 10.29). On the iOS 26.5 Simulator a paste showed 43 to 93 ms after Command-V, never in the read that follows the input at once, so with the interval `fill` took a paste of 36 characters 248 to 295 ms after the entry and without it 69 to 124 ms. Text typed as keys keeps the interval, since `fill` holds it 200 ms and a read at its first frame would put the next one 200 ms after it, and so does every other window and input, where an animation would otherwise make reads back to back. The frame hash cannot tell a caret from content: iOS 26.5 fades a focused field's caret out and in about once a second, in 8 frame changes, so a command that needs the tree within the minimum interval after a read during which the caret blinked waits for the next read, 222 to 252 ms on the fixtures' login screens; the harness's text entries, each right after a settle and the read that follows it, met that in 30 to 70 % of a series, a slower cluster recorded as the platform's (task 10.29). Refs are assigned from a stable identity built from window, class, identifier and sibling path, and are reissued only when the identity disappears. Alternative: always re-read on request (rejected: that is the model being replaced). S1 measured the costs on the API 36 emulator. A round trip costs about 0.7 ms on a static screen and up to 27 ms while SystemUI animates; requests run on the app's UI thread. Prefetch returns at most 50 nodes, and only below the requested node or from the parent's first child, so a cold read costs about one round trip per child beyond the 49th of any parent: 465 round trips and 349 ms for the 573-node Compose fixture screen with 500 cells under one parent, 506 and 390 ms for the 1049-node React Native one, 50 and 38 ms for Settings, where depth-first prefetch halves the count. Window roots bypass the cache, so even a warm read costs one round trip per window (3 ms for 573 nodes), and a window change empties the cache. Jetpack Compose sends no accessibility events for its content to a UiAutomation client, because it sends them only while `getEnabledAccessibilityServiceList` is non-empty and that list never includes UiAutomation; S1 found the cached tree of a Compose window stale after 19 of 22 actions, and those of View and React Native windows current after all 26 apart from an animating spinner. The mirror therefore refreshes View windows from content-change events and subtree reads, and re-reads Compose windows in full, with the platform cache cleared, after each injected action and on a poll, deriving their deltas by diffing; the same full read serves resync on demand. On a debuggable build every child that goes away during a walk makes `getChild` throw, which cost task 4.11's retry about 57 ms per child, so a tap that took the 500-cell screen away under a poll re-read held the 10.1 run's snapshot past its 10 s deadline; the agent therefore starts a walk again from the window roots when a child's parent is gone or has other children, spends at most 100 ms of a read on retries, and lets a waiting snapshot or resync request preempt the re-read (task 10.9), which answers the read after such a tap in 221 to 368 ms on the API 36 emulator while a cold read of that screen keeps its cost (331 to 335 ms p50 against 333 ms, 464 round trips either way). The agent identifies a Compose window by the `androidx.compose.ui.semantics.id` key in its nodes' available extra data, not by class name: on API 36 a Compose main window reports `androidx.compose.ui.platform.ComposeView` and a Compose dialog window no Compose class at all (task 3.6). The snapshot carries that verdict per window as `emits_events`, along with the owning system process and a modal flag, and per-node scroll semantics where the toolkit provides them. Two facts from the Compose fixture shape the mirror's node model: Compose reports only nodes inside the viewport, so scroll-hidden hints come from scroll-range semantics rather than from off-screen nodes, and Material components keep the label and role on child nodes of the tagged clickable container, so an element's accessible name is computed from its own text or description and otherwise from its non-actionable descendants, the way accessibility services do. Two interactive-listing rules come from the React Native smoke test (task 7.11): a text field with no label of its own takes the label of its nearest plain labelled container, which then drops out of the listing, and a labelled leaf container with no children, which is how iOS exposes a React Native view marked accessible around a hidden text input, receives a ref so that the element the user taps is addressable. SwiftUI attaches accessibility identifiers up to a second after launch on iOS 26.5, so the first tree after a launch is provisional and the mirror re-reads on the first change events before treating refs as stable. An iOS app can mark a view inside its window modal (`accessibilityViewIsModal`, as Bluesky marks its search typeahead), and assistive technology and XCTest's queries then leave out the view's siblings; no snapshot attribute reports the flag (none of the 81 attribute names XCTAutomationSupport knows), so the Simulator's reader asks the app to honour modal views (`snapshotKeyHonorModalViews`), which costs nothing while none is on screen, and when the app left children out it reads again without the option and flags the views the first read kept, 41 ms more on Bluesky's search screen (task 10.22). The mirror keeps what such a view covers, so its refs survive and actions on them fail with `element_covered`, and hides the nodes of the view's siblings that lie within its bounds. It keeps those outside, which XCTest leaves out: Bluesky's header, a sibling of the typeahead after React Native flattens the views between them, holds the search field being typed into and the button that closes the typeahead. The host translator cannot tell modal views, so its degraded reads list what they cover. Android has no such flag: React Native leaves `accessibilityViewIsModal` to iOS, the platform reports no occlusion inside a window (`isVisibleToUser` stays true for a node a sibling is drawn over), and a view group lists its children by where they lie, not in the order it draws them (task 10.28, `docs/research/android-agent.md`). On the API 36 emulator Bluesky's recent searches and typeahead are a sibling of the view holding the Explore page, both at (0, 406) to (1080, 2400) pixels, listed before it and drawn after it (`getDrawingOrder` 3 against 2). The agent therefore flags `on_top` a node drawn after every sibling its bounds overlap, and the mirror hides what the siblings of such a node hold within its bounds when it shows something, a node with a ref or a name in it or below it, judging only nodes with an area, since Android gives a node scrolled out of its list bounds clipped to nothing; the Simulator's reader sets no such flag, so iOS pays nothing. `snapshot -i` listed 12 and 26 refs under the recent searches and the typeahead, against 20 and 34 before with 8 covered controls each, the Explore page kept its 15 refs and its hint once the search was cancelled, and a ref taken before the overlay opened fails with `element_covered`; cold reads of the agent's 500-cell screens kept their 464 and 505 round trips, and warm reads took 8.00 to 8.45 ms on the Compose fixture and 11.04 to 12.40 ms on the Expo one at p50 through the host, against 8.10 to 8.24 and 10.95 to 11.82 ms (two runs each, the 1-minute load 3.0 to 6.2). The same rule cuts the content under an open drawer and its backdrop, a profile's details scrolled under its collapsed header, and what lies wholly under the tab bar Bluesky draws over a list's bottom. Nothing in the tree tells a transparent view from a drawn one: a view drawn over others that shows nothing, such as the decoration Bluesky draws over a video, hides nothing, but a transparent container that lets touches through and holds content would hide what it spans, which no Bluesky screen showed; and a node drawn over some siblings and under another it overlaps is not flagged, so what it covers stays listed.

### D6. Simulator control from Rust: host-side lifecycle, input and frames, a spawned in-guest reader for the tree
CoreSimulator (in `/Library/Developer/PrivateFrameworks`), SimulatorKit (`Xcode.app/Contents/SharedFrameworks`) and CoreSimDeviceIO are loaded with `dlopen` and driven through objc2 dynamic messaging with exception catching around every private call, which needs `panic = "unwind"`. The input transport is selected from the host's CoreSimulator version, as idb and iosef do. From 1155.4 it is the dtuhidd XPC service, `com.apple.coredevice.feature.remote.hid.digitizer`, reached through `-[SimDevice lookup:error:]` and hand-written bindings to the `_4sim` libxpc functions resolved with dlsym; its one connection carries touches with one or two contacts and the edge flag that system gestures need, keyboard usages and Consumer-page buttons. Before 1155.4 it is the Indigo Mach messages through SimulatorKit's legacy HID client. The session sends dtuhidd's activation probe, holds input until the reply, flushes it at once and keeps the one connection for the target's lifetime. Spike S3 (`docs/spikes/s3-simulator-hid.md`) measured this on Xcode 27 with CoreSimulator 1171.7 and iOS 26.5: a tap's touch-down reaches XPC 0.03 ms after the request at the median and 0.05 to 0.16 ms at p95, against the 20 ms dispatch gate, and the first changed frame follows 36 ms after a zero-hold tap, almost all of it the app's own rendering; activation takes about 9 ms once dtuhidd is running and 270 to 330 ms for the first session of a boot, while launchd starts the daemon; input submitted before the reply was never lost, warm or cold, and it is flushed as soon as the reply arrives, because a fixed wait after the reply only delayed it. The driver does not probe the legacy transport, because other sources report that activating dtuhidd disables it, although on this host Indigo touch kept working afterwards. The Indigo message builders keep unsynchronized global state, so Indigo calls run on one serial queue. Text longer than 32 characters, or with a character no key types, is pasted: the driver puts it on the general pasteboard with a `SET` to the guest's `dtpasteboardd`, the daemon behind `devicectl device pasteboard copy`, reached through `-[SimDevice lookup:error:]` for `com.apple.coredevice.feature.pasteboard` and the same `_4sim` functions over a connection per paste, then sends Command-V. `devicectl`, a process per paste, stands in when the guest does not take the `SET`; `simctl pbcopy` is not used, since its guest end, `CoreSimulatorBridge`, ignores it once `dtpasteboardd` runs. Every user application is granted TCC's `kTCCServicePasteboard`, which spares the "Allow Paste" prompt, again only once the device's application directory changes. Task 10.31 measured the `SET` at 8 to 35 ms against 118 to 250 ms for `devicectl` (`docs/spikes/s3-simulator-hid.md`, Addendum), and the 36-character text entry fell from 376 and 555 ms to 199 and 387 ms at p50 on the fixtures (`reports/10.26-remeasure.md`, 10.31 rerun). The accessibility tree cannot be read from a macOS process at useful speed: the host translator (`AXPTranslator` answered through `-[SimDevice sendAccessibilityRequestAsync:completionQueue:completionHandler:]`) makes about seven XPC requests per element and took 1.0 to 1.3 s on the fixtures' 500-cell screens, slower than XCTest (spike S4, `docs/spikes/s4-simulator-ax.md`). The tree is therefore read by a Rust binary built for the `aarch64-apple-ios-sim` target, a port of agent-device's snapshot bridge, which the daemon spawns once per booted Simulator through `-[SimDevice spawnWithPath:options:terminationQueue:terminationHandler:pid:error:]` with no installation, no signature beyond the linker's ad hoc one and no per-app build, and which serves the device protocol on a Unix socket. It loads XCTAutomationSupport and AXRuntime from the runtime root, reads the whole tree with one `-[XCTAccessibilityFramework userTestingSnapshotForElement:options:error:]` per request, and refuses the read when `+[AXElement primaryApp]` is not the target, reading SpringBoard's tree for a system alert instead. S4 measured it ready 292 ms after spawn at p50, within 343 ms at p95 warm and after an app relaunch, and within 299 ms after a device boot, against 568 to 1,183 ms through `xcrun simctl spawn`, which misses the 500 ms gate; a read took 126 to 130 ms at p50 and p95 for the 546 nodes XCTest returns on the SwiftUI 500-cell screen, and 242 to 249 ms on the Expo one, where the app's own snapshot takes 236 ms. Before a device's first boot the daemon writes `AccessibilityEnabled`, `ApplicationAccessibilityEnabled` and `AutomationEnabled` into its `com.apple.Accessibility` preferences under `-dataPath`; without them both read paths fail for several seconds after boot. On iOS 26.5 the keyboard's keys arrive in the application's own read inside the remote keyboard window, which the reader presents as an input-method window, and a blocking UIKit sheet (a transition view whose dimming view spans the window and takes touches) is presented as its own modal window titled by its navigation bar, so the host cuts what it covers (task 6.12). The reader ships prebuilt (0.89 MB after the bounds probes and window flags of tasks 10.11 and 10.12; 0.77 MB when first built) and the first spawn of a newly copied binary can miss the gate once, at install or update time. The translator path stays as the fallback when the reader cannot run: it needs nothing in the guest and names the frontmost application in under 2 ms, but it flattens the tree, drops the children of UIKit's tab bar and the identifiers of React Native text, and reports a childless application for seconds after a launch, so its snapshots are marked degraded. Alternatives: shelling out to an existing Swift tool (rejected: process per command, no frames); an XCTest runner (rejected: install, build, idle waits); an Objective-C shim compiled into the binary (kept as an escape hatch for any single private call that proves impractical through objc2, isolated in one file). Spikes S2, S3 and S4 exercised every private call site from Rust first, and none needed the Objective-C shim, which stays as the escape hatch; S4 reached every guest and translator call site through objc2 and `dlsym`, passing `AXUIElementRef` with the encoding `^{__AXUIElement=}` so objc2's signature checks stay on. Outcomes per call site are recorded in the compatibility table. DeviceHub.app stays closed during spikes: it attaches dtuhidd at boot, and quitting it shuts down every booted Simulator. Baseline measured through XCTest on the SwiftUI fixture under iOS 26.5: a snapshot of the 500-element screen takes 0.66 to 0.71 s, and the idle wait stalls 1.8 to 2.8 s on the animation tab; those are the costs the spawned reader and the settle predicate exist to remove. Spike S2 (`docs/spikes/s2-simulator-frames.md`) validated the lifecycle bindings from Rust: every CoreSimulator call works through plain objc2 message sends, but everything reached from `ioPorts` onward is a ROCKit forwarding proxy that objc2's debug-build checks reject, so those calls go through a small helper that invokes `objc_msgSend` directly and verifies the signature against the proxy's own method signature in debug builds; blocks handed to ROCKit must carry a signature (`RcBlock::with_encoding`). Readiness is `bootStatus` reaching a terminal state; the first boot of a new device takes 43 to 146 s to that point, later boots about 11 s, and attaching to a booted Simulator costs about 330 ms of framework loading per process.

### D7. Frames
Simulator frames come from the display surface as BGRA, are downscaled and JPEG-encoded on a worker thread, and are also hashed at low resolution to feed the settle predicate. Android emulators stream frames from the gRPC controller: RGB888 scaled by the emulator to the working width (S7 measured 540 px at about 45 fps with 15 ms timestamp-to-arrival lag and 87 MB/s, against 37 fps and 285 MB/s at native size), encoded on the host, with raw `getScreenshot` for full-resolution captures because PNG costs 57 ms per capture and drops two thirds of streamed frames at native size. The stream repeats unchanged frames and the status bar clock changes on its own, so frame hashes exclude the status bar. Input goes on a second gRPC connection, which halved drag-input p95 under load. Keys are sent through the agent unless the AVD declares `hw.keyboard=yes`, because `sendKey` returns OK and drops the key otherwise. S7's spike report lists the protocol quirks the client must handle: scaling needs both width and height, raw rows arrive top-down despite the proto, the display size comes from the deprecated `hardwareConfig`, and every call needs a deadline because some emulator ports accept TCP and never answer. Android devices use screenshots on demand; a video path is a later change. Alternative: screenshots everywhere (rejected: no change signal, too slow for settle). The JPEG encoder is chosen from Spike S2's measured encode time per frame at the default dimension. The display surface is cached because it never changes within a session (fetching it is cheap, 0.3 ms median). Spike S2 measured 60 fps at 21% of one core with turbojpeg at 460x1000 output and 30 fps at 12% with the rate cap, so the driver ships turbojpeg linked statically against libjpeg-turbo and keeps the pure-Rust `jpeg-encoder` as a dependency-free fallback that also meets the gate; downscaling, not encoding, is the largest per-frame cost. Frame callbacks fire without pixel changes (35 per appearance toggle with no visible change), so settle relies on the low-resolution hash, and frames are read on the callback and throttled by skipping frames rather than delaying reads, because late reads tear. Emulator 37.1.11 serves its token-protected controller even when started without `-grpc` and only `-ports` leaves it off, so the daemon's `--emulator-controller off` (`MOBILE_AGENT_EMULATOR_CONTROLLER=off`, the `emulatorController` setting) leaves it unused and puts input and frames on the agent path, which `status` and `doctor` report (task 10.12). Under host rendering (task 10.13, `docs/research/emulator-frames.md`) the stream delivers every frame the guest posts, 60 per second at 270, 540 and 1080 px wide with no frame event coalesced, 2.3, 4.6 and 14 ms from the emulator's timestamp to arrival at p50. The emulator stamps a frame before it reads it back, and a tap's changed frame is stamped while SurfaceFlinger is still composing it, so neither the frame's size nor the host's work enters tap-to-frame-change: 270 px and the display size measured the same as 540 px within their bootstrap intervals, and the width stays 540 px.

### D8. Settle semantics
Settled means no tree delta and no frame hash change for a quiet window, default 200 ms, bounded by a maximum, default 3 s. Spike S1 measured Android content changes arriving every 101 to 116 ms (p50) during a continuing change, with gaps up to 187 ms inside a scroll, so a 150 ms window would end inside a change. Windows hosting Jetpack Compose send the agent no content changes; for them the tree signal comes from re-reads and the frame hash carries settle. The result always reports elapsed time and, on timeout, which signal kept changing. This replaces platform idle waits, which the Android agent caps at a small bound and the Simulator path never invokes. Without a frame source (an emulator whose controller is left unused, and every physical device) the 10.1 run found `open` settling while the Expo screen was still coming in, and the next click aimed where the screen was mid-animation. Task 10.11 found why on the API 36 emulator: from Android 14 the platform reports a window it animates in or out at one frame of that animation, to reads and to `AccessibilityNodeInfo.refresh()` alike, until the animation ends and the window's bounds change at once (the Expo launch reads scaled to about 95% for about 300 ms over the launcher, or slid partly off the display for about 500 ms over another app, with no event meanwhile, longer than the quiet window). The agent therefore flags such a window `transformed` (its frame partly off the display, or its frame or root on screen at another size than the root's layout, which `getBoundsInWindow` gives from Android 14), and a settle without frames does not end while an application window outside picture-in-picture is flagged. Views an app moves without a change event keep stale bounds in the platform's node cache, so while it settles without frames the mirror also reads the bounds of up to four anchor elements (elements with refs on screen, spread from the first to the last) again every 50 ms through the agent's `bounds` method, which calls `refresh()` on each; a move between probes counts as a tree change, anchors that hold still where the replica does not have them bring a read of their windows with that cache evicted (the snapshot's `evict`), and the wait settles only after a probe that finds the anchors where the replica has them. Four anchors every 50 ms is the measured choice: with the 1-minute load between 1.9 and 3.7, a probe of four nodes cost 2.7 to 3.3 ms in the agent and 4.4 to 5.0 ms from the host at p50 (eight cost 5.1 to 6.3 and 6.8 to 8.1 ms), a still screen's `wait --settle` costs that one probe (4.5 ms p50), and `open` on the agent path now ends with the screen at rest in 20 of 20 opens (1 of 20 before) after 1,050 ms p50 over the launcher and 1,255 ms over another app, against 787 and 768 ms before and 1,184 and 1,247 ms on the frame path. The harness's list-scroll flow on the agent path still failed after that (task 10.14): its click on the list's last row, sent right after the settle that followed its last stroke, opened nothing, while the same commands typed by hand seconds apart did. From Android 12 a scroll view that a stroke pushes against an end of its range, or that a fling carries into one, draws a stretch that springs back on its own (`EdgeEffect`'s spring: natural frequency 24.657, damping ratio 0.98, the release or fling velocity taken in at 13 times); the stretch moves no view and sends no event, and until it rests `ScrollView` takes a touch that comes down as the start of a drag that catches it, so the row never sees the tap. On the API 36 emulator (task 10.14, 1-minute load under 4) the flow's last 600-point stroke pulled the Expo list against its end, and `dumpsys gfxinfo` frame stats showed the app drawing the stretch for 333 to 383 ms after the frame that took the finger's lift (5 of 5 strokes); of 11 clicks sent right after the settle, the 6 that came 307 to 353 ms after the stroke command returned opened nothing and every one from 358 ms on opened the row, as did 3 of 3 sent 100 ms later, clicks after a settle in the middle of the list opened their row in 6 of 6, and a fresh daemon after a failed click still read the list: the tap was lost, not the change. A settle without frames therefore does not end, after a stroke that leaves the content under it at an end of its range (a visible node under the point where the stroke came down, scrolling along its axis, that can scroll one way but not the other, as the replica has it), until 500 ms have passed since the stroke and since the tree's last change, which stands for a fling's arrival at the end: 117 ms beyond the longest stretch measured, for taller lists, whose stretch springs back from further, and a loaded host. The hold follows the latest input only while it is that stroke on the app still in front, and with frames, which show the stretch, it changes nothing. The settle after the flow's last stroke then takes 644 to 679 ms instead of 290 to 378 ms, and the click opened the row in 9 of 9 runs; on the frame path the same settle takes 861 to 1,814 ms, the frames changing for longer than the stretch.

`scroll --until` looks for its element only between strokes, in the replica after the settle that follows each, so no stroke may carry the element through its list between two looks (task 10.16). A stroke whose finger lifts moving flings the list on at the finger's speed: a 600-point stroke over 300 ms carried the Expo fixture's list 1,176 to 1,319 points and the Compose fixture's 1,103 to 1,272 on the API 36 emulator, where they show about 780, and the Expo fixture's 1,522 to 1,608 on the iOS 26.5 Simulator, where it shows about 730. With that step (1-minute load under 4, four runs each, relaunched on the List tab), `scroll down 600 --until row-100` failed with `element_not_found` after 10 or 11 strokes in 3 of 4 runs on each emulator fixture; on the Simulator three or four strokes happened to leave `row-100` in view, but `row-25`, which the first stroke carries past, failed in all 4 runs, two on each fixture. Detox scrolls in strokes no longer than the view's visible range with a swiper that does not fling; Maestro's scrollUntilVisible strokes at a speed the user sets and tells users to slow it to avoid overshooting. Three forms were measured through throwaway builds on both devices, with the step bounded so the content's travel stays inside the list: strokes that still fling, shortened to 345 points on the emulator and 210 on the Simulator, took `row-200` 18.4 to 19.2 s and 37.6 to 43.6 s; strokes slowed to 400 points a second 29.9 to 31.4 s and 47.0 to 54.1 s; strokes that come to rest before the finger lifts 11.2 to 12.3 s and 13.1 to 14.6 s, against 10.8 to 12.0 s and 13.6 to 16.3 s with the flinging step (the spike's 1-minute load 1.4 to 7.9). Every stroke of `scroll --until` therefore comes to rest before the finger lifts. Android's velocity tracker takes a pointer that has not moved for 40 ms as stopped only when its next event comes, and a View-based list such as React Native's scroll view takes its velocity from the moves before the lift, so a rest alone left the Expo list its fling (1,015 to 1,302 points) while Compose, which drops the velocity itself, stopped: the pointer rests 60 ms at the end, moves one pixel on and lifts there (the agent's swipe `rest_ms`, or the controller's last touches). UIKit takes a drag's velocity from its last moves, and a rest of 60 to 150 ms alone, or with one move of a pixel to 3 points after it, still ended in the drag's full momentum (645 to 1,652 points for strokes of 300 and 600), and three moves of a pixel did at one start point in sixteen: the finger rests 60 ms, then creeps on three moves of a point 16 ms apart and lifts at the last. Released so (1-minute load 3.4 to 4.2), 600-point strokes moved the emulator's lists 554 to 592 points and the Simulator's 543 to 573, never more than the finger less the tap threshold, and the screen settled 192 to 302 ms after each, where a flinging 600-point stroke's settle took 1,027 to 1,260 ms on the emulator and 2.8 to 2.9 s on the Simulator. A stroke that looks for the element is the step, or shorter: at most three quarters of what the scroll container under the stroke shows along the scroll's axis (the mirror's `scroll_viewport`; the scrolled area when the replica has no container there), plus the tap threshold, which the content does not follow. At one look at least the element then shows whole, or a quarter of what the container shows of it when it is longer, and task 10.15's bring-in stroke, which rests too, takes it from there; the fraction is the spike's, whose `row-200` times matched the flinging step's with it. Measured after (four runs each; the emulator on its controller's path, 1-minute load 2.5 to 3.4; the Simulator under 4 at each scroll's start): on the emulator `row-100` was found in every run after 8 strokes, 5.0 to 5.3 s on both fixtures, and `row-200` after 16, 10.8 to 11.0 s on Expo and 10.6 to 10.7 s on Compose, against 8 strokes and 11.1 to 12.2 s before (11.5 to 11.8 s in task 10.15), the strokes 596 and 578 points long; on the Simulator `row-100` after 8 or 9 strokes, 5.5 to 6.8 s, against 3 or 4 strokes and 7.2 to 9.6 s, `row-200` after 17 or 18 strokes, 12.5 to 13.7 s, against 6 or 7 strokes and 13.1 to 16.3 s, and `row-25` after 1 or 2 strokes in 0.7 to 1.8 s; the Expo list's strokes were 551.5 points, the SwiftUI list's the 600-point step, since that list runs from the top of the screen to the tab bar and shows 791 points. The bring-in stroke, resting, carried the Expo list 378 to 384 points of its 384-point aim on the emulator (411 to 425 when it lifted moving) and the SwiftUI list 106 to 112 points of 111 on the Simulator (283 to 299).

### D9. CLI grammar
The command set, ref syntax, interactive snapshot flag, JSON flag, batch mode and session flag mirror agent-browser where the concept exists on devices. Alternatives: Maestro YAML (rejected for this change: a flow runner can be layered later; agents act step by step); a new grammar (rejected: no transfer of existing skills).

### D10. Benchmark harness as a first-class crate
A Rust binary drives this project's CLI and, through adapters, the baseline tools, on flows described once. Fixtures are an Expo React Native app, a Compose app and a SwiftUI app checked into the repository with a deterministic 500-node screen each. Reports are JSON plus markdown. Gates are those in the benchmark spec.

### D11. Workspace layout and work partitioning
```
crates/protocol    message types, framing, negotiation           (no device code)
crates/mirror      replica, refs, settle, wait, diff, verdicts   (depends on protocol)
crates/android     adb client, agent deploy, agent session, emulator gRPC
crates/simulator   CoreSimulator bindings, HID, AX bridge, frames
crates/daemon      target registry, sessions, Unix socket API
crates/cli         thin client, output formatting
crates/bench       harness and baseline adapters
agent-android/     Kotlin sources, build script using kotlinc and d8
fixtures/          reference apps and flow descriptions
```
Each crate is a separately assignable unit with disjoint files. `protocol` and the agent's message set are written first because everything else depends on them.

### D12. Hidden and private API policy
All private Apple framework use and hidden Android API use is confined to `crates/simulator` and `agent-android`, behind traits defined in `crates/protocol` and `crates/mirror`. Every such call site records the Xcode or Android version it was validated on. On Android, hidden-API enforcement is off for processes started by `app_process` (ART enables it only for zygote-forked apps or with an explicit runtime flag) and the shell user is exempt from Android 14's writable-dex rule, so no bypass is planned; the real risk is OEM framework differences. The compatibility table cites `android-17.0.0_r1` (API 37); `UiAutomationConnection` ownership is unchanged from Android 14 to 17. A compatibility table is generated into the CLI's `doctor` output.

## Delivery process

These rules bind every task in tasks.md and every subagent that implements one.

- **Research first.** Each task group opens with a state-of-the-art note in `docs/research/` naming what exists, what is reused, where this design differs, and the sources. No implementation task starts before its group's note exists.
- **Spikes before construction.** The seven spikes S1 to S7 in tasks.md group 2 de-risk the assumptions this design rests on: shell-user ownership of Android UI automation, Rust control of the Simulator lifecycle and frames, both Simulator input transports, the Rust accessibility bridge, the wire format, the ADB transport and the emulator control endpoint. Each spike is throwaway code under `spikes/`, delivers `docs/spikes/<id>.md` with measurements and a go or no-go verdict, and gates the groups that depend on it. A failed spike changes this design; it is not patched around.
- **Measured decisions.** D3, D4, D6 and D7 are candidates until their spike records numbers here. Any later choice with measurable consequences follows the same rule.
- **Tests first.** Every implementation task adds failing tests, records the failure, then implements until they pass. A task without red-then-green evidence is not complete, and the validation phase checks that changed code is covered.
- **Atomic commits.** Each task lands as one or more atomic commits made by the implementer, one logical change per commit, message in `type(scope): summary` form, no attribution trailers.
- **Validation and fix after every task.** Before the next task starts: `cargo build --workspace`, `cargo clippy --workspace -- -D warnings`, `cargo fmt --check`, `cargo test --workspace`, the agent and fixture builds where touched, `openspec validate`, and a diff review against the spec section the task implements. Failures are fixed and committed first.
- **Installs through Socket.** Every dependency install is prefixed with Socket Firewall: `sfw cargo add`, `sfw cargo fetch`, `sfw npm install`, `sfw pnpm add`. Bun is not documented as supported; the fixture task verifies `sfw bun` and falls back to `sfw npm` if it is not wrapped. No bare installs.
- **Pinned toolchain.** `rust-toolchain.toml` pins Rust 1.98.1 with clippy, rustfmt and the `aarch64-apple-ios-sim` target, so local builds and CI use one compiler, while `rust-version` keeps the 1.95 MSRV. Dependabot checks weekly for a new stable and opens a pull request, which the bump procedure in `docs/research/toolchain.md` completes.
- **Recap before dispatch.** Whoever dispatches a task to an implementer restates its goal, the spec and design sections it implements, the files it owns, the acceptance checks and the constraints above.

## Risks / Trade-offs

- [Simulator private APIs change again in an Xcode beta] → transport probing at attach, a CI matrix over installed Xcode versions, and the Objective-C escape hatch so a fix is one file.
- [An OEM Android build blocks the shell-user automation path] → detect at deploy and report; instrumentation APK fallback scheduled as a follow-up change rather than built speculatively.
- [The only fast Simulator tree reader depends on a private framework built for the iOS Simulator platform and must run inside the guest] → keep the host-only translator path as the fallback, record per-Xcode validation for the spawned reader, and report readiness time in target status.
- [Only one UI automation owner per Android device] → the daemon is the single multiplexer; the platform never names the other holder (the error carries only a binder proxy id), so the conflict report infers a likely holder from the process and instrumentation listings; the role is released when the owning process dies; a force flag exists for recovery.
- [Compose windows send no accessibility events to UiAutomation, and a full re-read of a wide Compose screen costs hundreds of round trips] → re-read Compose windows after each action and on a poll, report their read cost in snapshot metadata, and let the frame hash carry settle there.
- [Reflection on hidden Android members breaks on a new API level] → the agent verifies each member at startup and reports which capability is lost instead of crashing; the capability set is what the daemon negotiates on.
- [Tap-to-frame-change on an emulator mostly measures the guest's own frame pipeline, and its limit depends on the GPU mode] → decomposed in task 10.13 (`docs/research/emulator-frames.md`) with a trace of the guest beside the controller's frames: the tool's dispatch took 2.4 to 2.8 ms at p50 and at most 3.4 ms at p95, and the emulator stamps the changed frame while SurfaceFlinger composes it. The rest is the guest: the input's delivery to the app, the wait for the app's next VSync, and the app's pipeline to SurfaceFlinger's composition, from the up event to SurfaceFlinger's commit 2.4 frames of the 60 Hz display at p50 and 3.0 at p95 for the Compose fixture, whose debug build misses SurfaceFlinger's deadline in more than half the taps on an idle host, and 2.1 and 2.8 for the React Native fixture, which hands input to JavaScript one frame late. Streaming at 270 px or the display size instead of 540 px, and sending a tap's down and up in one `streamInputEvent` call, changed nothing within the measurements' spread. So the gate is restated for host rendering at p95 under 67 ms, four frames of the 60 Hz display, which the 10.1 run's 52.5 and 55.1 ms and task 10.13's 52.9 to 59.1 ms through the daemon pass; software rendering, where S7 measured 146.5 ms at p95, is not gated. The same build reads slower on an idle host: one busy host core cut the Compose fixture's p50 from 53 to 57 ms to 25 to 35 ms and its p95 from 59 to 61 ms to 29 to 39 ms, so reports carry the 1-minute load.
- [A Simulator display can stop presenting while input is still accepted; S3 saw it once, cleared by a reboot, cause unknown] → the driver reports a frame stream that stays static across accepted input as a degraded target and offers a reboot.
- [Frame hashing misreads video content as never settled] → settle reports the reason so agents can choose the tree-only signal; a tree-only mode is exposed.
- [Ref identity collides for visually identical siblings] → sibling index is part of the identity; collisions are detected and reported as a degraded verdict rather than silently merged.
- [Benchmark fixtures drift between tools] → flows are defined once and adapters are tested against a golden result before timing runs.

## Migration Plan

Greenfield. No deployment beyond building the workspace; nothing to roll back. The Android agent is versioned with the protocol and replaced on the device whenever the version differs.
