# Design

## Context

`docs/research/agent-surfaces.md` holds the evidence: the MCP revision of 2026-07-28 is stateless (no protocol sessions, handles as arguments, logging deprecated) and older clients still speak the earlier era; Claude Code cuts instructions at 4,096 characters, backgrounds a call past 2 minutes and aborts a silent one after 30 unless progress arrives, Codex gives a call 60 s and shows only `structuredContent` when a result has it, Cursor keeps tool names alone; `rmcp` 3.5.1 (official, Tier 1, dual-era, progress and cancellation) costs about 2.9 MB and 22 crates against a 0.54 MB hand-written loop; the daemon's 18 actions read 42 parameters by name and build replies with `json!`, so no schema can be derived today; on the 500-cell fake screen `snapshot -i --json` is 45 KB of which the refs map repeats the 22 KB listing, an unchanged delta is 302 bytes, a default screenshot about 612 image tokens; a target runs its commands in order, the daemon has no cancel, and only `close` releases a claim, stopping the app. The maintainer's decisions: standalone (no agent-browser provider), the CDP subset not built, the unverified mode its own later change.

## Goals / Non-Goals

**Goals:**
- An MCP server that gives a model what the CLI gives a shell: the same refs, replies, codes, sessions and verification, in a context-sized form.
- One definition of the daemon's requests and replies, with schemas, serving the CLI, the harness and the server.
- Waits that neither hold a target nor fall to a client's timeout.
- The CLI's start time and the harness's gates untouched.

**Non-Goals:**
- The agent-browser `device` provider and the CDP subset (recorded below).
- The unverified mode (its own change).
- Streamable HTTP transport, remote servers, authentication: stdio only, one client per process.
- Pushing changes to the client (MCP notifications do not reach the model portably); the blocking `wait --change` is the form.

## Decisions

### D1. The SDK: `rmcp`, measured against a hand-written loop
`rmcp` 3.5.1 serves both protocol eras, generates input schemas from Rust types through schemars, and carries progress and cancellation; a hand-written loop (agent-browser's and agent-device's way) is 0.54 MB against rmcp's 3.43 MB in the research note's measurement and 22 fewer crates, but both eras, discovery, progress and cancellation would be written and followed by hand as the specification moves (three breaking SDK majors in 2026 mirror a moving specification). The server takes `rmcp`, pinned, in its own binary so the cost is the server's alone; the spike S13 measures the round trip the SDK adds over the socket path. Revisited if a major migration costs more than the loop would have.

### D2. Where it runs: a crate of its own, `crates/mcp`
`mobile-agent-mcp`, the binary of a crate `mcp` beside `crates/cli`, built on the CLI's library for what the server shares with the shell: `client.rs` (discovery, the daemon's start, the version check, retries, the reply wait) and `output.rs` (a reply's text, D5). `rmcp`, `tokio` and `wire`'s `schema` feature are that crate's dependencies alone. Cargo gives every target of a package the same dependencies, so a second `[[bin]]` in `crates/cli` would compile them into every build of the CLI, and one behind a feature would need the feature on every build and install. `mobile-agent` keeps its size and its 5 ms start, which the harness gates (`cli-start` under 20 ms); a workspace build unifies `wire`'s features, so a CLI built with the workspace compiles schema code that the linker drops, which task 5.1's size check measures both ways. Alternatives: a `mobile-agent mcp` subcommand (rejected: the CLI would link the SDK's runtime, a start-time risk the gate would have to re-measure); a second binary of `crates/cli` (rejected as above). As built (task 5.1), the crate `mcp` and its binary `mobile-agent-mcp`, on `rmcp` 3.5.1 pinned with `server`, `macros` and `transport-io`, tokio's current-thread runtime, `wire` with `schema` and the CLI's library for `client`, `output`, `request`, `doctor` and `config`, none of which changed; the release binary is 4,169,824 bytes built alone, against S13's 3,859,824 for three tools, and 4,381,632 built with the workspace, which unifies the features of what the server shares with the daemon and the harness; it starts in 5.9 to 8.9 ms at p50 and 12.5 to 13.1 at p95 to the answer to `initialize`, and 8.3 to 8.6 at p50 and 10.9 to 14.8 at p95 to `server/discover`, in two runs of 30 starts after 3 at a 1-minute load of 4.9 and 2.9 on a host the endpoint scanner was loading, against S13's 3.6 / 4.5 and 5.0 / 10.9 for its three tools; the server builds its 16 definitions at start, whose share of that is not measured apart; the CLI's release binary is 1,682,128 bytes built alone and 1,682,704 with the workspace, 576 bytes the linker keeps of the unified features, against 1,665,488 at task 3.2, the 16,640 between being the CLI's own commits of tasks 4.2 and 4.4.

### D3. The shared types: `crates/wire`
A crate `wire` of the daemon's request and reply types: the envelope (`id`, `session`, `action`), one flat struct of parameters per action with serde derives, each parameter's default in the type (Codex calls a tool with `{}`, S13), and `schemars` behind a `schema` feature that only the MCP binary and the schema tests enable, so the CLI and the daemon link no schema code. Requests are typed on both sides: the daemon's handlers deserialize the action's struct instead of reading 42 parameters by name, the CLI's `request.rs` builds it, and the MCP server's tool inputs are the structs' schemas at run time (flat objects, since Claude rejects `anyOf` at a schema's root; S13 found schemars 1.2.3 giving `Option<u32>` as `["integer", "null"]` with `default: null` and doc comments as descriptions, which Claude Code took as they were). Replies keep the handlers' construction: the CLI's `output.rs` formats a reply's JSON into the text the user reads and the server reuses it (D5), so a reply-data struct per action is defined in `wire` for `outputSchema` (D5's `--structured`) and the harness's reads (`readMs`, `servedFromReplica`), and held to the handlers by a round-trip test per action, through the fake, that parses the handler's reply into its struct with unknown fields denied: a field added to a reply fails that test until the struct gains it. The handlers' messages and codes do not change: a missing or malformed parameter answers with the same `invalid_argument` text the by-name reads gave, the CLI's and daemon's tests being the guard, and the request parse keeps ignoring keys it does not know, as `serde(flatten)` cannot deny them. Alternatives: schemas written beside the tools (rejected: three copies drift, the research note's finding on agent-browser's 62.7 KB of hand-written definitions); replies built from the structs in the handlers (rejected for this change: 74 construction sites rewritten for no reader, the text form being the CLI's formatting, and the round-trip tests give the same hold against drift).

### D4. Names and arguments
Tool stems follow agent-browser's where the concept matches (`snapshot`, `click`, `fill`, `type`, `press`, `swipe`, `scroll`, `screenshot`, `wait`, `get`, `open`, `close`), with the daemon's own for the rest (`devices`, `status`, `doctor`, `diff_snapshot`, `help`); no prefix, since Claude Code prefixes the server's name. The element argument is `selector` as agent-browser names it (a ref `@e3`, an id `#login`, or `text=`), the other arguments the daemon's names (`interactive`, `maxDepth`, `delta`, `text`, `key`, `direction`, `amount`, `until`, `timeout`); the mapping is one table in the server and the README. Tool annotations mark `snapshot`, `diff_snapshot`, `get`, `wait`, `screenshot`, `devices`, `status`, `doctor` and `help` read-only and `close` destructive. Three actions are not tools: `set_timeout`, since every waiting tool takes its `timeout` and the server bounds each call (D7); `shutdown`, since the daemon serves the shell's sessions too and exits when idle; and `cancel`, which the server sends itself on a client's cancellation (D7). A tool's input is its request struct's schema with the changes of one table in the server: the element argument `target` named `selector`; `snapshot`'s `interactive` and `delta` defaulting to true (D5); the envelope's `session` and `device` on every tool and `force` on `open`, its other fields left to the server. A test holds every other parameter of each struct to its tool's schema, so a parameter added to a struct reaches the tool or fails that test. As built (task 5.1), the table is `crates/mcp/src/tools.rs`, served through rmcp's handler trait, `ServerHandler`'s `list_tools` and `call_tool` in `server.rs`, rather than its tool macros, since every definition comes from the table; each tool's definition is built once at start from its struct's schema with the table's changes, the `selector` renaming carried into `required` and the descriptions, and the table holds two changes beyond those above: `screenshot`'s `inline`, which the server sends set and the tool does not take, and its `ifChanged`, the tool's own flag, read and not sent, with `path` described for the tool; 16 tools, `help` being task 5.5's; the schema test, `crates/mcp/tests/tools.rs`, carried task 4.4's `frames` into `wait`'s schema with no change to the server.

### D5. Results: text, no map, `structuredContent` opt-in
A result's text is the reply as the CLI prints it without `--json`: the listing for snapshots (without the refs map, which repeats it and doubles the size), the lines the CLI prints for actions (`✓ Done (dispatch 0.3 ms, no change in 202 ms)` for a click), the `warning` on its own line as the CLI marks it, and a failure as `isError` text, the CLI's line with the daemon's code named, whose message already says what to do next. The text is the CLI's `output.rs` writing into a buffer instead of the terminal: one formatter for both surfaces, so the agent guide's examples hold for either. `structuredContent` with an `outputSchema` is sent only with `--structured`, since Codex then shows the model that JSON alone and drops images (research note, How the clients consume servers). Snapshots default to `interactive: true` and `delta: true`, the first delta of a session being its whole listing, so an unchanged screen costs `unchanged (revision N)`, 22 to 25 characters against the CLI's 302-byte JSON reply (S13); `full: true` asks for the whole listing, which S13 counted at 12,163 tokens on Claude Code's model for the 500-cell screen, 1.81 characters a token, about twice the research note's estimate. As built (task 5.1), `output.rs` served as it was: its `human` already returns a reply's standard output and error as two strings, so no CLI change was needed; the result is the output's lines then the error's, the warning's `⚠` line among them, and a failure's text is the CLI's `✗` line with the code set after the mark (`✗ stale_ref: e2 is stale: ...`); `doctor` runs the CLI's checks in the server, `cli::doctor::run_checks`, and answers with the report's text, a failed check making it an execution error ending `✗ doctor_failed: checks failed: ...`; `full` reaches the tool from the struct, and `structuredContent` is task 5.6's.

### D6. Screenshots inline with `ifChanged`
The screenshot tool asks the daemon for the JPEG (quality 80, long edge 1000 px, within Claude's 2000 px bound for many-image requests) and returns it as image content; with `ifChanged`, the server compares the frame hash the daemon reports with the session's last and returns a text "unchanged since the last screenshot" instead, sparing the 612 tokens; `path` returns the file's path alone for clients that cannot take images. The daemon's `screenshot` gains the bytes in its reply for a server that asks (`inline: true`), so no file is read back: `image`, base64-encoded, and `mimeType` beside `path`, which is null when no path was given and no file is written then (task 4.3). As built (task 5.3), the daemon's reply carries the frame's `seq` and no hash, so the server hashes the image itself, its base64 text through the standard library's `DefaultHasher`, and keeps the hash per session and per `device` the call named, a screenshot's reply naming no target; `ifChanged` with a `path` compares the same way and answers the line instead of the path; a relative `path` is taken from the server's working directory, as the CLI takes one from its own.

### D7. Long waits: progress, a bound, a cancel
Every tool that can wait (`wait`, `scroll --until`, `open`, `fill`, `click` with its settle) sends a progress notification every 5 s with what it waits for, which keeps Claude Code's idle timer alive and shows in its task entry; each call is bounded by `--call-timeout`, 55 s by default (under Codex's 60 s), passed to the daemon as the command's timeout so the daemon's own wait ends first; and an MCP cancellation sends the daemon the new `cancel` action, which ends the session's command in flight (it fails with `cancelled`), so a target is not held by a wait the client abandoned. The daemon runs a target's commands in order (`crates/daemon/src/worker.rs`), so `cancel` reaches the worker through a flag the waiting command checks at its next wakeup; it does not interrupt a device call in flight. The waits that hold a target longest, the mirror's `wait` and `settle`, loop inside the mirror and block on the event stream, so the flag lives there (`Mirror::cancel_on`, task 4.2): the mirror's `run_until`, `wait` and `settle` look at it before they block and every 50 ms while they do (`CANCEL_SLICE`), and fail with `cancelled`, so every daemon wait built on them sees it, the click's watch, `fill`'s read-back, `open`'s waits and `scroll --until`'s settles among them; a flag that stays down changes nothing they do. The worker records the command running, its session and action, and lowers the flag as it ends, under the lock `cancel` raises it with; `cancel` finds the targets through the session's claims, replies once the command it ended is over, up to 5 s, with a warning naming one held longer in a device call, and changes nothing when nothing of the session runs. The cancelled command's failure names its action. A click whose tap went in completes, its watch cut short with a warning: the tap took effect, and a failure would invite a client to tap again.

### D8. `wait --change`
A `wait` mode that returns when the session's listing changes, the listing in the options of the session's last snapshot (interactive for a session that took none) against the one that snapshot showed, with the delta (as `snapshot --delta` gives it), or `wait_timeout` at its bound; built on the mirror's `run_until`, `next_wakeup` and revision as the overview's section 7 assessed. It is the portable form of a change notification: the model calls it after an action whose effect may still be arriving, instead of polling snapshots. The CLI gets the same flag. A change the listing does not show does not end it: the first build (task 4.1) returned at any move of the replica's revision or of the frames, and on the Simulator a second wait returned at once with `both` and an `unchanged` interactive listing, the revision having moved outside it; a caret's blink, a spinner or the status bar's clock move the frames all the time, which would end every such wait at once. With `frames` (`--frames`) a frame change ends it too, for a canvas, a map or a screen the tree does not describe, whose listing may then be `unchanged` (task 4.4). The wait compares the listing again only when the revision moved. The baseline is the session's last snapshot of any kind (plain, delta, diff, or an earlier change wait's), so a change between that snapshot and the call returns at once; once something moved the wait brings the tree up to the frames as a snapshot does; `endedBy` names what moved with the settle reply's names, `tree` for the listing, `frame` or `both`, so with `frames` a change outside the listing that the frames show gives `frame`; the delta is taken in the options of the session's last snapshot and becomes its last snapshot; a session that took no snapshot gets the whole listing at once, as its first delta snapshot would. The bound is the waits' default, the command's `timeout`, else the session's, else 10000 ms.

### D9. Sessions and claims
The server mints `mcp-<pid>` as its session and takes an optional `session` argument on every tool for a client that resumes a transcript with refs; on exit (stdin closed, SIGTERM) it sends `close --keep`, the new form that releases the claim without stopping the app, so the next session does not meet `target_claimed` and the app a model was driving stays where it was; `close` alone keeps today's meaning. As built (task 4.2), `close --keep` forgets the session's app, so its next `close` stops nothing, `status` still names the app on the target, and the reply adds `kept: true`. As built (task 5.2), the server keeps, per session a call went out in, the targets its successful replies name (`open`'s, a snapshot's and a diff's; `close`'s removes its own) and on every way out, its input's end, SIGTERM, SIGINT and rmcp's initialization error for a client that only discovered it, releases each with `close` and `keep` and the target's id, then each target `status` lists for those sessions, since a click on a selector claims without naming, waiting at most 5 s for the daemon and starting none; the runtime is left running at exit, since dropping it would wait on the read of standard input a signal interrupted, and the server exits 0 on each of these ways out. The daemon's idle exit and `shutdown` are unchanged.

### D10. Profiles and instructions
`--tools read-only|all` (default `all`): the read-only set is `devices`, `status`, `doctor`, `snapshot`, `diff_snapshot`, `get`, `wait`, `screenshot`, `help`, which also passes Codex's write approvals without prompts; the instructions card is one paragraph under 512 characters that stands alone (what the server drives, that refs come from snapshots, that replies verify, where to read more), the whole under 4,096 characters, and the agent guide (`help agent`, 119 lines) is the `help` tool's text, as agent-device splits them.

### D11. The spike before the build
S13 (`docs/spikes/s13-mcp-server.md`, `spikes/` are kept privately, the report public): a throwaway `rmcp` stdio server with three tools (`snapshot`, `click`, `screenshot`) over the daemon's socket against the fake 500-cell target, measured on a quiet host: the tool call's round trip at p50 and p95 against the CLI's process per command (5 ms start plus the socket) over 100 calls; the result sizes in characters and Claude's token ratio for the interactive listing, an unchanged delta and a screenshot; a functional check that Claude Code on this host and Codex, if installed, list and call the three tools in their era. Go: a round trip under 20 ms at p95 and the listing under 7,000 tokens; no-go on the SDK falls back to the hand-written loop with the same tools. S13 found the round trip under the gate in every round, the server adding 0.3 ms to the 500-cell listing (1.16 to 1.25 ms at p95, against 7.4 to 9.0 through the CLI), and both eras served to Claude Code (2026-07-28) and Codex (2025-06-18), so `rmcp` stays. The listing misses the gate as Claude Code counts it, 12,163 tokens at 1.81 characters a token against the 6,290 the research note's 3.5 gave, a cost of the daemon's listing that no SDK changes (`docs/spikes/s13-mcp-server.md`). The maintainer's decision: the listing line stays as the CLI prints it, agent-browser's form with the id, and the gate is restated per listed element, 25 tokens each at the measured ratio, which the 500-cell stress screen meets at 24 and a screen of 60 elements at about 1,500 tokens; the acceptance (task 6.2) counts the fixtures' screens against it. A terser line and a cap on the listing stay options, recorded in D12.

### D12. Recorded, not built
The agent-browser `device` provider: its plugin policy wants providers out of process returning CDP endpoints, so a provider needs either a CDP endpoint on this side or a new backend in agent-browser's actions; kept as an option for when agent-browser opens a non-CDP backend. The CDP subset: agent-browser's fill and focus run JavaScript on DOM nodes and Metro's inspector expects a JavaScript runtime; low value for the cost, a viewer at most. The unverified mode: its own change, after this one, with the server's tools gaining the flag then. Two ways to cut the listing's tokens, kept for when a screen or the acceptance shows the need, each as an option a caller turns on rather than a change to the default line: a terser line for both surfaces (`button "Cell 123" #cell-123 @e650`, which drops the brackets and the `id=` and `ref=` keys for about a third of the tokens, behind a snapshot flag so that skills written for agent-browser's `[ref=eN]` form keep parsing the default), and a bound on the listed elements (`limit`, with a hint line counting what it leaves out, as `-i`'s hints count what a cover hides, so that a model asks for more by depth, by scope or by scrolling instead of reading 500 cells).

## Risks / Trade-offs

- [`rmcp` breaks on a major] → pinned, bumped on purpose by Dependabot's cooldown, the hand-written loop the recorded fallback.
- [Clients change what reaches the model] → the research note's limits are dated; the acceptance checks two clients, and the card and sizes are tuned to the smallest.
- [The shared types change how the daemon reads requests] → round-trip tests per action first, the messages and codes unchanged, the harness's and CLI's tests as the guard.
- [A cancel that cannot interrupt a device call leaves the target busy for that call's length] → bounded by the device's own deadline (10 s on the runner); recorded in the reply.
