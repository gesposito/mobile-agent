# Design

## Context

Three changes fixed what the passes on real apps found (`real-app-fixes`, `action-verdicts`, `android-pass-fixes`), each proven by the next pass; the fourth pass left iOS with no failed call and found nine new gaps with the site's recording runs (the private demo notes of 2026-10-30 and the site's recording report; `reports/12.5-fourth-pass.md` is this change's public record). Two of the gaps came one run in five or three runs in a prep, which is the shape of a host effect as much as a tool's; the passes have only ever run on one Mac, under the load of its other sessions. CI runs the fakes alone: the device-backed tests are gated on `MOBILE_AGENT_SIM_UDID` and `MOBILE_AGENT_ANDROID_SERIAL`, which `ci.yml` never sets, while `benchmarks.yml` creates a fresh iPhone 17 Simulator on the runner's iOS 27.0 runtime and boots the API 36 emulator for the harness. The first CI harness run (41181272250) showed the fixture's list screen failing every tool under iOS 27, a version this Mac does not run.

## Goals / Non-Goals

Goals: every finding reproduced where it can be, on CI's fresh devices or on the fakes, before a fix; each fix gated on its case; a public record of the pass and the known issues. Non-Goals: per-pull-request device tests (40 minutes of macOS runner per run); fixes for the apps' own behavior (Calendar's node, Chrome's first run) beyond naming them; the noise study of the benchmarks (ci-benchmarks task 2.1).

## Decisions

### D1. Device-backed tests run in CI, on fresh devices, on a schedule and on demand
A workflow `device-tests.yml` provisions what `benchmarks.yml`'s harness jobs provision (the Simulator created, booted and given the SwiftUI fixture on the macOS runner; the emulator through `reactivecircus/android-emulator-runner` with the Compose fixture on Linux), then runs the workspace's tests with `MOBILE_AGENT_SIM_UDID` and `MOBILE_AGENT_ANDROID_SERIAL` set, so that the gated tests run, and a new gated test module on the default apps (`crates/daemon/tests/real_apps.rs`: Settings, Maps, Calendar, Photos on the Simulator; Settings, Clock, Chrome on the emulator), one test per finding of this change. Every assertion is on what the device guarantees, the reply's fields and the listing, with generous timeouts and no fixed number of milliseconds, since the runners coalesce timers (the wall-clock lesson of the timing fixes of 2026-10-30). The job runs weekly, off the hour, and on dispatch; the summary lists each test's verdict. Prior art: `docs/research/ci-benchmarks.md` on the runners, the emulator runner's documentation, the runner images' Simulator runtimes. Triage protocol: a finding whose test is red on CI is the tool's and its task fixes it; a finding whose test is green on CI and red only on this Mac is the host's, recorded in the README's known issues with the condition it needs (load, a Simulator not booted by the driver); the record goes in "As found" below.

### D2. A refused launch is retried once
`simctl launch` right after an app's termination can fail with `NSPOSIXErrorDomain 3: Simulator device failed to launch <bundle>`, ten times across two runs, a retry after 3 s succeeding every time. The driver retries exactly once, after a bounded wait measured on CI's Simulator and this Mac as the shortest that succeeds (start from 500 ms, double to 3 s), gated on that error alone; the reply says it retried and how long it waited; a second refusal fails as today. No general retry of launches.

As built (task 2.7, 2026-11-01): not reproduced on CI's fresh Simulator, where none of ten launches right after terminate and Home was refused (D1's "As found"), so the retry is a correctness fix gated on its case, the error alone. The driver launches through CoreSimulator's `-[SimDevice launchApplicationAsyncWithID:…]`, not `simctl`, so the fake is a launch call the test supplies. `launch_with` in the macOS driver launches once more after `LAUNCH_RETRY`, 3 s, when the launch call answers `NSPOSIXErrorDomain` 3, and fails as it came on a second refusal or on any other error; the wait is one wait, not the doubling from 500 ms this decision first named, since nothing shorter than 3 s could be measured: CI's Simulator never refused, and the agent's Mac had no device. `Launched::retried_after` carries the wait to the daemon, whose `AppControl::launch` now returns a `Launched`; `open`'s reply names it in `retriedAfterMs`, its line ending `(retried the refused launch after 3000 ms)`. The tests: `macos::driver::tests::a_launch_refused_with_esrch_is_launched_once_more_after_the_wait`, red first, the refusal returned after one call; `handlers::act::tests::an_open_whose_launch_the_driver_retried_says_after_what_wait` and the CLI's `output::tests::an_open_whose_launch_was_retried_says_after_what_wait`; Settings' test on the default apps counts the launches retried (#41). The proof: the filtered device-tests run 41300936685 on iOS 27.0, where `simulator_settings_a_launch_right_after_terminate_and_home_is_not_refused` passes in 188 s; a passing test's output is not printed, and CI's Simulator refuses no launch, so the run shows the launch path with the retry in place, not a retry.

### D3. The read-back waits for the field
`type`'s read-back came one keystroke early once in five runs: the field was read while the last key was in flight. After the keys, the field is read until two consecutive reads agree, or the value holds the text, within a bound of the keys' own time plus a margin, measured on the fake and the Simulator; the line says what it read, and when the read-back is shorter than the text it warns `shorter than typed` instead of ticking. The fake gets a typing mode whose last key lands after the first read, which makes the test red first.

As built (task 2.1, 2026-11-04): not reproduced on CI's fresh Simulator, which read `Lisbon Portugal` back whole five times in five (D1's "As found"), so the fix is gated on its case, keys. The code's cause: a field that showed other text was read until 1 s after the entry whatever the entry, so a last key the app took later than that left the text's start in the read-back, and the CLI's line ticked whatever the read-back said. The rule (`read_bound`): after keys a field that does not show the text is read until 1 s and the time the keys took, the entry's own time measured around it in the daemon, which on a Simulator grows with the text and the host's load and holds the tap that readies a field named by its ref; text in one piece keeps 1 s. At the bound a read-back that holds the start of what the keys would have left (`shorter`: its value, its descendants or the part of its name the entry changed, mask characters counted as the text's) gives `type` the reason `shorter_than_typed` and a warning saying it is shorter than typed, advising `fill`; `fill` takes the same path, its paste again following as before; the CLI's line for a `type` whose field holds other text is marked ⚠ rather than ✓ and says `shorter than typed` for that reason, and the server's text is that line. The clause on two consecutive reads that agree is not built: a field that stops short is a dropped key, and only the bound tells it from a late one, while a still field gets no read on a Simulator before the mirror's 1 s poll; the agent-cli delta's requirement and scenarios read as built. The test: the fake's typing mode `late`, its keys 60 ms apart and the last shown as long after them as they took, 1.38 s for 24 keys: `type` into the focused field read the text less its last key back at 1 s and `fill` pasted it again, both red; the field that keeps its first 6 characters answered `text_mismatch` for `exampl`, red; the CLI's line ticked a differing read-back, red (#48). The proof: the filtered device-tests run 41837061214 on iOS 27.0, where `simulator_maps_type_reads_the_whole_text_back_five_times` passes in 143 s, five `type`s of `Lisbon Portugal` into Maps' emptied search field read back whole, as before the fix on CI's quiet runner; a passing test's output is not printed, so the run shows the bound costing no read-back its whole text, not a late key caught.

### D4. A settle that gives up says so
A settle that stops at its timeout prints ⚠ and exits 0, by the convention of `action-verdicts` (a spinner that keeps turning is not a failure for a model, and a failed call would make it retry). Scripts need to tell the two apart: the reply carries `settled: true|false` and, when false, `stoppedAfterMs` and the reason; the exit status stays 0 unless `--strict` is given, which fails `settle_timeout` in the wait's timeout family. The server's tool keeps the warning and gains the field.

As built (task 2.2, 2026-11-04): the reply carried `settled: false` already; a settle that stops at its timeout now adds `stoppedAfterMs`, how long it waited, and `reason`, what kept changing in its last quiet window, `frames_kept_changing`, `tree_kept_changing`, `tree_and_frames_kept_changing`, or `screen_kept_changing` when it names neither signal, and stays a success with its warning. `--strict` is a flag of the CLI's `wait` alone (`cli::strictly`, which batch entries go through too): it turns such a reply into the failure `settle_timeout`, the warning its message and the settle's data kept, beside `wait_timeout` in the README's code table; the daemon and the server's tool are unchanged, the tool's output schema gaining the two fields through `wire::reply::Wait`, so a model never sees a failed call for a spinner. The test, through the CLI on the fixture's Anim tab: `spans::a_settle_that_gives_up_says_after_how_long_and_why_and_fails_settle_timeout_with_strict`, red on the missing fields; a settled screen passes `--strict`, and `wait --strict` without `--settle` is a usage error, though clap does not refuse it beside a positional, as `--tree-only` and `--quiet` (#47). No test on the default apps: the fake is the proof.

### D5. A tap by coordinates names the labeled element under the point
`hit generic (no ref)` tells the model nothing. The hit's name is the deepest node under the point that has a name, an identifier or a role other than generic; failing that, the nearest labeled ancestor; failing that, the text under the point; `generic` only when nothing under the point is labeled. The reply's `hit` keeps its fields; the line names what it names.

As built (task 2.3, 2026-11-01): the cause, on the fake as on CI's emulator: under the point Clock's minute chip, a checkbox with a ref at `visible=0%`, lay under a view without a label inside a container that bears its identifier alone; no element with a ref takes the tap there, so the hit was the top-most element the full listing lists, the container, `generic` without a name. The rule (`visibility::Sight::named_under`), gated on a hit that is a generic node without a name: the deepest node under the point that the full listing lists, on screen, inside its scroll containers and cut by no modal, whether or not a view drawn over it takes the tap, the one drawn last among equals, and the hit itself when none lies deeper. D5's later clauses, the nearest labeled ancestor and the text under the point, are met by the first: an ancestor or a text under the point is a listed node, and the gated hit always bears an identifier, so the search always finds one; every other hit is as before, the reply's `hit` keeps its fields, and the CLI's line and the server's text name what it names. The test: the placeholder app's overlay board, a button and a text under a disabled view drawn over them in a container with an identifier, and a container holding nothing (`handlers::act::tests::a_click_by_coordinates_names_the_deepest_labeled_element_under_the_point`), red on both platforms for the button and the text, the container named, the empty container generic before and after (#35). The proof: the filtered device-tests run 41285150127 on the emulator, where `android_clock_a_tap_by_coordinates_names_the_labeled_element_it_hit` passes in 33 s; the run reads failed only by its last step, `adb emu kill` finding no emulator console on port 5554, which failed the same way in run 41263236496: the workflow's teardown, not the test.

### D6. The listing after a system window closes
Right after an alert's dismissal, `snapshot` listed no interactive element and the settle said nothing changed, while the full listing held the buttons: the replica still carried the alert's cover over the application window after the alert left, or the read after the dismissal predated it. The mirror re-reads the application's windows when a system window leaves the replica, through the catch-up of `profiling` (`Mirror::reread_now`), and the interactive listing never lists a cover that is gone; the fake gets an alert whose dismissal is scripted, which makes the test red first; CI's fresh Simulator reproduces it on Photos' first launch.

As built (task 2.4, 2026-11-01): the cause is neither a cover the replica kept nor a change the settle did not count. On CI's iOS 27.0 Simulator (run 41263236496) the click on "Don't Allow" saw its tree delta at 175 ms, and `snapshot -i` right after read the device for 170 ms and listed `origin SpringBoard`, `(no interactive elements)`: the Simulator's reader reads the process that owns the foreground, and SpringBoard kept it, holding nothing, after its alert left and before Calendar was active again; the settle after it ended by the tree 1.4 s later and the next listing held Calendar. The replica held SpringBoard's window alone, not a cover over the app's, and a window's arrival or leaving is a delta the settle counts; the fourth pass's "settled after 0 ms: nothing changed" came a model turn after the empty listing, once the worker's poll had read the app. The fake reproduces it: a fake Simulator gives SpringBoard holding nothing for 400 ms once a tap answered its location prompt, and on the fixture's System tab the listing right after the refusal listed SpringBoard with nothing, a settle straight after the click ending before the app came back. The fix: a tap whose top-most window is system UI's and holds a dialog is noted (`Replica::note_tap`), and while the replica then holds system UI's windows alone without a dialog (`Replica::awaiting_application`) the catch-up before every tree read (`Attached::catch_up`) asks the mirror to read again until a window of the application is back (`Mirror::await_application`): at once after each frame change, every minimum re-read interval otherwise, the app's return showing in no frame once the alert's fade has ended, at most `DIALOG_LEAVING`, 2 s, after the tap. A settle on the Simulator reads the tree its frames changed through the catch-up once it settled, so it counts the app's return. On Android the dialog has a window of its own above the app's, which stays, and nothing waits. The delta spec's requirement names the trigger as built, a tap that answers a system dialog with system UI's windows left alone, where it said a system window leaves the replica: on a Simulator system UI's window stands in place of the app's. The test: `handlers::act::tests::the_listing_right_after_a_system_alert_closes_lists_the_screen_and_a_settle_names_the_change`, red on iOS, the listing SpringBoard's, green on Android before and after (#37). The proof: the filtered device-tests run 41287585783 on the Simulator, where `simulator_photos_the_listing_right_after_an_alert_closes_lists_the_screen` passes in 101 s; a passing test's output is not printed.

### D7. A stale ref names the dialog in front
When a stale ref has no twin and `Mirror::system_dialog` holds a dialog, `stale_ref` names the dialog and says to dismiss it; without a dialog the failure is as today.

As built (task 2.5, 2026-11-01): `aim::current`, where a stale ref without a twin fails, asks `Mirror::system_dialog`, and while a dialog of system UI holds the screen the failure reads `e2 is stale: the textbox "Username" it named is not on the screen while alert "Allow “FixtureSwiftUI” to use your location?" of system UI stands in front of it; dismiss the dialog first, with one of the buttons a snapshot lists, then take a new snapshot and use its refs`; without one it is the mirror's, as before. The CLI prints it after ✗, the server after the code, and the agent guide and the server's card say so. The test: on the fixture, the ref the Login tab's snapshot gave the username field, after a move to the System tab and the location prompt, SpringBoard's alert on iOS, whose tree the Simulator's reader reads in place of the app's, and the permission controller's dialog on Android: a click, a fill and a `get` on it failed without naming the dialog on both platforms, red; once the prompt is answered it fails naming none (#42). No test on the default apps shows a system dialog over a rebuilt screen on demand: the fake is the proof.

### D8. A text wait prefers the whole text
`wait --text Lisbon` resolved on "Lisbon Airport (LIS)". Among the elements whose text matches, one whose text is the whole sought text (equal, case and whitespace aside) wins over one whose text merely contains it; ties keep the listing's order; `--text` keeps matching substrings so that a wait for a word still resolves when no element holds it alone.

As built (task 2.6, 2026-11-01): `Selector::whole` and `Mirror::first_match`: for a text the element's name or value need only contain, as `wait --text`, `text=` and a bare text give it, the first element on screen whose name or value is the text alone, both trimmed and compared in lower case, comes before the first that only contains it, then the elements out of sight in the same order; `text==` and the other selectors are unchanged. A click by text resolves its selector the same way, so `click text=Lisbon` taps Lisbon too. The test: the placeholder app's places board, "Lisbon Airport (LIS)" above "Lisbon" (`handlers::act::tests::a_text_wait_prefers_the_element_whose_text_is_the_whole_text`), red on both platforms, the wait and the click resolving on the airport, and a wait for Airport, which no element holds alone, naming the airport (#36). The proof: the filtered device-tests run 41286317143 on the Simulator, where `simulator_maps_a_text_wait_prefers_the_element_whose_text_is_the_whole_text` passes in 121 s with the runner's network; a passing test's output is not printed, so the run does not show whether a text "Lisbon" stood alone on the screen that time.

## Risks / Trade-offs

- The runners' timers coalesce and their load is shared: every device test asserts guarantees, never milliseconds, and the job is not a merge gate.
- A fresh Simulator shows first-launch sheets and permission alerts the tests must dismiss; that is also where D6 reproduces.
- Maps' search and Chrome's first page need the runner's network; a test that cannot reach it is skipped with a reason, not failed.
- `--strict` on settle is one more flag; the default stays the model's convention.
- Fixes to the fixture for iOS 27 must keep iOS 26.5's behavior, which this Mac runs.
